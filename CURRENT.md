| **Last Session Summary** | **7.1 Testing Fundamentals — taught from zero.** Calibration first: student self-reported **A (almost no testing experience** — tests exist at work but they rarely write or read them), and "no idea" on the opening guess, so this was taught as genuine new ground rather than fast-tracked like the React material. Every example was grounded in their own Module 06 milestone app (Repo Pulse). Frame: **manual testing proves the app worked once; a test is that same check written down so it re-runs on every change** — the payoff is not finding bugs today but being able to change code tomorrow without fear (confidence / regression safety / executable documentation). Four concepts. (1) **The pyramid trades confidence for cost** — unit (~1 ms, tells you exactly which function), integration/component (~100 ms, tells you which feature), E2E (seconds, tells you "something somewhere"); why not all E2E (300 E2E = a 30-minute flaky suite → the team stops trusting it → stops running it); the **testing trophy** as the frontend variant (integration fattest, because UI bugs live in the wiring, not in pure functions); the rule both shapes share: **push each test down to the lowest level that can still catch the bug.** Answered the student's opening question directly: with exactly one test, write one E2E happy path (widest net per test), which is also precisely why you do not write 200 of them. (2) **Behavior, not implementation** — litmus: *"if I refactor without changing what the user sees, does this go red?"*; brittle tests are false alarms, and false alarms teach a team to read red as noise; tied back to 6.6 (a behavior test survives swapping TanStack Query out through the seam hook); Arrange–Act–Assert plus test names that read like a promise. (3) **Test doubles** — why the real GitHub API cannot be in the suite (slow / non-deterministic star counts / 60-req-per-hour rate limit); stub vs fake vs mock split by **what you assert** (outcome vs interaction), noting that Vitest calls all three "mock"; rule: **fake the boundaries you do not own, do not mock your own internals** — mocks are right only when the call itself *is* the behavior (analytics fired, payment called once). (4) **What is worth testing** — logic, trust boundaries (their Zod schema), error/empty/loading states, the 1–3 flows that justify the app, and a regression test for every bug fixed; not library internals, not styling, not coverage as a target (coverage measures lines executed, not behavior verified). **Say-back (2 questions, new lighter cadence, skeletons given up front): Q1** (which level for a `1500 → "1.5k"` formatter) — **half right**: correctly rejected E2E as too expensive, but chose *integration* when the answer is *unit*, because the bug lives in a pure function; corrected by restating the reasoning as "ask where the bug lives," plus the architect footnote that if the logic sits inline in a component, the right move is to **extract it so it can be unit-tested** — testability pushes you toward better boundaries. **Q2** (review a PR whose tests assert `useRepoStats` was called and that the error div has class `text-red-600`) — the first slot came back **inverted** (the good check described as the problem), then the student asked for choices directly; multiple-choice offered on all four slots → **4/4 correct** → **full four-beat comment delivered in one pass**, the first time the who-pays ending has landed without a second run.
