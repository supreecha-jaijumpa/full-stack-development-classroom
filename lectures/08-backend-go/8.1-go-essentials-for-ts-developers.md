# 8.1 — Go Essentials for TS Developers

> Module: 08 — Backend with Go · First taught: 2026-11-05 · Last updated: 2026-11-05

## TL;DR
Go looks familiar to a TypeScript developer, but it has stricter rules. Types exist at runtime, every variable has a zero value instead of `undefined`, and a capital letter is what exports a name. Go copies structs when you pass or assign them unless you use a pointer. Expected failures are returned as ordinary `error` values rather than thrown, and wrapping them with `%w` lets callers still identify the original error.

## Key Concepts

### Toolchain and TS equivalents

| TypeScript | Go | The real difference |
|---|---|---|
| `npm init` / `package.json` | `go mod init` / `go.mod` | No `node_modules` folder in your project |
| `tsx file.ts` | `go run .` | Compiles, then runs |
| `tsc` + bundler | `go build` | Produces one standalone binary |
| Vitest / Jest | `go test` | Built in |
| Prettier | `gofmt` | Built in, with no style options |
| `export function` | `func Capitalized()` | The capital letter is the export |
| `interface Track {}` | `type Track struct {}` | A struct is a real value in memory |
| `undefined` | zero value | A declared variable always has a value |

- `package main` plus `func main()` makes a runnable program.
- `var x T` declares a variable with its zero value. `x := value` declares a variable and infers its type. `=` assigns to a variable that already exists.
- `:=` needs at least one new variable on the left, which is why `data, err := ...` can be followed by `tracks, err := ...` in the same scope.
- `gofmt -l .` lists files that need formatting, and `gofmt -w file.go` rewrites a file. On Windows, it also lists correctly laid-out files that use CRLF line endings.
- `go vet ./...` reports suspicious code that still compiles.

### Packages and exported names
A package is one folder of `.go` files. A name that starts with a capital letter is visible outside its package, and a lowercase name is not. This works like `export` in a TS module, but the name itself carries the rule.

### Zero values
Every type has a zero value: `0` for numbers, `""` for strings, `false` for booleans, and `nil` for pointers, slices, and maps. A struct's zero value has each field set to its own zero value.

A missing JSON key leaves a field at its zero value. So `Plays: 0` might mean the key was missing or the value really was `0`.

### Structs and JSON tags
```go
type Track struct {
	ID    int    `json:"id"`
	Title string `json:"title"`
	Plays int    `json:"plays"`
}
```

A **struct tag** names the JSON key for a field. `json.Unmarshal` lives in the `encoding/json` package, so it can only see exported fields. It silently skips unexported ones, with no compile error and no returned error.

Without a tag, the decoder matches names while ignoring case. A misspelled tag key, such as `jdon:"plays"`, is ignored, so the field can appear to work for the wrong reason. Compiling and running `go vet` won't catch it.

### Values vs. pointers
Go copies a struct when you pass it to a function. In TS, passing an object shares it, so this is a major difference.

- `*Track` as a type means "a pointer to a `Track`".
- `&track` means "the address of `track`".

```go
func addPlayByValue(t Track) {
	t.Plays++ // changes the copy only
}

func addPlayByPointer(t *Track) {
	t.Plays++ // changes the caller's struct
}

track := Track{Title: "Blinding Lights", Plays: 10}
addPlayByValue(track)    // track.Plays is still 10
addPlayByPointer(&track) // track.Plays is now 11
```

The function doesn't change the pointer. It uses the pointer to reach the original struct, then changes that struct.

`json.Unmarshal(data, &track)` takes a pointer for the same reason: it has to fill in the caller's variable.

### Slices and `range`

| TypeScript | Go |
|---|---|
| `Track[]` | `[]Track` |
| `arr.push(x)` | `arr = append(arr, x)` |
| `for (const t of tracks)` | `for _, t := range tracks` |

Assign `append`'s result back, because it may return a new slice. `append` also works on a nil slice.

`range` copies each element into the loop variable. To change the elements of a slice, use the index:

```go
for _, t := range tracks {
	t.Plays++ // changes a copy, so tracks is unchanged
}

for i := range tracks {
	tracks[i].Plays++ // changes the element in the slice
}
```

### Maps and `nil`
`map[string]int` has one fixed key type and one fixed value type.

A missing key returns the zero value. Use the two-value form to tell a missing key from a real zero:

```go
plays := map[string]int{"Levitating": 20}
plays["Unknown"]             // 0
count, ok := plays["Unknown"] // 0, false
```

**Reading** a nil map is safe and returns the zero value. **Writing** to one panics, because a nil map has no storage to write into. `make` creates a real, empty map:

```go
var broken map[string]int
broken["x"] = 1 // panic: assignment to entry in nil map

working := make(map[string]int)
working["x"] = 1 // fine
```

`append` can work with a nil slice because it returns a result you assign back. A map write returns nothing, so it has no way to hand back newly created storage.

### Errors are values
A Go function usually returns an error as its last result, and the caller decides what to do with it.

| TypeScript | Go |
|---|---|
| `throw new Error("...")` | `return nil, fmt.Errorf("...")` |
| `try { } catch (e) { }` | `if err != nil { }` |
| `new Error("load failed", { cause: err })` | `fmt.Errorf("load failed: %w", err)` |
| `e instanceof NotFoundError` | `errors.Is` or `errors.As` |

```go
func loadFile(path string) ([]byte, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		return nil, fmt.Errorf("load %s: %w", path, err)
	}
	return data, nil
}
```

After handling an error, usually `return`. Otherwise the code carries on with missing or incomplete data.

### Wrapping with `%w`
`%w` puts the original error inside a new one that adds context. `%v` copies only its text.

- **`errors.Is(err, target)`** checks whether a specific error value, such as `os.ErrNotExist`, is in the chain.
- **`errors.As(err, &target)`** looks for an error of a specific type and gives you access to its fields:

```go
var syntaxErr *json.SyntaxError
if errors.As(err, &syntaxErr) {
	fmt.Println("bad JSON at byte", syntaxErr.Offset)
}
```

### `panic` is not `throw`
A panic means something is broken, such as a bug in the program. Expected failures, like a missing file or bad JSON, should be returned as errors. A missing file does not panic: `os.ReadFile` returns an error, and the program continues normally.

## Examples

### Why `%w` matters in an API
```go
data, err := loadFile(path)
if err != nil {
	if errors.Is(err, os.ErrNotExist) {
		return 404 // not found
	}
	return 500 // any other failure
}
return 200 // success, with data
```

If someone changes `%w` to `%v` in `loadFile`:

1. `err` still isn't nil.
2. `errors.Is` returns `false`, because the original error is gone.
3. The code falls through to the 500.

> `%v` doesn't wrap the original error, so `errors.Is` returns `false`, and the API returns a 500 instead of a 404. **Users** see a generic server error for something that's simply missing. The **business** loses trust and support time. The **team** has to investigate a false server failure, and it's hard to find because the log text looks the same.

### What `%w` and `%v` print
Using a missing file on Windows:

```text
%w
error: load missing.json: open missing.json: The system cannot find the file specified.
not found? true

%v
error: load missing.json: open missing.json: The system cannot find the file specified.
not found? false
```

The text is identical, and only the check result differs.

## Diagrams

```text
%w: wraps the original
+------------------------------+
| "load missing.json: ..."     |
|   +----------------------+   |
|   | original error       |   |  errors.Is finds os.ErrNotExist
|   +----------------------+   |
+------------------------------+

%v: copies the text
+------------------------------+
| "load missing.json: open..." |  text only, so errors.Is finds nothing
+------------------------------+
```

## Common Pitfalls
- **Lowercase struct fields with JSON:** the code compiles and returns no error, but the fields stay at their zero values.
- **Misspelled struct tags:** the tag is ignored, and the case-insensitive name match can hide the mistake.
- **Handling an error without returning:** printing the error and continuing, or returning `value, nil`, tells the caller that everything worked.
- **Expecting a panic for a normal failure:** a missing file returns an error, whereas TS code often expects a throw.
- **Changing the `range` variable:** this changes a copy, not the slice element.
- **Writing to a nil map:** a common source is a struct with a map field that was never initialized.
- **Assuming a map's `0` means the key exists:** use `value, ok := m[key]` when the difference matters.
- **Using `%v` when callers need to check the error:** the log looks identical, but `errors.Is` and `errors.As` stop working.
- **Using `:=` for an existing variable:** with nothing new on the left, it fails with `no new variables on left side of :=`. Use `=`.
- **Reading `os.Args[1]` without checking its length:** this panics when no argument is given.
- **Assuming `fmt.Printf` adds a line break:** it doesn't, so add `\n`. `fmt.Println` adds one for you.
- **Trusting a test file you didn't re-check:** a formatter can repair deliberately invalid JSON, such as a trailing comma, so an error test may pass through the success path.
