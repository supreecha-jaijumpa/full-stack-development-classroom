# 8.1 — Node Runtime & the Event Loop

> Module: 08 — Backend with Go · First taught: 2026-11-03 · Last updated: 2026-11-03

## TL;DR
Node runs your JavaScript on **one thread** and handles the waiting elsewhere, in the OS kernel or libuv's thread pool. All requests take turns on that thread, so one handler doing heavy synchronous work delays every other request on the process. `await` pauses a **function**, not the thread, and it only frees the thread when the work is happening somewhere else. The event loop moves through fixed phases, and after each callback it empties the `nextTick` queue and then the Promise microtask queue.

## Key Concepts

### What Node is made of

| Piece | Job | Browser equivalent |
|---|---|---|
| **V8** | Runs JS on one thread | V8 in Chrome |
| **libuv** | Runs the event loop and handles I/O | The browser's event loop and network stack |
| **Node APIs** (`fs`, `http`, etc.) | Connect JS to libuv | Web APIs (`fetch`, `setTimeout`) |

The model matches a browser click handler. In `await fetch(...)`, the network work happens outside your JS and the UI stays responsive. A 3-second `while` loop in the same handler freezes the tab. On a server, the same freeze affects every user on that process instead of one tab.

### What "non-blocking I/O" means
JS starts the work, registers a callback, and returns. The waiting happens in one of two places:

- **The OS kernel:** network sockets, so thousands of open connections need no extra threads.
- **libuv's thread pool (4 threads by default):** file system work, `dns.lookup`, `zlib`, and some crypto such as `pbkdf2`.

A classic thread-per-request server gives each request its own thread. In Node, requests share one JS thread, and each handler gives up its turn at an `await` on outside work.

### What `await` does
JavaScript evaluates the expression to the right of `await` **first**:

```js
const csv = await buildCsv();
// Step 1: buildCsv() runs to completion. If it is synchronous, the thread is busy.
// Step 2: await receives the finished value
// Step 3: the function pauses briefly, then continues
```

| Code | Where the work happens | Thread free? |
|---|---|---|
| `await db.query(...)` | Database server | Yes |
| `await sleep(3000)` | Timer tracked by the event loop | Yes |
| `await buildCsv()` (synchronous loop) | Your JS, on this thread | **No** |
| `await runInWorker(...)` (your own wrapper) | Another thread | Yes |

Marking a CPU-heavy function `async` doesn't change this, because its loop still runs on the same thread.

### Event loop phases

| Phase | What runs here |
|---|---|
| **Timers** | `setTimeout` and `setInterval` callbacks that are due |
| **Pending callbacks** | A few deferred system callbacks, such as some TCP errors |
| **Poll** | Most I/O callbacks, such as file reads and incoming requests. The loop waits here when idle |
| **Check** | `setImmediate` callbacks |
| **Close** | Close events, such as `socket.on('close')` |

There is also an internal idle/prepare step that application code can ignore. Unlike the browser, Node has no rendering step.

### Priority queues
After **each callback**, Node empties two queues before continuing:

1. The **`process.nextTick` queue**
2. The **Promise microtask queue**

So the order is: current synchronous code → `nextTick` → Promises → the next callback.

Ordering details to remember:
- `nextTick` runs sooner than `setImmediate`, despite the names.
- In the main script, the order of `setTimeout(0)` and `setImmediate` isn't guaranteed. Inside an I/O callback, `setImmediate` always wins, because Check comes right after Poll.
- The priority above applies to CommonJS. In an ES module's top-level code, Promises can run before `nextTick`.

### Where work should run

| Work | Where it runs | Production risk |
|---|---|---|
| Network I/O | OS kernel | Handles thousands of connections cheaply |
| `fs`, `dns.lookup`, `zlib`, `pbkdf2` | libuv thread pool | A fifth slow task queues up, so slow file or password work can delay unrelated work |
| Your own heavy JS | Main thread | Blocks everyone, so move it to `worker_threads` or a background job |

The thread pool only runs libuv's tasks. Making it bigger doesn't help a slow JS loop.

## Examples

### Waiting vs blocking
Both slow routes below take 3 seconds:

```js
const http = require('node:http');
const { setTimeout: sleep } = require('node:timers/promises');

function blockFor(ms) {
  const end = Date.now() + ms;
  while (Date.now() < end) {} // busy CPU work
}

http.createServer(async (req, res) => {
  if (req.url === '/wait') {
    await sleep(3000);
    return res.end('wait done\n');
  }
  if (req.url === '/block') {
    blockFor(3000);
    return res.end('block done\n');
  }
  res.end('ping\n');
}).listen(3000);
```

Suppose a second user calls `/ping` one second after the first user's request:

- **During `/wait`:** the thread is free, so `/ping` responds immediately.
- **During `/block`:** the thread is busy, so `/ping` waits about 2 seconds.

### `await` on synchronous work
```js
const start = Date.now();
setTimeout(() => console.log('500ms timer fired at', Date.now() - start), 500);

(async () => {
  await blockFor(3000); // blockFor from the example above
  console.log('blockFor finished at', Date.now() - start);
})();
```

One run of this printed:

```
blockFor finished at 3001
500ms timer fired at 3013
```

The timer came due at 500 ms but ran about 2.5 seconds late, because its callback needs the thread. Replacing the call with `await sleep(3000)` lets the timer fire on time.

### Log order inside an I/O callback
```js
const fs = require('node:fs');

fs.readFile(__filename, () => {
  setTimeout(() => console.log('A timeout'), 0);
  setImmediate(() => console.log('B immediate'));
  Promise.resolve().then(() => console.log('C promise'));
  process.nextTick(() => console.log('D nextTick'));
  console.log('E sync');
});
```

The order is **E, D, C, B, A**. Synchronous code runs first, then `nextTick`, then Promises. The callback runs in Poll, and Check comes next, so `setImmediate` runs before the timer, which waits for the next iteration's Timers phase.

### A blocking export route
A YouTube-style API builds a large analytics CSV in a synchronous loop that takes 4 seconds. Even if only one admin uses it once a day, this review comment applies:

> **Problem:** This route runs 4 seconds of CPU work on the JS thread.
> **Consequence:** While it runs, every request on that process waits, not just the admin's.
> **Who pays:** Users first, because their requests stall. Then the business, through timeouts and lost trust. Then the team, who have to debug latency spikes on routes nobody changed.
> **Instead:** Move the export to a worker thread or background job, so the main thread stays free.

## Common Pitfalls
- A common mistake is believing `await` makes the thread wait. It pauses the function and leaves the thread free for other work.
- Another is believing `await` or `async` makes synchronous code non-blocking. The synchronous call finishes before `await` does anything, so it looks safe in code review but still stalls every request.
- Treating a rarely used route as safe to block. Frequency doesn't limit the impact, because every request on that process stalls while it runs.
- Using the thread pool size to fix a slow JS loop, or moving blocking work to night hours. Neither takes the work off the main thread, and a global audience may be awake at night.
- Calling sync APIs such as `readFileSync` in a request handler, or running `JSON.parse` on a huge payload.
- Using a recursive `nextTick`, which starves the loop because I/O never gets a turn.
- Leaving rejections unhandled. They crash the process by default since Node 15.
