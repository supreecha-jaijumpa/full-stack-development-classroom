# 3.8 — Build an Interactive App

> Module: 03 — JavaScript Fundamentals · First taught: 2026-06-23 · Last updated: 2026-06-23

## TL;DR
The Module 03 capstone: plan a vanilla-JS app around a public API, fetch its data once on load, render it as DOM elements, and let the user filter it in memory without re-fetching. Organize everything across four ES modules — data, UI, logic, and orchestration — and deploy the result. Every prior concept in the module becomes concrete in one working application.

## Key Concepts

### App architecture: four-module split
A small vanilla-JS app maps cleanly to four files with distinct responsibilities:

| File | Owns | Exports |
|------|------|---------|
| `api.js` | Network communication | `fetchRepos()` |
| `ui.js` | DOM writes | `showLoading`, `showError`, `renderCards`, `populateLanguageDropdown` |
| `filters.js` | Filter logic | `filterRepos(repos, term, language)` |
| `main.js` | Application state + event wiring | *(none — entry point)* |

`main.js` imports from the other three but the other three never import from each other. This pattern mirrors layered architecture at scale (data layer / presentation layer / business logic / controller) — the boundary concepts are the same even when files get larger.

### In-memory filtering vs re-fetching
Fetch the full dataset once, store it in a variable, filter locally on every interaction. Re-fetching on every keypress costs:
- A network round trip (100–500ms minimum)
- API rate limits (GitHub's unauthenticated limit: 10 requests/minute)
- A visible loading flash on every character typed

Filtering a local array is synchronous and instant. This is the same principle behind TanStack Query's `select` option and most client-side search implementations.

### Pure functions for filter logic

```js
export function filterRepos(repos, searchTerm, language) {
  const term = searchTerm.toLowerCase();
  return repos.filter(repo => {
    const matchesSearch = repo.name.toLowerCase().includes(term);
    const matchesLanguage = !language || repo.language === language;
    return matchesSearch && matchesLanguage;
  });
}
```

A pure function takes inputs, returns a value, and changes nothing outside of itself. No DOM access, no state mutation, no side effects. The `!language` guard handles the "All Languages" case — when `language` is an empty string, the condition is true for every repo.

Pure functions are trivially testable (input/output only) and safe to call from any event handler.

### State ownership in a module
Module-level variables act as application state when there is no framework:

```js
let allRepos = [];
let searchTerm = '';
let selectedLanguage = '';

function applyFilters() {
  renderCards(filterRepos(allRepos, searchTerm, selectedLanguage));
}
```

`allRepos` is the single source of truth — fetched once, never modified. Both event handlers update their own slice of state and call the same `applyFilters()`. React's `useState` solves exactly the same problem at the component level.

### XSS risk when injecting external data into innerHTML
`innerHTML` parses whatever string it receives as HTML. If that string contains `<script>` or `<img onerror="...">`, it executes:

```js
// Risky — repo.description comes from an external API
container.innerHTML = `<p>${repo.description}</p>`;

// Safe — textContent sets plain text; HTML is never parsed
const p = document.createElement('p');
p.textContent = repo.description;
```

For text-only content, always use `textContent`. If rich external content is required, sanitize first (e.g., `DOMPurify`). This is the most common source of XSS bugs in production JavaScript.

## Examples

### GitHub Repo Explorer
Built in this session — live at https://supreecha-jaijumpa.github.io/github-repo-explorer/

- Fetches the 30 most-starred JavaScript repos via the GitHub Search API
- Renders each repo as a card: name (linked), description, star count, language badge
- Search input (input event) updates `searchTerm` and calls `applyFilters()`
- Language dropdown (change event) updates `selectedLanguage` and calls `applyFilters()`
- No re-fetch on filter interaction — both events re-render from `allRepos` in memory

```
GitHub API → allRepos[]
                  │
    searchTerm ───┤ filterRepos() → renderCards()
selectedLanguage ─┘
```

### Netflix client-side filtering
Netflix fetches your content list once per page load and filters it locally as you interact with genre chips, search, or sort — same pattern at much larger scale with millions of client instances avoiding repeated server calls.

## Common Pitfalls

A common mistake is re-fetching from the API on every search keystroke. Fetch once on load, store the full result, and filter the local array on each interaction.

A common mistake is putting filter logic directly inside the event handler. When two events (search and language dropdown) both need to apply the same combined filter, duplicating the logic causes them to diverge. Extract to one `applyFilters()` function that both handlers call.

A common mistake is mixing concerns across modules — for example, making a `fetch` call inside `ui.js`. If a module starts doing two jobs, split it. The rule is: each module has one reason to change.

A common mistake is injecting external API data directly into `innerHTML`. Text fields from any external source (description, title, name) should go through `textContent` — not raw `innerHTML`.
