# 3.7 — ES Modules

> Module: 03 — JavaScript Fundamentals · First taught: 2026-06-23 · Last updated: 2026-06-23

## TL;DR
ES Modules is the system JavaScript uses to split code across files and share it with `import` and `export`. Each file gets its own isolated scope — nothing leaks to `window`. A module runs exactly once regardless of how many files import it, so all importers share the same instance. Bundlers like Vite serve native ES modules in development and bundle them for production.

## Key Concepts

### The Three Import Forms

| Syntax | What it does |
|--------|-------------|
| `import { add } from './math.js'` | Named import — picks one specific named export |
| `import Multiply from './math.js'` | Default import — picks the single default export |
| `import * as Math from './math.js'` | Namespace import — collects ALL named exports under one object |

Named imports use `{ }` because a file can have many named exports — you must specify which ones you want. Default imports omit `{ }` because a file can only have one default export — and the consumer can name it anything:

```js
import React from 'react'     // valid
import Whatever from 'react'  // also valid — same default export, different local name
```

`import React from 'react'` is a **default import** of React's default export object. It is NOT the same as `import * as React from 'react'` (namespace import), which collects all named exports under one object.

### Named vs Default Exports

```js
// math.js
export const add = (a, b) => a + b        // named export — many allowed per file
export default function multiply(a, b) {   // default export — only one per file
  return a * b
}
```

Rules:
- A file can have **many named exports**
- A file can have at most **one default export**
- Named imports must match the export name exactly (or use `as` to alias: `import { add as sum }`)
- Default import names are chosen entirely by the consumer

### Module Paths

```js
import { useState } from 'react'         // no dot = node_modules package
import { add } from './math.js'          // ./ = relative path from this file
import { format } from '../utils/fmt.js' // ../ = up one directory
```

The runtime (browser or Node/Vite) uses the path prefix to decide where to look. Omitting `./` from a local file makes it try node_modules instead — a common bug.

### Module Scope

Before modules, every `<script>` tag shared the global `window` scope — a later file could silently overwrite a variable declared in an earlier one. With modules, each file has its own scope. Nothing leaks to `window` unless explicitly assigned. `<script type="module">` is required in HTML to activate this behavior.

### The Singleton Rule

A module executes exactly once, regardless of how many files import it. All importers share the same instance:

```js
// counter.js
let count = 0
export const increment = () => ++count
export const getCount = () => count
```

If `a.js` and `b.js` both import from `counter.js`, they share the same `count`. This is the foundation of module-level singleton stores.

### How Vite Uses Modules

**Development:** Vite serves files directly as native ES modules. The browser fetches `main.js`, sees `import` statements, and fetches each imported file in turn — no bundling step, which makes cold-start fast.

**Production (`vite build`):** Vite traces the full import graph and bundles everything into a handful of optimized chunks. Hundreds of small dev files become fewer, minified prod files. The `import`/`export` syntax you write stays unchanged — Vite handles the translation.

## Examples

### Splitting a single script into modules

Before (everything in one file):
```js
const users = [{ name: 'Alice', score: 90 }, { name: 'Bob', score: 75 }]
function getTopUser(users) { return users.reduce((top, u) => u.score > top.score ? u : top) }
function renderUser(user) { document.body.textContent = `${user.name} — ${user.score}` }
renderUser(getTopUser(users))
```

After (split into three files):
```js
// data.js
export const users = [
  { name: 'Alice', score: 90 },
  { name: 'Bob', score: 75 },
]
export function getTopUser(users) {
  return users.reduce((top, u) => u.score > top.score ? u : top)
}

// ui.js
export function renderUser(user) {
  const div = document.createElement('div')
  div.textContent = `${user.name} — ${user.score}`
  document.body.appendChild(div)
}

// main.js — entry point, no exports needed
import { users, getTopUser } from './data.js'
import { renderUser } from './ui.js'
renderUser(getTopUser(users))
```

`main.js` has no exports — entry points consume, they don't expose. Same pattern as `main.tsx` in every Vite/React project.

### Module-level singleton

```js
// store.js
let count = 0
export const increment = () => ++count
export const getCount = () => count

// ComponentA.js
import { increment } from './store.js'
increment() // count → 1

// ComponentB.js
import { getCount } from './store.js'
console.log(getCount()) // 1 — same instance, same count
```

## Common Pitfalls

- **Confusing default import with namespace import.** `import React from 'react'` imports only the default export object. `import * as React from 'react'` imports all named exports under one namespace. They look similar in usage but are different things.
- **Expecting named imports to work with arbitrary names.** `export const add` must be imported as `{ add }`. Use `import { add as sum }` to rename it locally.
- **Expecting a module to re-run on every import.** Top-level code runs once. Side effects (like `console.log`) fire once no matter how many files import the module.
- **Omitting `./` from relative paths.** `import { x } from 'utils'` looks in node_modules. `import { x } from './utils'` looks on disk next to the current file.
- **Using `<script src>` without `type="module"` in vanilla HTML.** `import`/`export` syntax only works inside `<script type="module">`. Without it the browser throws a syntax error.
