# 5.3 — State & Events

> Module: 05 — React Fundamentals · First taught: 2026-06-29 · Last updated: 2026-06-29

## TL;DR
State is the data a component holds that changes over time *and* cannot be derived from anything it already has. Events (`onClick`, `onChange`, `onSubmit`) are how the user pushes new values into that state, and React re-runs the component to reflect them. The hard part is not the `useState` API — it is judgment: deciding *what* deserves to be state, *where* that state should live, and *why* React makes state asynchronous and immutable. All three questions are the same principle in disguise: **single source of truth.**

## Key Concepts

### What counts as state (the two-clause test)
A value earns a `useState` slot only if it passes **both** tests:

1. **It changes over time**, and
2. **It cannot be computed from data you already hold.**

"It renders to the screen" is *not* a test — plenty of rendered values are not state.

| Candidate | State? | Why |
|---|---|---|
| List fetched from an API | yes (server state) | changes over time, can't be derived |
| Whether a dropdown is open | yes (UI state) | changes over time, can't be derived |
| The list's length / item count | **no** | derivable: `list.length` |
| The currently logged-in user | not *this component's* state | owned elsewhere (auth/context) |

> **"Don't put in state what you can calculate during render."**

A stored copy of derived data is a **second source of truth that can drift** out of sync with the first — add an item, forget to bump the stored count, and the UI now lies. You manufactured a whole class of bug by storing something you could have recomputed for free.

The fourth row adds the **ownership test**: a value can be genuine state yet not belong to *this* component. The logged-in user is real, mutable state — but it lives in auth/context, not in a card that merely displays it. **Wrong owner is as much a bug as wrong type.**

### Events and the synthetic event
React does not attach listeners to each DOM node. It attaches one listener per event type at the app root and dispatches via bubbling, wrapping the native event in a cross-browser **synthetic event**. You read values off it the same way (`e.target.value`), but you type it with React's types, keyed by **event + element**:

| Handler | Type |
|---|---|
| `onChange` on an input | `React.ChangeEvent<HTMLInputElement>` |
| `onSubmit` on a form | `React.FormEvent<HTMLFormElement>` |
| `onClick` on a button | `React.MouseEvent<HTMLButtonElement>` |

It is **not** the raw DOM `InputEvent`. A controlled input wires value + change together:

```tsx
const [query, setQuery] = useState<string>("");

const handleChange = (e: React.ChangeEvent<HTMLInputElement>): void => {
  setQuery(e.target.value);
};

<input value={query} onChange={handleChange} />
```

This is a **controlled input**: state is the single source of truth, the DOM only mirrors it.

### Where state lives — lift only what is shared
When two siblings need the same value, you cannot leave it inside one of them. **Lift it up** to their nearest common parent and pass it down as props; the parent becomes the owner, one child writes it, the other reads it.

But lifting is not free:
- The parent now re-renders whenever that value changes.
- The two siblings are **coupled through the parent** — prop-drilling is the bill.

So the rule is **lift only what is shared; colocate everything else.** A search box's `query` that no sibling reads should stay *local* to the search box. Lifting it anyway pays the coupling cost for zero benefit. (Putting shared state in the **URL** query string is a legitimate senior alternative when the state should be shareable/bookmarkable — the trade is global, stringly-typed state plus history/debounce concerns.)

### Why state is async + re-render, not mutate
React state setters do not mutate in place; they schedule a re-render with a new value. Two reasons:

1. **Batching** — multiple `setState` calls inside one event handler collapse into **one** re-render, not N.
2. **Snapshot consistency (the big one)** — within a single render, state is a *frozen snapshot*; every line of the component sees the same value top to bottom. If a setter mutated synchronously mid-render, the value could change between line 10 and line 40 of the *same* render, and the output would be built from two different truths. That inconsistency is called **tearing**.

This protects the core contract **`UI = f(state)`**: render is a *pure function* of a stable snapshot. Mutation breaks purity, so React forbids it. When the next value depends on the previous one, use the **functional update**:

```tsx
setItems((prev) => [...prev, newItem]);
```

### Invariant vs affordance — where to enforce a rule
When a rule must always hold (e.g. "the list never contains duplicates"), *where* you enforce it matters:

- An **affordance** is a UI hint that *discourages* an action — a `disabled` button. It lives in one component and protects nothing structurally; remove it, add a second caller, fire it from a keyboard shortcut, and the rule is gone.
- An **invariant** must be enforced at the **state boundary** — the single chokepoint every write passes through (inside the setter/handler). Then it holds for *every* path, regardless of UI.

> **The disable is a courtesy; the guard is the law.**

This refines the "defensive code is bad" idea from props design: defensive code is bad **at the edges** (every component re-validating its inputs) but **correct at the chokepoint** (one guard where all writes converge). Same instinct, different altitude.

## Examples

### Playlist builder (two siblings + a parent)
A feature that lets a user search a video catalog and build a playlist, with a live summary — a clean illustration of all four concepts.

- **Catalog** of videos → a module constant, *not state* (never changes).
- **`playlist`** (the added videos) → real state, **lifted to the parent** because both siblings touch it.
- **`searchTerm`** → state, but **local** to the search component (no sibling reads it).
- **Item count and total duration** → *derived* from `playlist` (`playlist.length`, `playlist.reduce(...)`), never their own state.
- **"Add" vs "Added"** on each row → *derived* from whether the playlist already contains that id, never a third state.

```tsx
type Video = { id: number; title: string; min: number };

const CATALOG: readonly Video[] = [ /* ...fixed list... */ ];

function PlaylistBuilder() {
  const [playlist, setPlaylist] = useState<Video[]>([]); // the ONE source of truth

  const playlistIds = new Set<number>(playlist.map((v) => v.id)); // derived

  const handleAdd = (video: Video): void => {
    // invariant enforced at the chokepoint, not at the button
    setPlaylist((prev) =>
      prev.some((v) => v.id === video.id) ? prev : [...prev, video]
    );
  };

  return (
    <>
      {/* each child gets the SMALLEST thing it needs */}
      <VideoSearch playlistIds={playlistIds} onAdd={handleAdd} />
      <PlaylistSummary playlist={playlist} />
    </>
  );
}
```

Note the **minimal prop surface** (a 5.2 idea applied here): the search component receives only a `Set<number>` of ids (O(1) `.has()` for the Added check), while the summary receives the full array it needs to total. Each sibling gets the smallest thing that does its job.

## Common Pitfalls
- **Storing derived data in state.** A common mistake is keeping a count, a filtered list, or a boolean flag in its own `useState` when it can be recomputed from existing state each render — it creates a second source of truth that drifts and makes the UI lie.
- **Lifting everything "to be safe."** A common mistake is hoisting state to a parent that no sibling actually needs, paying re-render + coupling costs for nothing. Lift only what is shared; colocate the rest.
- **Enforcing an invariant in the UI instead of at the boundary.** A common mistake is relying on a `disabled` button to prevent an illegal action; the rule must live in the state-writing function so it holds for every caller.
- **Typing the event as the raw DOM type.** A common mistake is `InputEvent`/untyped `e` instead of `React.ChangeEvent<HTMLInputElement>`, leaving the handler as implicit `any`.
- **`never[]` inference.** A common mistake is `useState([])` for an array of objects — TS infers `never[]` and rejects every push; annotate it `useState<Item[]>([])`.
- **Forgetting the functional updater.** A common mistake is `setX([...x, item])` when several updates queue in one handler; derive from `prev` instead: `setX(prev => [...prev, item])`.
- **Permitting mutation through a read-only prop.** A child that only reads a list should type the prop `readonly Item[]` so the contract forbids `push`/`splice`.
