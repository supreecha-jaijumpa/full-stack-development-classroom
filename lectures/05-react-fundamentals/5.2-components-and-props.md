# 5.2 — Components & Props

> Module: 05 — React Fundamentals · First taught: 2026-06-28 · Last updated: 2026-06-28

## TL;DR
A component's prop interface is a **public API**, not a bag of function arguments — every prop is a promise you keep forever. Good prop design minimizes the surface and makes illegal states unrepresentable, so bad combinations fail at compile time instead of being defended against at runtime. Props flow one way (down) and are read-only; events flow up. Prefer composition (`children`) over piling on configuration knobs — pass a value as a **prop** when the component must *interpret* it, and as **children** when it only needs to *place* it.

## Key Concepts

### Props are a contract, not arguments
A component is a unit other people (and future-you) compose. The architect question is not "what data does this need?" but **"what is the smallest, hardest-to-misuse surface that still does the job?"** Three principles:

1. **One-way data flow** — props go down, events go up. Props are read-only; a child mutating a prop is like a function reaching out to edit its caller's variables.
2. **Make illegal states unrepresentable** — the type system should reject bad prop combinations at compile time, not at runtime.
3. **Composition over configuration** — prefer passing *content* (`children`) over accumulating boolean/string knobs.

### Who pays for "flexibility"?
Making every prop optional does **not** add flexibility — it moves the cost downstream. Each optional prop is a branch the *component* must now defend against. "Flexible for the caller" becomes "the caller's laziness is the component's bug surface." A contract is made flexible by making it *correct*, not by making it *weak*. If a component can't render without a value, the type should require it.

### Make illegal states unrepresentable (discriminated unions)
A set of mutually exclusive flags (`isLive`, `isPremiere`, `isMembersOnly`) is a trap: nothing stops a caller passing all three `true`, so the component grows defensive code for states that should never exist. Model the *one* real status as a **discriminated union** instead:

```tsx
type VideoBadge =
  | { kind: "live" }
  | { kind: "premiere"; startsAt: Date }  // forces startsAt to travel with premiere
  | { kind: "members" }
  | { kind: "none" };
```

Now the three-booleans bug is structurally impossible, and `premiere` *cannot* be constructed without its `startsAt`. The invariant is enforced by the type checker at every call site — not by a comment and a code review hoping someone remembers.

### Lift shared fields to a base, put variant-only fields on the variant arm
When some fields exist only for one variant (e.g. only a top-level comment can be pinned or have replies), put them on that arm of the union, not on a shared base with a runtime "ignore these if it's a reply" rule. A leaf variant then *cannot be constructed* with fields it shouldn't have.

```tsx
interface CommentBase {            // fields every node carries
  id: string;
  author: { name: string; avatarUrl: string };
  text: string;
  likeCount: number;
  publishedAt: string;             // ISO string — format at render, don't pre-stringify
}
interface TopLevelComment extends CommentBase {
  kind: "top-level";
  pinnedByChannelName?: string;    // pinning is top-level-only → lives here exclusively
  replies?: { count: number; items: ReplyComment[] };
}
interface ReplyComment extends CommentBase {
  kind: "reply";                   // leaf: cannot be pinned, cannot nest
}
type CommentItemProps = TopLevelComment | ReplyComment;
```

### Prop vs. children: interpret vs. place
- Use a **prop** when the component must *understand* the value — format it, branch on it, style it. (A like count is a prop: the button formats `1.2M`, pluralizes, hides at zero.)
- Use **`children`** when the component only needs to *place* it in a slot, without knowing what it is. (A card's caption/channel row is `children`: the card just positions it.)

This is why `children` is "composition over configuration" in practice — instead of six props for everything under a title, the card exposes one slot and the parent composes the content.

### Optional boolean smell
`flag?: boolean` has three states: `true | false | undefined` — but `false` and `undefined` usually mean the same thing, so the third state is noise. Prefer a required boolean with a default of `false`, or model presence-only, keeping the same illegal-states discipline.

## Examples

**YouTube "Up next" card.** A naive `<Card>` with `thumbnail?`, `icon?: string`, and three independent badge booleans is a weak contract: `icon` says nothing about whether it's an emoji/URL/name, and the booleans allow three-badges-at-once. Tightened: `thumbnail` required (a card without one is broken), one `badge?: VideoBadge` discriminated union, and a `children` slot for the channel row / view count so the card doesn't need a prop per line of metadata.

**YouTube comment thread.** Top-level comments can be pinned and can show "View N replies"; replies are indented leaves that can do neither. Splitting `TopLevelComment | ReplyComment` over a shared `CommentBase` makes a reply carrying pin/reply-count data a compile error. `replies` bundles `count` + loaded `items` together so the toggle can render "View N replies" before any replies are fetched.

## Common Pitfalls
- **Optional-everything contracts.** Making all props optional doesn't add flexibility — it pushes defensive branching into the component for states that should be impossible.
- **Parallel mutually-exclusive booleans** (`isLive`/`isPremiere`/...) instead of one discriminated union — allows nonsense combinations the component then has to guard.
- **Putting variant-only fields on a shared base** and ignoring them at runtime for the wrong variant — the invariant lives in a comment, not the compiler.
- **Three-state optional booleans** where `false` and `undefined` collapse to the same meaning.
- **Reaching for `children` when the component must interpret the value** (e.g. a count it formats) — that's a prop, not a slot.
- **Pre-stringifying values** (timestamps, counts) in props — pass raw data and format at render so the component controls presentation.
