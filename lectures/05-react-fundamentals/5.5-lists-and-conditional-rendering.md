# 5.5 — Lists & Conditional Rendering

> Module: 05 — React Fundamentals · First taught: 2026-06-29 · Last updated: 2026-06-29

## TL;DR
Rendering collections (`array.map(...)`) and showing/hiding UI (`&&`, ternary, early return) are mechanically trivial — the depth is in two ideas that are really about **identity** and **correctness**, not syntax. A `key` is React's way of tracking *which element is the same element across renders*, so it binds DOM nodes and component state to a piece of *data*, not to a *position* — get this wrong (index keys on a reorderable list) and state silently attaches to the wrong row. Conditional rendering with `&&` carries a JavaScript footgun: `&&` returns its left operand when falsy, and React renders `0` and `""` (but skips `false`/`null`/`undefined`), so a raw `count && <X/>` leaks a literal `0` into the UI. Both topics reduce to: keys are a correctness primitive that happens to be fast; conditions need a real boolean.

## Key Concepts

### Rendering a list: `.map()` returns elements
A React element is just data (see 5.1), so you produce a list by mapping data → elements:

```tsx
{songs.map((song) => <SongRow key={song.id} song={song} />)}
```

Each iteration returns one element; React renders the resulting array of elements in order. Filtering/sorting is plain array work done *before* `.map()` — keep the transform pipeline (`filter → sort → map`) outside the JSX or in a clearly-named variable so the render stays readable.

### The `key` prop is an identity claim, not a label
This is the concept that carries the whole topic.

> A `key` is not for you — it's how you tell React's reconciler **which element is *the same element* as one from the previous render.**

When a component re-renders a list, React must match each new element to a previous one to decide: reuse this instance (and its DOM node + local state), create a new one, or remove an old one. It matches **by key**. So the key answers "is this the same thing as before?" — an identity question.

- **Stable data key (`key={song.id}`):** identity is bound to the *song*. When the list reorders or filters, React follows each song to its new position, preserving that row's DOM node and local state correctly.
- **Array index (`key={index}`):** identity is bound to the *slot*. "The same element" means "whatever is in position 0 now." On reorder/insert/delete, React keeps the slot's component instance but feeds it different data — so the row *re-renders with correct text* but its **local state stays behind on the wrong item.**

### Why index keys break — the precise mechanism
A common wrong explanation is "index keys stop the row from re-rendering." It does re-render. Here's what actually happens on a reorder:

1. Item that was at index 0 (Song A) is now at index 4; Song B is now at index 0.
2. React sees `key={0}` again → decides "same element as last render" → **reuses that component instance.**
3. It passes the new prop (`song={B}`), so the instance re-renders and the **visible text updates to B — correctly.**
4. But the instance's **local state** (an open "⋯" menu, focus, a half-typed input) was never reset — it's still the state that belonged to Song A, now displayed on Song B's row.

So the bug is not "wrong text" — it's **stateful UI landing on the wrong row.** Index keys glue component *state* to a *position*; when positions and data decouple, state desyncs.

### Stable keys = correctness first, performance for free
When 3 items are removed from the middle of a 50-item list:
- **With `key={id}`:** React matches keys by identity. The 3 removed ids have no match → unmount exactly those 3. The other 47 keys still match → those instances stay untouched in place.
- **With `key={index}`:** removing 3 from the middle shifts every index below them, so ~26 rows now "belong" to a different item → React reconciles 26 rows that didn't change.

The reduced DOM work is real but it is the **side effect**. The fundamental purpose of a key is *identity preservation*, and identity preservation is a **correctness** guarantee: each DOM node and its local state stay bonded to the right data. The real failure mode of bad keys is not "slow" — it's "wrong" (lost focus, an input's text jumping rows, a CSS transition animating the wrong element).

> Same shape as `useEffect` ("a sync primitive, not a lifecycle hook"): React APIs sold as performance tools are often really **identity/correctness** tools.

### Conditional rendering: three tools
- **`&&`** — "render this or nothing": `{isLoading && <Spinner />}`. React renders nothing for `false`/`null`/`undefined`.
- **Ternary** — "render A or B": `{isError ? <Error /> : <List />}`. Forces you to name both branches.
- **Early return** — bail out of the whole component for a top-level state: `if (loading) return <Spinner />;` before the main JSX. Good for loading/error gates.

### The `&&` falsy-leak footgun
Two facts collide:

1. **`a && b` returns `a` when `a` is falsy** (not a boolean). So `0 && <Badge/>` evaluates to `0` (the number), and `"" && <X/>` evaluates to `""`.
2. **React skips `false`/`null`/`undefined`/`true`, but renders `0` and `""`** as text nodes (a `0` is legitimately displayable — a price, a count).

Result: `{cartItems.length && <Badge/>}` on an empty cart → `0 && <Badge/>` → `0` → React prints a stray **`0`** in the UI. Fix by guaranteeing a real boolean: `{cartItems.length > 0 && <Badge/>}` (`0 > 0` is `false`, which React skips). Architect habit: the moment a number or string could reach the left of `&&`, prefer a ternary — it forces an explicit else-branch (`: null`) and cannot leak.

### Empty states are a first-class branch
"No results" is not an afterthought — it's a real UI state. A filtered list has (at least) two display states: items, and empty. Model it explicitly:

```tsx
{visible.length > 0
  ? <ul>{visible.map((i) => <Row key={i.id} item={i} />)}</ul>
  : <EmptyState message="No items match your search." />}
```

## Examples

### Spotify "Liked Songs" — why index keys detonate
Render rows with `key={index}`, open the "⋯" context menu on a song, then hit **Sort by recently added**. The array reorders; React reuses each slot's instance with new data, but the open-menu state stays on slot N — so the menu is now floating over a *different* song. Switching to `key={song.id}` ties the menu state to the song, so it follows the song (or closes with it).

### GitHub issues list — filtering by label
A 50-issue list keyed by `issue.id`. Filtering out 3 issues from the middle unmounts exactly those 3 and leaves the other 47 in place — surviving rows keep focus, scroll position, and any in-row editing state. With index keys, the same filter reconciles ~26 rows and can drop focus or visually "shift" an open inline editor onto the wrong issue.

### YouTube notification badge — the `0` leak
`{unreadCount && <Badge count={unreadCount} />}` renders a literal `0` next to the bell icon when the user has zero unread items. `{unreadCount > 0 && <Badge count={unreadCount} />}` (or a ternary) renders nothing, as intended.

## Common Pitfalls
- **Using the array index as `key` on a list that can reorder, filter, or have items inserted/removed.** Safe only for static, append-only, never-reordered lists. The symptom is never wrong text — it's stateful UI (focus, open menus, inputs, animations) attached to the wrong row.
- **Believing keys are a performance feature.** They are a *correctness* feature (identity); the speed is a consequence. Optimizing keys "for performance" misses that the real bug class is incorrect behavior.
- **Guarding JSX with a raw number or string: `{count && <X/>}`.** Leaks a literal `0` (or empty string) into the DOM because `&&` returns the falsy left operand and React renders `0`/`""`. Coerce to boolean (`count > 0 &&`) or use a ternary.
- **Reaching for `&&` when both branches exist.** If there's a real "else," a ternary (or early return) is clearer and leak-proof — it forces you to name the alternative.
- **Treating the empty/"no results" state as an afterthought.** It's a distinct UI state; render it explicitly instead of letting an empty list render as a blank void.
- **Putting heavy `filter`/`sort` logic inline in JSX.** Compute the visible array in a named variable (or `useMemo` if expensive) above the return — keeps render readable and the transform pipeline obvious.

## Quick Recall

6. Where in the render flow should `filter`/`sort` happen, and why not inline in the JSX?
