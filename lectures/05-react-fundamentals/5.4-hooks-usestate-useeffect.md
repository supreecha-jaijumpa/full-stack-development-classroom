# 5.4 — Hooks: useState & useEffect

> Module: 05 — React Fundamentals · First taught: 2026-06-29 · Last updated: 2026-06-29

## TL;DR
`useState` declares a value React tracks across renders; type it with a generic when the initial value can't infer the full type (`useState<User | null>(null)`). `useEffect` is **not** a lifecycle hook — it is a *synchronization* primitive: it keeps something **outside** React's world (the network, `document.title`, a subscription, a timer) in sync with your state, running *after* the DOM is committed. The dependency array is a **declaration of what the synced output depends on**, not a list of triggers, and the cleanup function **undoes the previous sync before the next one runs** (unmount is just the final sync to nothing).

## Key Concepts

### useState in one line
`const [value, setValue] = useState(initial)`. The setter schedules a re-render with the new value; it does not mutate in place. Use a **functional update** `setValue(prev => …)` whenever the next value derives from the previous one. Type with a generic when inference isn't enough:

```tsx
const [user, setUser] = useState<User | null>(null);   // would infer `null` only
const [items, setItems] = useState<Item[]>([]);        // would infer `never[]`
```

### useEffect is synchronization, not lifecycle
The common (wrong-altitude) model is "componentDidMount + componentDidUpdate + componentWillUnmount in one." That model makes you ask *"when does this run?"* and you get the deps array wrong.

The correct model: **an effect keeps an external system in sync with current state.**

- `UI = f(state)` is what `render` gives you for free — but render can only touch React-owned things (the DOM, via the virtual DOM).
- Anything **outside** React's world — `fetch`, a WebSocket, `document.title`, `setInterval`, a third-party chart lib — render cannot touch.
- `useEffect` is the bridge: `externalSystem = f(state)`, run after the DOM is committed.

You stop thinking in *moments* (mount/update/unmount) and start thinking in *consistency*: "given the current state, what should the outside world look like, and how do I get it there?"

This single reframe answers three questions at once:

| Question | Lifecycle answer (wrong) | Sync answer (right) |
|---|---|---|
| What goes in deps? | "things that should trigger a re-run" | "every reactive value the effect *reads*" — a declaration of what the output depends on |
| Why cleanup? | "avoid leaks on unmount" | "undo the last sync before the next one — unmount is just the final sync to nothing" |
| Why did it run twice? | "Strict Mode is annoying" | "if setup→cleanup→setup breaks you, the effect isn't a true sync — it has a hidden run-once assumption" |

### The dependency array is a contract
The `react-hooks/exhaustive-deps` lint rule forces every reactive value the effect reads into the array. The reason, in sync terms:

> The deps array is a promise that the effect's output depends on *exactly* these reactive values. Lie about it (e.g. write `[]` when the effect reads `trackId`) and you've told React the external system is in sync when it's actually tracking a **stale** value — the invariant `externalSystem === f(currentState)` is broken.

- `[]` (empty) → effect runs once after mount, never re-syncs. Correct only when the effect reads no reactive values.
- `[a, b]` → re-runs whenever `a` or `b` changes (by `Object.is` comparison).
- no array → runs after *every* render (rarely what you want).

### Cleanup = the first half of the next sync
The function you `return` from an effect runs **before the next run of that effect** and **on unmount**. Its job is to undo the previous sync: unsubscribe the old WebSocket, `clearInterval` the old timer, `abort` the old fetch. Unmount is simply the last sync — to nothing.

### Rules of Hooks
- Call hooks only at the **top level** of a component or custom hook — never inside conditions, loops, or nested functions. React tracks hooks by call **order**, so the order must be identical on every render.
- Call them only from **React function components** or **custom hooks** (functions named `use*`).

## Examples

### Fetch-on-change with a cancelled request (the canonical effect)
A "now playing" lyrics panel: when the track changes, an external system (the lyrics API) must re-sync to the new `trackId`.

```tsx
function TrackLyrics({ trackId }: { trackId: string }) {
  const [lyrics, setLyrics] = useState<{ lines: string[] } | null>(null);
  const [status, setStatus] = useState<"loading" | "ready" | "error">("loading");

  useEffect(() => {
    const controller = new AbortController();
    setStatus("loading");

    fetch(`/api/tracks/${trackId}/lyrics`, { signal: controller.signal })
      .then((res) => res.json())
      .then((data) => { setLyrics(data); setStatus("ready"); })
      .catch((err) => { if (err.name !== "AbortError") setStatus("error"); });

    return () => controller.abort(); // cleanup: undo the previous sync
  }, [trackId]);                      // deps: re-sync whenever the track changes

  if (status === "loading") return <p>Loading lyrics…</p>;
  if (status === "error")   return <p>Couldn't load lyrics.</p>;
  return <ul>{lyrics?.lines.map((line, i) => <li key={i}>{line}</li>)}</ul>;
}
```

### The race condition cleanup prevents
With fast changes `A → B`, request order ≠ arrival order:

1. `trackId = "A"` → fetch A starts (slow)
2. user skips → `trackId = "B"` → fetch B starts
3. B resolves first → screen shows B ✅
4. A resolves later → `setLyrics(A)` → **A's lyrics over B's track** ❌

The bug is that *the later setter wins, and arrival order is not request order.* `controller.abort()` in cleanup tears down request A when B's effect supersedes it, so A never resolves into a `setLyrics`.

### Real-world: the "now playing" track change
When a music player's `currentTrack` changes, several external systems must re-sync, each its own effect keyed on `currentTrack`:
- the tab title (`document.title = "Song — Artist"`)
- OS media-session metadata (lock-screen / media-key controls)
- a live-lyrics WebSocket subscription (cleanup unsubscribes the previous track's feed)
- the `<audio>` element's `src`

None of these are JSX you return — they're all `externalSystem = f(currentTrack)`.

## Diagrams

```
render commits DOM ──▶ run effect (setup) ──▶ … state changes …
                              │
                              ▼
                    run cleanup (undo) ──▶ run effect (setup, new values)
                              │
                              ▼  (component removed)
                    run cleanup (final sync → nothing)
```

## Common Pitfalls
- **Treating `useEffect` as a lifecycle hook.** Asking "when does this run?" leads to wrong deps. Ask "what external system am I keeping in sync, and with which values?"
- **Lying to the deps array** (writing `[]` to "run once") when the effect reads reactive values — the external system silently tracks a stale value. Trust the `exhaustive-deps` lint.
- **A boolean `cancelled` flag instead of `AbortController`.** A flag (`if (!cancelled) setState(...)`) *does* hide the stale result visually, but the network request still runs to completion — wasted bandwidth, an occupied connection (browsers cap ~6 per host), and server work nobody reads. `AbortController` makes the stale response *not happen* rather than merely ignoring it.
- **Forgetting cleanup for subscriptions/timers/listeners** → duplicated subscriptions and leaks, because each re-run stacks a new one on top of the old.
- **Calling a hook conditionally** (`if (x) useState(...)`) → breaks the call-order contract and throws.
- **Initial-value type inference traps** — `useState(null)` infers `null`; `useState([])` infers `never[]`. Supply a generic.

2. What exactly does an empty `[]` dependency array mean, versus `[trackId]`, versus omitting the array entirely?
