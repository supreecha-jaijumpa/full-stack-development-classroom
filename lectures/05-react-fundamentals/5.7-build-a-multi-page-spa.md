# 5.7 — Build a Multi-Page SPA

> Module: 05 — React Fundamentals · First taught: 2026-07-06 · Last updated: 2026-07-06

## TL;DR
A multi-page SPA is where components, props, state, hooks, and routing combine into one app. The hard part is not the wiring — it is the **architecture decisions**: how to lay out routes under a shared shell, where shared state (like a cart) should live, and how to model every async UI state. The recurring lesson is that most of these decisions are about *ownership, identity, and correctness*, not syntax — and that hand-rolling data fetching per screen reveals exactly why server-state libraries exist.

## Key Concepts

### Plan before you code: routes + a shared shell
Sketch the routes and which component renders at each *before* writing anything. A product catalog needs at least three:

- `/` → list page
- `/products/:id` → detail page (the `:id` makes each product deep-linkable)
- `/cart` → cart page

All three share a header/footer, so they mount **inside one layout route** that renders the shell once and drops an `<Outlet/>` where the URL-matched child goes (see 5.6). The shell is written once; the router swaps only the outlet content.

```tsx
<Routes>
  <Route element={<AppShell />}>          {/* renders header + <Outlet/> once */}
    <Route index element={<ProductList />} />
    <Route path="products/:id" element={<ProductDetail />} />
    <Route path="cart" element={<Cart />} />
  </Route>
</Routes>
```

### Where does shared state live? Decide by *consumer location*, not "persistence"
The central decision in this build is where the cart lives. Three common options — a `useState` lifted to a common ancestor, React Context, or a store (e.g. Zustand). The right way to choose:

- **It is NOT about persistence.** A client store is in-memory too — it survives *navigation between routes* but **not a page refresh**, unless you add a `persist` middleware that writes to `localStorage`. And a `useState` lifted to the top-level `App` (above `<Outlet/>`) *also* survives navigation, because `App` never unmounts when routes change. So "it needs to persist" does not distinguish a store from lifted state.
- **It IS about where the consumers are.** A cart is read and written from places scattered across the tree: the **navbar badge** (count), the **list page** (add buttons), the **cart page** (the line items). Lifting `useState` to `App` and drilling it down to all of those couples every component in between to the cart. A store lets each of those components subscribe **directly**, with no drilling.

### Selector subscriptions
A store lets a component subscribe to just a *slice* of state, so it re-renders only when that slice changes:

```ts
const count = useCart((s) => s.items.reduce((n, i) => n + i.quantity, 0))
```

The navbar badge using this selector re-renders when the *count* changes but not on unrelated cart edits. This is the concrete answer to Context's weakness — a Context value change re-renders **every** consumer, whereas a selector re-renders only the components whose selected slice actually changed.

### A persisted snapshot is stale data
If you persist a cart to `localStorage`, you are storing a *snapshot*. By the time the user opens the cart, server-owned fields (price, name, availability) may have changed. The robust pattern:

- Trust the persisted copy for **identity and quantity only** (`{ id, quantity }`).
- Re-fetch the products fresh and **join by id** to get current price/name, with a fallback branch for "this product no longer exists."

This way the displayed price is always server truth — the user never acts on a stale number.

### Stale-while-revalidate beats a blocking refetch
Re-fetching to avoid stale prices is the right instinct, but doing it as a **blocking** fetch (show a spinner, wait, then render) forces an avoidable delay on every visit for data you already have a snapshot of. The better shape is **stale-while-revalidate**: render immediately from the snapshot, revalidate in the background, and swap if the data changed. (This is exactly what a server-state library like TanStack Query does by default — see Module 06.)

### Four async UI states, not three
A screen that loads data has **four** states, and each shows the user something different:

| State | What happened | What the user sees |
|-------|---------------|--------------------|
| loading | request in flight | spinner / skeleton |
| error | request failed | error message + retry |
| **empty** | request succeeded, returned `[]` | friendly "no results" message |
| data | request succeeded, has items | the list |

`empty` is a *happy-path* state — a successful fetch of zero rows — and is easy to forget because it looks like "nothing." Forgetting it ships a blank screen the user reads as broken.

### Duplication across fetch sites is the signal to reach for a library
When list, detail, and cart each hand-roll the same block —

```ts
const [data, setData] = useState<T[]>([])
const [status, setStatus] = useState<'loading' | 'error' | 'ready'>('loading')
useEffect(() => {
  let active = true
  fetchThing().then(d => active && (setData(d), setStatus('ready')))
             .catch(() => active && setStatus('error'))
  return () => { active = false }
}, [])
```

— that repeated boilerplate (status union, cleanup flag, `.then/.catch`) *is* precisely what server-state libraries exist to delete: loading/error/data handling, caching, request dedup, and revalidation. Feeling this pain by hand first is the natural way to arrive at the tool.

## Examples
- **Product catalog (this build):** list → detail → cart, cart shared via a store. Reused across GitHub (`/pull/:id`), Shopee/YouTube-style catalogs — any app with a list, a deep-linkable detail, and a piece of state (cart, selection) that many screens touch.
- **The stale-price trap:** an e-commerce cart persisted to `localStorage`. If it renders the persisted price and the seller changed it to a higher one, the customer sees the old price, clicks checkout, and is charged the new one — a surprise charge and a support ticket. Re-fetching by id and joining fresh fixes it.

```
                                    └─────────────────────┘
```

Cart-as-cache data flow:

```
persisted store: [{ id, qty }]  ──┐
                                  ├─ join by id ─→ render with fresh price
fetch products (server truth) ────┘              (fallback: "unavailable")
```

## Common Pitfalls
- **Justifying a store by "persistence."** A store is in-memory and dies on refresh without a `persist` middleware; lifted `useState` survives navigation anyway. The real reason to use a store is scattered consumers, not persistence.
- **Forgetting the empty state.** Handling only loading/error/data means a successful empty result renders a blank screen that looks broken.
- **Rendering a persisted price as truth.** A persisted cart is a stale snapshot; re-join server-owned fields from a fresh fetch.
- **Blocking on a refetch for data you already have.** Prefer stale-while-revalidate over a spinner-on-every-visit.
- **Inconsistent derived numbers.** If a header count includes items a total excludes (e.g. unavailable products), the two disagree; define once what "in the cart" means and derive both from it.
- **Prop-drilling shared state through many layers.** If more than one or two intermediate components pass a value through only to hand it down, that value probably belongs in a store or context.
