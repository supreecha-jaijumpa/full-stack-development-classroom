# 5.6 — Routing (React Router)

> Module: 05 — React Fundamentals · First taught: 2026-07-01 · Last updated: 2026-07-01

## TL;DR
Client-side routing turns a single React app into a multi-page experience without full page reloads. The key idea for an architect is that **routing is a state-management decision, not "navigation"**: you choose the *URL* as the source of truth for a slice of your app's state. Because the URL is external, serializable, and addressable, everything React Router provides — browser history, dynamic params, deep-linking, shared layouts — falls out of that one choice.

## Key Concepts

### 1. Routing is choosing the URL as a source of truth
You *could* track "which page am I on" with a top-level `useState` and swap components based on it — no router needed. It renders fine. But that state lives only in memory, and that breaks four things the URL fixes for free:

- **Refresh** — `useState` resets to its initial value, so a reload sends you back to the start page. The URL survives a reload.
- **Deep link / share** — you cannot send someone a `useState`. You *can* send them a URL. The URL is the only piece of app state that is **serializable into a link**.
- **Back / forward button** — the browser's history stack operates on the URL. With `useState`, the back button leaves your app (or does nothing), because the browser never saw a navigation happen.
- **One source of truth** — with `useState` you have *two* ideas of "where am I": the address bar and your state. They drift. Putting the page in the URL makes them one thing.

The architect's one-liner: *routing isn't navigation — it's choosing the URL as your source of truth for a slice of app state. History, params, and deep-linking are consequences of that decision, not separate features.*

### 2. Setup: `BrowserRouter`, `Routes`, `Route`
```tsx
import { BrowserRouter, Routes, Route } from "react-router-dom";

<BrowserRouter>
  <Routes>
    <Route path="/" element={<Home />} />
    <Route path="/videos" element={<VideoList />} />
    <Route path="/videos/:id" element={<VideoDetail />} />
    <Route path="*" element={<NotFound />} />   {/* catch-all 404 */}
  </Routes>
</BrowserRouter>
```
`BrowserRouter` wires the app to the browser's History API (real URLs, no `#`). `Routes` picks the single best-matching `Route` for the current URL and renders its `element`. `path="*"` matches anything unmatched — the 404.

### 3. Navigation: `<Link>`, `<NavLink>`, `useNavigate`
- `<Link to="/videos">` renders an `<a>` but intercepts the click so the router swaps content **without a full page reload** (the whole point of an SPA). Never use a raw `<a href>` for in-app navigation — it triggers a full document reload and throws away app state.
- `<NavLink>` is a `<Link>` that knows whether it points at the *active* route, so you can style the current tab (`className={({ isActive }) => ...}`).
- `useNavigate()` returns a function for **programmatic** navigation — navigating after an event rather than a click, e.g. `navigate("/login")` after a failed auth check, or `navigate(-1)` for "go back."

### 4. `:id` — the deep-linking primitive
A dynamic segment lets one component serve infinitely many URLs:
```tsx
<Route path="/pull/:id" element={<PullRequest />} />

function PullRequest() {
  const { id } = useParams();   // "42" for /pull/42
  // ...fetch and render PR #42
}
```
Compare two ways to build "click an item → see its detail":

- **`useState` version:** clicking sets `selectedId`, and you render `<Detail id={selectedId} />`. The detail shows — but the URL never changed. Refresh loses it, you can't share a link to it, and the back button doesn't work.
- **`:id` version:** clicking navigates to `/pull/42`. The item's identity is now **encoded in the address**, and `useParams` reads it back on every load. Refresh reloads the same item, the URL is a shareable link straight to that item, and each item view is a real entry in history.

That is what "deep-linking primitive" means: `:id` is the smallest building block that lets you put a link to a *specific record* into the world. One component, infinite addressable items.

### 5. Nested routes and shared layouts with `<Outlet>`
When several pages share a shell — e.g. a page header and tabs that stay put while only the panel below changes — nest the routes and let a layout render the shell once:
```tsx
<Route path="/pull/:id" element={<PullLayout />}>   {/* shared shell */}
  <Route index element={<Conversation />} />        {/* /pull/42          */}
  <Route path="commits" element={<Commits />} />    {/* /pull/42/commits  */}
  <Route path="files" element={<Files />} />        {/* /pull/42/files    */}
</Route>

function PullLayout() {
  return (
    <div>
      <Header />         {/* rendered once, for every child route */}
      <Tabs />
      <Outlet />         {/* the URL-matched child mounts here */}
    </div>
  );
}
```
`<Outlet />` is a placeholder the router fills with whatever child route matches the current URL. Mental model: **`<Outlet>` is `props.children`, except the child is chosen by the URL instead of by the parent.** `index` marks the child shown at the parent's exact path.

Why this beats each page importing its own copy of the header:
- **DRY** — the header lives in one place; change it once, not in three page components (one of which you'll forget).
- **Separation of concerns / "who owns what"** — the header is the *shell's* job, not the commits page's job. The shell is deliberately ignorant of which child it's showing, so you can add a `/checks` tab tomorrow **without touching the layout at all.**

## Examples
- **GitHub pull request** (`github.com/org/repo/pull/42`): `/pull/:id` makes every PR a directly shareable, refreshable, bookmarkable address served by one component. The PR header + tab bar are the shared layout; `/pull/42/commits` and `/pull/42/files` swap only the `<Outlet>` content.
- **YouTube / Netflix watch page** (`/watch?v=abc` or `/videos/:id`): the video id in the URL is why pasting a link opens the exact video, and why refresh keeps you on it — the id is app state that lives in the address.

## Common Pitfalls
- **Using a raw `<a href>` for in-app links.** It causes a full page reload that discards all app state — the exact thing an SPA router exists to avoid. Use `<Link>`/`<NavLink>`.
- **Reaching for `useState` to track "the selected item."** It works visually but produces state that can't survive a refresh, can't be shared, and ignores the back button. If a user should be able to link to it, it belongs in the URL.
- **Forgetting the catch-all `path="*"` route.** Unmatched URLs then render nothing instead of a helpful 404.
- **Nesting routes but forgetting `<Outlet/>` in the layout.** The child routes match but never appear, because there's no placeholder telling the router where to mount them.
- **Framing the payoff of routing as a code convenience** ("components can read the id") rather than user value ("any item becomes a shareable, refreshable link"). The user-facing benefit is the reason the feature exists.
