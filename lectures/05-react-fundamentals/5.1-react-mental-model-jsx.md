# 5.1 — React Mental Model & JSX

> Module: 05 — React Fundamentals · First taught: 2026-06-28 · Last updated: 2026-06-28

## TL;DR
React is declarative: you write a pure function that returns a *description* of the UI for the current state (`UI = f(state)`), and React owns when and how the real DOM is mutated. JSX is not HTML — it compiles to `createElement(...)` calls that evaluate to plain JavaScript objects, so a React element is **data, not a DOM node**. When state changes, React re-runs the component function, diffs the new element tree against the previous one (reconciliation over the "virtual DOM"), and commits only the minimal real-DOM changes. The genuine cost of a re-render is rarely the rendering itself — it's expensive work inside render or a large subtree re-running, which is why fixes target *work* and *cascade size*, not "render speed."

## Key Concepts

### 1. The declarative contract: `UI = f(state)`
In imperative UI code you manually find and mutate DOM nodes ("get the badge, increment its text, show it if hidden"). In React you give that up. Your only job is to write a **pure function** that, given the current state, returns a description of what the UI should look like. React figures out the diff and performs the DOM writes. You trade direct control over the DOM for predictability — the UI is always a deterministic function of state.

### 2. JSX is an expression that produces data
JSX is syntax sugar. This:

```tsx
const el = <button className="play">Play</button>;
```

compiles to:

```tsx
const el = React.createElement("button", { className: "play" }, "Play");
```

which evaluates to a plain object roughly like:

```js
{ type: "button", props: { className: "play", children: "Play" } }
```

A React element is therefore just a lightweight JS object — a description, not a real DOM node. Consequences that all fall out of this one fact:
- **Single-root rule**: a function returns one value, so JSX must resolve to one element. Two stacked siblings are two separate objects with no operator joining them — invalid JS.
- **`className` / `htmlFor`**: the keys become JS object properties, and `class` / `for` are reserved words.
- **Elements are values**: you can store them in variables, pass them as props, and produce them with `array.map(...)` — because they're just objects.

### 3. Fragments
To satisfy "return one value" without adding a wrapper DOM node, use a Fragment:

```tsx
<>
  <A />
  <B />
</>
// compiles to:
React.createElement(React.Fragment, null,
  React.createElement(A),
  React.createElement(B),
);
```

The Fragment is one element (so the return rule is satisfied), but its `type` is the special `React.Fragment` symbol, which tells React: render my children directly into the parent and emit **no DOM node of my own**. It exists only in the element tree, never in the real DOM.

### 4. The render → reconcile → commit pipeline
```
state change
  → component function re-runs
  → returns a NEW element tree (cheap plain objects)
  → React diffs new tree vs previous tree   (reconciliation, in memory)
  → React commits only the minimal real-DOM mutations   (commit)
```
The "virtual DOM" is just that in-memory element tree. **Re-rendering ≠ touching the DOM.** A component can re-run many times and cause zero DOM writes if its output is unchanged.

### 5. Component element vs host element
React decides what to do with an element by looking at its `type`:
- `type` is a **string** (`"div"`, `"button"`) → **host element** → maps directly to a real DOM node.
- `type` is a **function** (your component) → **component element** → React calls the function to find out what it renders, then recurses.

The whole tree is React repeatedly resolving function-typed elements until everything bottoms out in string-typed host elements. `console.log(<MyComponent />)` shows `type: MyComponent` (a function reference); `console.log(<div />)` shows `type: "div"` (a string).

### 6. Where re-render cost actually lives
A re-render does four things; only some cost anything:
1. The function body runs again — usually cheap.
2. It returns a new element tree (object allocation) — cheap.
3. React diffs new vs old — usually cheap, scales with tree size.
4. React commits DOM changes — expensive, **but gated by the diff**: only what actually changed is written.

So "this component re-renders too much" almost never means rendering is slow. It means one of:
- **Heavy work inside render** (sorting/filtering large arrays, expensive formatting) → fix with `useMemo` to avoid re-running the work.
- **A large render cascade** — a parent re-render re-runs the whole subtree's functions; thousands of cheap functions summed become a frame drop → fix with `React.memo` / component boundaries to prune branches.
- **Unnecessary DOM commits** (e.g. new array/object identity making React think everything moved).

The most architectural fix is **moving state down** (colocation): place state close to where it's used so a change cascades over a smaller subtree. Many "too many re-renders" problems are really "state placed too high," fixed by relocation, not memoization.

## Examples

### GitHub notification bell (declarative vs imperative)
The unread badge is `count => count > 0 ? <span>{count}</span> : null`. When `count` changes `0 → 3`, the function re-runs, returns a new description, React notices the badge went from "nothing" to "a span with 3," and makes exactly that one DOM change. No code ever issues a DOM instruction.

### Spotify search box (render cascade)
Typing in the search box updates a `query` state. If that state lives too high in the tree, every track row, the sidebar, and the now-playing bar re-run their functions on every keystroke — none individually expensive, but 1,500 of them together stutter. The fix is isolating/lowering the state, not memoizing everything.

### YouTube video card (HTML → JSX + reusable ids)
Converting a static card to a typed, reusable `<VideoCard>` component surfaces a classic trap: a hardcoded `id="notify"` (with a matching `htmlFor="notify"` label) breaks the moment the component is reused — multiple cards produce duplicate ids, which is invalid HTML and mis-wires each label to the first card's checkbox. The fix is `useId()`, which gives each instance a unique, SSR-safe id meant exactly for associating elements (label↔input, `aria-describedby`).

```
     └ <div>     ("div")    ──────▶  <div>
        └ <></>  (Fragment)         (no node)
           ├ <A/>(function)──────▶  ...host nodes...
           └ <B/>(function)──────▶  ...host nodes...
```

## Common Pitfalls
- **Thinking "re-render" means "DOM update."** Re-rendering re-runs a function and allocates throwaway objects; the DOM is only touched for what actually changed in the diff.
- **Reaching for `React.memo` / `useMemo` reflexively.** They target two different costs — `useMemo` for expensive work *inside* a render, `memo` for pruning an unnecessary *cascade*. Neither makes "rendering" itself faster, and many cases are better solved by moving state down.
- **Treating JSX as HTML.** It's an expression returning one object — hence the single-root rule, `className`/`htmlFor`, and camelCase props.
- **Hardcoding singletons (like `id`) inside a reusable component.** Every instance collides. Use `useId()` for unique, SSR-safe associations; `useId` is *not* for list keys or DOM querying.
- **Confusing a Fragment with a wrapper `<div>`.** A Fragment emits no DOM node; a `<div>` pollutes the DOM and can break layout (flex/grid) and semantics.
