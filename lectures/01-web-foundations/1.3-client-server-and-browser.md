# 1.3 Client, Server & the Browser

> Completed: 2026-06-17

## Three Axes for Placement Decisions

When deciding whether logic runs on the client or server, apply these in order:

1. **Where is the data?** — the server has DB access; the client has user interaction
2. **Who do you trust?** — never the client for security or data integrity
3. **Separation of concerns** — data on the server, presentation on the client

## Placement Rules

| Logic Type | Where |
|---|---|
| Fast UX feedback, avoid wasted requests | Client |
| Data integrity (DB writes) | Server — always |
| Security / input sanitization | Server — always |
| Access control (who can see/do what) | Server — always |
| Data formatting / presentation | Client |

**Client validation ≠ server validation.** Client validation is UX (fast feedback, fewer round trips). Server validation is security — it cannot be skipped because client-side code can be bypassed entirely via Postman, curl, or modified JS.

## The Browser Runtime

Three engines working together:

```
┌──────────────────────────────────────────┐
│                 Browser                   │
│  ┌─────────────┐   ┌───────────────────┐ │
│  │  Rendering  │   │  JavaScript       │ │
│  │  Engine     │   │  Engine (V8)      │ │
│  │  (Blink)    │   │                   │ │
│  │  HTML → DOM │   │  Runs your JS     │ │
│  │  CSS → CSSOM│   │  Event loop       │ │
│  └─────────────┘   └───────────────────┘ │
│  ┌────────────────────────────────────┐   │
│  │  Web APIs (provided by browser)    │   │
│  │  fetch · setTimeout · localStorage │   │
│  │  geolocation · WebSocket · DOM API │   │
│  └────────────────────────────────────┘   │
└──────────────────────────────────────────┘
```

`fetch` is a **Web API**, not JavaScript. The browser provides it; Node.js has its own implementation. This defines the client's capability boundary.

## Static vs Dynamic Content

| Strategy | Generated | Content | Use case |
|---|---|---|---|
| SSG | Build time | Same for all users | Blog, docs, marketing |
| ISR | Build time + revalidation | Same for all, refreshable | Product listings |
| SSR | Per request (server) | Can be user-specific | SEO + user-specific/fresh data |
| CSR | Client-side after load | User-specific | Dashboards, anything behind auth |

Decision tree:

```
Does it need SEO?
├── No → CSR (fetch client-side after auth)
└── Yes → Same content for all users?
          ├── Yes, rarely changes → SSG / ISR
          └── No, or per-user → SSR
```

**TanStack Query = browser-side cache of server state.** That's the whole product in one sentence.

## The Browser Announces Itself

```js
navigator.userAgent  // → sent as User-Agent header on every request
window.location.href // → sent as Referer header when navigating
```

Server uses these for: device-specific responses (mobile vs desktop), analytics, CSRF protection, bot detection.
