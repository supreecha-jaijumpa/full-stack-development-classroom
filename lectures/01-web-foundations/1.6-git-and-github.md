## The 3-Area Mental Model

```
Working Tree  →  Staging Area  →  Commit History
  (your files)     (git add)        (git commit)
```

- **Working Tree** — files on disk as you edit them
- **Staging Area (Index)** — a draft of the next commit; lets you commit only part of your changes
- **Commit History** — immutable linked list of snapshots; each commit points to its parent

**HEAD** is a pointer to the current commit. Checkout a branch → HEAD moves. Commit → HEAD advances.

```
main:   A ← B ← C  ← HEAD

After creating a feature branch and committing:

main:   A ← B ← C
                 ↖
feature:          D ← HEAD
```

## Conventional Commits

Format: `<type>(<optional scope>): <short description>`

```
feat(auth): add login form markup
fix: prevent double-submit on checkout form
refactor: extract useCart hook from CartPage
chore: upgrade React to 18.3
```

Common types: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `perf`

**Why it matters:** commit messages are machine-readable. Tools like semantic-release, changelog generators, and GitHub Actions parse them to auto-generate release notes, version bumps, and deployment triggers. A commit message is documentation that both humans and machines consume.

**Grammar rule:** use noun form in the description (`form validation`, not `form validate`).

## Branching Strategies

### Feature Branch Workflow
One branch per story/ticket, commits per task, merge via PR.

```
main
 └── feat/login-page
      ├── commit: add form markup
      ├── commit: wire up validation
      └── commit: connect to auth API → merge PR → main
```

Good for: small teams, simple release cycles.
Problem at scale: long-lived branches diverge → painful merges, integration surprises.

---

### Gitflow
Adds `develop` + `release/*` branches. For versioned software (v1.0, v1.1...).

Almost nobody recommends Gitflow for web apps — web apps deploy continuously, not by version.

---

### Trunk-Based Development
Everyone commits to `main` (the "trunk") or via very short-lived branches (max 1–2 days).

```
main:  A ─ B ─ C ─ D ─ E ─ F  (deploys happen here)
```

**Enabler: Feature Flags** — merge incomplete features behind a flag so `main` is always deployable.

```js
if (featureFlags.newCheckout) {
  return <NewCheckout />
}
return <OldCheckout />
```

Good for: teams deploying multiple times per day (Google, Facebook, Netflix).
**Requires:** short PRs + feature flags + fast CI. Strategy and infrastructure are a package deal.

---

### Decision Framework

| Question | Strategy |
|---|---|
| Versioned releases (v1.0, v2.0)? | Gitflow |
| Continuous web deployment? | Trunk-Based |
| Small team, no CI yet? | Feature Branch |

**Default for web products: Trunk-Based Development.**

## Git + CI/CD

```
Push to feat/* branch  →  CI: lint + tests + build
Merge to main          →  CI again → auto-deploy to staging
Tag a release          →  CI deploys to production
```

**Branch Protection Rules** (GitHub) enforce the strategy at the infrastructure level:
- `main` requires a PR — no direct push
- PR requires CI to pass + at least 1 reviewer approval
- Branch must be up to date with `main` before merge

The strategy is enforced by the system, not by trust.
