# 1.1 — How the Web Works

> Module: 01 — Web Foundations & Dev Setup · First taught: 2026-06-16 · Last updated: 2026-06-16

## TL;DR

Every web request travels a chain of steps before a single pixel appears on screen: DNS turns a domain into an IP, TCP and TLS establish a secure connection, HTTP carries the request and response, and the browser's rendering engine turns bytes into a visible page. Understanding this chain explains every caching strategy, performance optimization, and architectural trade-off in modern web development.

## Key Concepts

### 1. URL Anatomy

A URL encodes all the information needed to locate and communicate with a resource:

```
https://github.com:443/facebook/react?tab=readme
  │       │         │   │              └─ query string
  │       │         │   └─ path
  │       │         └─ port (443 is default for HTTPS, omitted when default)
  │       └─ host (domain name)
  └─ scheme (protocol)
```

### 2. DNS Resolution

DNS translates a human-readable domain into a numeric IP address. The lookup follows a caching chain — stopping as soon as a match is found:

```
1. Browser DNS cache       ← checked first
2. OS DNS cache            ← includes /etc/hosts (or Windows hosts file)
3. Router / local network  ← often has its own cache from the ISP resolver
4. ISP recursive resolver  ← first internet hop
   └─ Root nameserver (.)
        └─ TLD nameserver (.com, .io, etc.)
             └─ Authoritative nameserver (github.com)
                  └─ Returns IP address
```

**TTL (Time to Live)** controls how long each layer caches the result. A high TTL (e.g. 3600s) means DNS changes take up to an hour to propagate globally — this is why users sometimes see a stale deployment after a server switch.

**CDNs and DNS:** CDNs use DNS as a routing mechanism. When you query `github.com`, the authoritative nameserver returns *different* IP addresses depending on your geographic location, directing you to the nearest CDN edge node.

### 3. TCP 3-Way Handshake

Before any data is exchanged, a reliable connection must be established:

```
Client → SYN          "I want to connect"
Server → SYN-ACK      "OK, I'm ready"
Client → ACK          "Confirmed"
```

This costs **1 round-trip** before a single byte of the request goes out. On a 100ms connection, that's 100ms of pure setup.

### 4. TLS Handshake (HTTPS)

After the TCP connection, a second handshake establishes encryption:

```
Client → ClientHello       "Here are the cipher suites I support"
Server → ServerHello       "Use this one, here's my certificate"
Client → verifies certificate against a trusted CA (certificate authority)
Both   → derive a shared session key
```

This costs an additional **1–2 round-trips**. Only after this is complete does the HTTP request go out over an encrypted channel.

**Why HTTP/2 matters:** HTTP/1.1 performed a new TCP + TLS handshake for each resource. HTTP/2 multiplexes many requests over a single connection, eliminating repeated handshakes for the 50–100 assets a typical page loads.

### 5. HTTP Request / Response

With the connection open, HTTP carries the actual application data:

**Request:**
```
GET /facebook/react HTTP/2
Host: github.com
Accept: text/html
Cookie: ...
```

**Response:**
```
HTTP/2 200 OK
Content-Type: text/html; charset=utf-8
Cache-Control: max-age=0

<!DOCTYPE html>...
```

The server reads the method, path, and headers to route the request to the correct handler, then returns a status code, response headers, and an optional body.

### 6. Critical Rendering Path

Once the browser receives HTML bytes, it builds a visible page through a pipeline:

```
HTML bytes
  └─ DOM (Document Object Model) — tree of elements
       │
       ├─ CSS encountered → fetch + parse → CSSOM
       │
       └─ DOM + CSSOM → Render Tree (visible nodes only)
                └─ Layout    — compute size and position of each element
                └─ Paint     — draw pixels (colors, borders, shadows, text)
                └─ Composite — assemble GPU layers into the final frame
```

**Blocking behavior:**
- **CSS is render-blocking:** The browser will not render anything until the CSSOM is complete. Seeing a blank page while CSS loads is this in action.
- **`<script>` is parser-blocking by default:** The HTML parser pauses while a script downloads and executes. This is why scripts go at the bottom of `<body>`, or use `defer`/`async`.

### 7. SSR vs CSR

| | CSR (Client-Side Rendering) | SSR (Server-Side Rendering) |
|--|--|--|
| What server sends | `<div id="root"></div>` + JS bundle | Fully rendered HTML |
| When content appears | After JS downloads + runs | Immediately on HTML parse |
| DevTools tell: | Response tab shows an empty shell | Response tab shows real content |
| View Source tells: | No readable content | Actual page content visible |

**How to confirm:** Right-click → View Page Source (not Inspect Element). If the content (article text, product names, repo file list) is present as text, it was server-rendered. If you see only script tags and empty containers, it's client-rendered.

## DevTools: Reading a Request's Timing

Open Chrome DevTools → Network tab → click any request → Timing tab:

| Field | What it measures |
|-------|-----------------|
| Queueing / Stalled | Browser waiting to start (connection limits, priority) |
| DNS Lookup | Time for DNS resolution |
| Initial connection | TCP handshake |
| SSL | TLS handshake |
| TTFB (Waiting) | Time to first byte — server processing time |
| Content Download | Transfer time for the response body |

If DNS/connection steps are missing, the browser reused an existing connection (HTTP/2 keep-alive). Open an Incognito tab for a cold-start view.

## Common Pitfalls

- A common mistake is confusing CDNs with DNS. DNS resolves domain names to IP addresses; CDNs use DNS to route users to geographically close servers. They work together, but are distinct layers.
- A common mistake is thinking SSR means "the server does all the work." In Next.js, SSR sends pre-rendered HTML but also ships a JS bundle that "hydrates" the page — making it interactive client-side. Both server and client do work.
- A common mistake is reading the Inspect Element (DevTools Elements tab) to check for SSR. Inspect Element shows the *live* DOM after JS has run. Always use View Page Source to see what the server actually sent.
- A common mistake is treating `<script defer>` and `<script async>` as interchangeable. `defer` preserves execution order and runs after HTML parsing; `async` runs as soon as the script loads, in no guaranteed order.
