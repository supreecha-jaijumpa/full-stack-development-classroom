# 1.5 — Command Line Basics

> Module: 01 — Web Foundations & Dev Setup · First taught: 2026-06-17 · Last updated: 2026-06-17

## TL;DR
Every process exits with a number (0–255) called an exit code — 0 means success, anything else means failure. The shell captures this in `$?` and CI/CD systems use it to pass or fail jobs. Piping (`|`) connects programs by feeding one program's stdout directly into the next program's stdin, without touching disk. Redirection (`>`, `>>`, `2>`, `2>&1`) lets you write those streams to files instead.

## Key Concepts

### Exit Codes
Every process that runs exits with a number 0–255. Zero means success; anything else means failure.

```bash
ls nonexistent-folder
echo $?    # prints 1 or 2 (non-zero = error)

ls .
echo $?    # prints 0 (success)
```

Common codes:

| Code | Meaning |
|------|---------|
| 0 | Success |
| 1 | Generic error |
| 2 | Misuse of command |
| 126 | Permission denied |
| 127 | Command not found |
| 130 | Terminated with Ctrl+C (SIGINT) |

Shell variable: `$?` in Bash/Git Bash, `$LASTEXITCODE` in PowerShell.

### How CI/CD Uses Exit Codes
GitHub Actions (and every other CI system) marks a step as failed when the command exits non-zero. It does not read output text — it reads the exit code. This is why `npm run build` failing causes a CI job to fail: the build tool calls `process.exit(1)` internally.

In Node.js you control this yourself:

```js
process.exit(0)   // tells the caller: success
process.exit(1)   // tells the caller: failure — CI marks the job as failed
```

### Exit-Code-Driven Branching: && and ||

```bash
npm run build && npm run deploy
# deploy only runs if build exits 0

npm run test || echo "Tests failed, stopping"
# echo only runs if test exits non-zero
```

These are the same `&&`/`||` as in JavaScript — but they branch on exit code, not a boolean value.

### Three I/O Streams
Every process has three streams by default:

| Stream | File Descriptor | Default |
|--------|-----------------|---------|
| stdin  | 0               | keyboard |
| stdout | 1               | terminal |
| stderr | 2               | terminal |

### Piping |
Pipe takes the stdout of one command and feeds it as stdin to the next — without writing anything to disk.

```bash
command1 | command2 | command3
```

Think of it as method chaining in JavaScript:

```js
// JavaScript
array.filter(x => x > 0).map(x => x * 2).sort()

// Shell equivalent
cat data.txt | grep "error" | sort
```

Real example — count `console.log` calls in TypeScript files:

```bash
grep -r "console.log" src/ | grep "\.ts" | wc -l
```

Each `|` passes output forward. The data streams through memory without touching disk.

### Redirection: >, >>, 2>, 2>&1

| Operator | Effect |
|----------|--------|
| `>`      | Redirect stdout to a file (overwrites) |
| `>>`     | Redirect stdout to a file (appends) |
| `2>`     | Redirect stderr to a file |
| `2>&1`   | Merge stderr into stdout |

```bash
npm run build > build.log             # capture stdout
npm run build > all.log 2>&1          # capture stdout and stderr together
npm run build 2> errors.log           # capture only errors
echo "deploy started" >> deploy.log   # append a line without overwriting
```

### Windows: Git Bash
On Windows, Unix shell commands (`grep`, `wc`, `cat`, `|`) are available in **Git Bash**, which ships with Git. Switch to it in the VS Code terminal dropdown. For heavier backend and DevOps work, WSL (Windows Subsystem for Linux) provides a full Linux environment (`wsl --install`).

## Examples

Find and count lines matching a pattern across a directory:

```bash
# Find every line with "HTTP" in modules/, filter to those also containing "1.1", count
grep -r "HTTP" modules/ | grep "1.1" | wc -l
```

Chain build and deploy, deploying only on success:

```bash
npm run build && npm run deploy
```

Capture both stdout and stderr into one CI log file:

```bash
npm run test > test.log 2>&1
```

## Common Pitfalls

- A common mistake is thinking `grep | grep` searches files a second time — the second `grep` filters the *text output* of the first, not files on disk.
- Only `0` is success. `1` is the most common error code, but any non-zero value signals failure to the caller.
- `>` silently overwrites the file — use `>>` if you want to append rather than replace.
- `2>&1` must come *after* `>` — writing it before (`2>&1 > file`) redirects stderr to the terminal before stdout is redirected, which is not what you want.
- On Windows, Unix commands (`grep`, `wc`, `|`) require Git Bash or WSL — they do not work in cmd.exe or standard PowerShell.
