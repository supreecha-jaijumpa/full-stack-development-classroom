# 1.4 — Dev Environment Setup

> Module: 01 — Web Foundations & Dev Setup · First taught: 2026-06-17 · Last updated: 2026-06-17

## TL;DR

A professional dev environment means intentional tooling — not just what a scaffold handed you. Node.js version management, a deep understanding of `package.json` fields, and a clean ESLint + Prettier separation are the three things that separate a personal setup from an architecture-grade one. The key rule: Prettier owns formatting, ESLint owns code quality — never let them overlap.

---

## Key Concepts

### Node.js: Current vs LTS

Node.js ships two tracks simultaneously:

- **Current** — latest features, odd + even major versions, ~6 months of support
- **LTS** (Long-Term Support) — even major versions (18, 20, 22…), ~3 years of security patches

For production projects and team environments, always default to the **active LTS**. Scaffolding tools and CI images target LTS. Using Current in production means shorter support windows and potential breaking changes on minor upgrades.

Check the current LTS at [nodejs.org/en/about/previous-releases](https://nodejs.org/en/about/previous-releases).

### Version Managers: fnm / nvm

Instead of installing Node globally, use a version manager so you can switch Node versions per project:

- **fnm** (Fast Node Manager) — Rust-based, cross-platform, the best choice on Windows
- **nvm** — the original, POSIX-only (works on Mac/Linux via WSL on Windows)

Both read a `.nvmrc` or `.node-version` file at the project root:

```
# .nvmrc
22
```

When everyone on the team commits this file, `fnm use` (or `nvm use`) pins the environment to the same version — no "it works on my machine" Node version drift.

### `package.json` — Fields Beyond the Basics

Most developers know `name`, `version`, `scripts`, `dependencies`, and `devDependencies`. The fields that matter at architecture level:

**`"type": "module"`**

```json
{ "type": "module" }
```

Switches the package to ESM. Without it, Node defaults to CommonJS (`require`). Set this on every modern Node/TypeScript project. Missing it causes the common error: `require is not defined in ES module scope`.

**`"engines"`**

```json
{ "engines": { "node": ">=22.0.0" } }
```

Documents the minimum required Node version. `npm` warns (not blocks by default) if the consumer's version is below this. Add `engine-strict=true` to `.npmrc` to turn warnings into hard blocks.

**`"exports"`**

```json
{
  "exports": {
    ".": "./dist/index.js",
    "./utils": "./dist/utils.js"
  }
}
```

Controls the public API surface of a package. Any file not listed in `exports` is **private** — callers cannot import it, even if the file exists on disk. This is the modern replacement for `"main"` and is how libraries like React enforce internal encapsulation.

**Scripts convention**

Every project in an org should expose the same top-level script names so pipelines and onboarding docs stay generic:

```json
{
  "scripts": {
    "dev":        "...",
    "build":      "...",
    "start":      "...",
    "test":       "...",
    "lint":       "...",
    "typecheck":  "tsc --noEmit"
  }
}
```

### ESLint + Prettier: The Separation of Concerns

The single most important rule in frontend/fullstack tooling:

> **Prettier owns formatting. ESLint owns code quality. They must never overlap.**

Prettier handles: indentation, quotes, semicolons, line length, trailing commas.  
ESLint handles: unused variables, type safety, import rules, logic bugs.

`eslint-config-prettier` enforces this boundary by disabling all ESLint rules that touch formatting. It must always be the **last entry** in the ESLint config so it wins over any prior rule that conflicts.

### Baseline Config

**`eslint.config.mjs`** (ESLint 9 flat config):

```js
import tseslint from "@typescript-eslint/eslint-plugin";
import tsParser from "@typescript-eslint/parser";
import prettier from "eslint-config-prettier";

export default [
  {
    files: ["**/*.{ts,tsx}"],
    languageOptions: { parser: tsParser },
    plugins: { "@typescript-eslint": tseslint },
    rules: {
      ...tseslint.configs.recommended.rules,
      "@typescript-eslint/no-unused-vars": ["error", { argsIgnorePattern: "^_" }],
      "@typescript-eslint/no-explicit-any": "warn",
    },
  },
  prettier, // always last
];
```

**`.prettierrc`**:

```json
{
  "semi": true,
  "singleQuote": false,
  "tabWidth": 2,
  "trailingComma": "all",
  "printWidth": 100
}
```

**`.vscode/settings.json`** (project-level, committed):

```json
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  }
}
```

### What Scaffolding Tools Give You vs What You Need

`create-next-app` generates an ESLint config tied to Next.js (`next/core-web-vitals`, `next/typescript`). This is fine for a pure Next.js app but has no Prettier integration, no backend/Node rules, and is useless on an Express API. Always replace or extend the scaffold config with the intentional baseline above.

## Common Pitfalls

- A common mistake is treating Prettier and ESLint as interchangeable — they serve different roles. Running ESLint with formatting rules enabled causes save-on-format conflicts when Prettier and ESLint disagree on style.
- A common mistake is assuming silence from `npx eslint` means something went wrong. ESLint follows Unix convention: **no output = success**. Only errors and warnings produce output.
- A common mistake is skipping `"type": "module"` on Node projects and then being confused by `require is not defined` errors when using `import` syntax.
- A common mistake is using a globally installed Node version in a team context. Without a version manager and a pinned `.nvmrc`, Node version drift causes inconsistent behavior between local and CI environments.
- A common mistake is placing `eslint-config-prettier` anywhere other than last in the config array. An earlier entry can re-enable formatting rules that prettier would otherwise own.
