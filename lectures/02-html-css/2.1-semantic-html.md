# 2.1 — Semantic HTML

> Module: 02 — HTML & CSS · First taught: 2026-06-17 · Last updated: 2026-06-17

## TL;DR
Semantic HTML is an **API contract**, not a styling concern. Your markup is consumed by three machines you don't control: the accessibility tree (screen readers), crawlers (SEO/social), and the next developer. Elements are chosen by **intent and meaning**, not appearance — and the cost of getting it wrong is invisible, paid later by someone else. Two things must always hold: every landmark has an accessible name, and the headings alone form a usable table of contents.

## Key Concepts

### Markup as a contract
HTML compiles and ships even when it's `<div>` soup. The cost shows up later and invisibly — broken screen-reader navigation, poor SEO, unmaintainable structure. Treating markup as a contract consumed by machines you don't control is the architect mindset applied to the front end.

### The document outline
`<h1>`–`<h6>` should read, on their own, as a coherent table of contents. A screen-reader user skims a page by jumping heading to heading — so a section with no heading is invisible to that navigation.

Important caveat: the old HTML5 "sectioning content resets heading levels" **outline algorithm was never implemented** by any browser or assistive tech. `<section><h1>` does **not** become an `<h2>`. You manage heading levels manually — don't skip levels (`h1` → `h2` → `h3`, never `h1` → `h3`).

### Landmarks
`header`, `nav`, `main`, `aside`, `footer` map to ARIA landmark roles. They let a screen-reader user jump around the page the way a sighted user scans — directly to "main", "the navigation", "the complementary sidebar".

Rule: when a page has **more than one of the same landmark** (two `<nav>`s, multiple `<aside>`s), each needs a distinguishing accessible name via `aria-label` or `aria-labelledby` — otherwise they're indistinguishable in the landmarks list. A landmark with no name is "a room with no doorplate."

### `<article>` — the syndication test
The test for `<article>` is **not** "is it a blog post." It's:

> Could this unit stand alone or be syndicated independently?

A user comment passes: it has its own author, timestamp, and meaning out of context (e.g. quoted in a "your comment got a reply" email). So comments are `<article>`s. And `<article>` **nests** — a post is an `<article>`, and each comment on it is a smaller `<article>` inside the comments section. Same pattern in YouTube, Facebook, any feed.

### `<nav>` vs `<aside>` — intent over appearance
Both can render as "a list of links," but they encode different intent:
- `<nav>` = navigating **the site's own structure** (Home, Topics, About; a sidebar of app sections like Home/Shorts/Subscriptions/Library).
- `<aside>` = **related/complementary content** (recommended videos, "related posts"). Algorithmic suggestions about the current page are related content, not site navigation.

Semantics encode intent, not visual pattern. Two identical-looking link lists can be different elements.

### `alt` text decisions
- Image is the link's **only** content → `alt` describes the destination: `alt="YouTube home"`.
- Link **already** has a text/aria label → image is redundant → `alt=""` (decorative; removed from the accessibility tree so the name isn't announced twice).
- `alt=""` (empty but present) ≠ missing `alt`. **Missing** `alt` makes a screen reader read the **filename** (`logo.png`) — the worst outcome. Empty-but-present is a deliberate "skip me."

### Text-level semantics
- `<time datetime="2026-06-17T14:30:00+07:00">` — machine-readable timestamp; **include the timezone offset**.
- `<address>` — contact/authorship info for the nearest `article` or the document.
- `<figure>` + `<figcaption>` — an image (or code, chart) with a caption.
- `<figure>` + `<blockquote>` + `<figcaption>`/`<cite>` — a quotation with attribution. Note: per spec `<cite>` marks the **title of a work**, not a person's name — but the `figcaption`-with-`cite` attribution convention is near-universal in practice. Either way, a pull-quote needs a visible source.
- An `<a>` with **no `href`** is not a link and is not focusable — it's just text to assistive tech. Real links need an `href`.

## Examples

### YouTube watch page skeleton
The primary content (video + its metadata + comments) is one `<article>`. The comments section is a `<section>` with an `<h2>` heading, and **each comment is a nested `<article>`**. "Up next" recommendations are an `<aside>` (complementary), *not* a `<nav>` — they're suggestions about this video, not site navigation. The top bar (logo + search + profile) is page chrome inside `<header>`, and doesn't need to be a `<nav>` if it holds no menu of site sections.

```html
<main>
  <article>
    <video src="..."></video>           <!-- not void: needs a closing tag -->
    <h1>Video title</h1>
    <p>Channel · <button>Subscribe</button></p>
    <section aria-labelledby="comments-h">
      <h2 id="comments-h">328 Comments</h2>
      <article>comment 1</article>       <!-- nested article -->
      <article>comment 2</article>
    </section>
  </article>

  <aside aria-labelledby="upnext-h">
    <h2 id="upnext-h">Up next</h2>
    <ul><li><a href="...">rec 1</a></li></ul>
  </aside>
</main>
```

### Blog post page
`<header>` (logo + primary `<nav>`) and `<main>` are **siblings** — `<main>` is never a child of `<header>`. The post is an `<article>` with author `<address>`, a `<time>`, body `<section>`s, a `<figure>` pull-quote with attribution, a captioned `<figure>` image, and a nested-`<article>` comments section. A "Related posts" `<aside>` sits beside the article. A `<footer>` with copyright + a second (social) `<nav>` closes the page — and because there are now two `<nav>`s, both get `aria-label`s (`"Primary"`, `"Social"`).

## Common Pitfalls
- A common mistake is thinking `<section><h1>` auto-demotes to `<h2>` — the outline algorithm was never implemented; manage heading levels by hand.
- A common mistake is treating `<article>` as "blog-post only" and refusing it for comments — comments are the spec's textbook example of `<article>`.
- A common mistake is nesting `<main>` **inside** `<header>` by forgetting to close `</header>` — `<main>` must be a sibling.
- A common mistake is using multiple `<nav>`/`<aside>` landmarks without `aria-label`s, leaving them indistinguishable to screen-reader users.
- A common mistake is choosing `<nav>` vs `<aside>` by how it looks (a list of links) instead of by intent (site navigation vs related content).
- A common mistake is omitting `alt` entirely (filename gets read aloud) when the intent was decorative — use `alt=""`.
- A common mistake is dropping the timezone offset in a `<time datetime>` value.
- A common mistake is writing `<a>` without an `href` — it isn't a link and isn't focusable.
