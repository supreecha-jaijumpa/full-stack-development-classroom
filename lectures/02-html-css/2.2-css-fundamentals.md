# 2.2 — CSS Fundamentals

> Module: 02 — HTML & CSS · First taught: 2026-06-17 · Last updated: 2026-06-17

## TL;DR
CSS decides which declaration wins through a fixed **4-step resolution algorithm**: origin & importance → cascade layer → specificity → order of appearance. Each step only runs if the previous one didn't already pick a winner. The two things that trip up even senior developers are the **inversions**: `!important` reverses both the origin order and the `@layer` order. The senior mindset is that **specificity is the third question you ask, not the first** — a weak selector can beat a strong one purely on importance or layer.

> This file currently covers the **cascade** half of the topic. Specificity-as-a-tuple, stacking contexts, units, and custom-property architecture will be merged in as those are taught.

## Key Concepts

### The cascade is a 4-step pipeline
When two or more declarations set the same property on the same element, the browser resolves the winner in this exact order. It stops as soon as a step produces a single winner.

1. **Origin & importance** — who authored the rule, and whether it's `!important`
2. **Cascade layer** — which `@layer` the rule lives in (and unlayered vs layered)
3. **Specificity** — the `(id, class, type)` tuple of the selector
4. **Order of appearance** — among everything still tied, the **last** declared wins

The common folk-model — *"specificity, then last one wins"* — is only steps 3 and 4. The interesting decisions usually happen in steps 1 and 2.

### Origin order (step 1) and its `!important` inversion
There are three origins. For **normal** declarations the priority is:

```
user-agent  <  user  <  author          → author normally wins
```

For **`!important`** declarations the order **inverts**:

```
author-!important  <  user-!important  <  user-agent-!important   → UA/user wins
```

This is intentional: it guarantees a user's accessibility stylesheet (e.g. forcing a larger font) can override an author's `!important`, so a developer can never fully defeat a user who needs it.

### Cascade layers (step 2) and their `!important` inversion
`@layer` lets you declare named buckets in a chosen priority order:

```css
@layer reset, framework, overrides;   /* later layer = higher priority for normal rules */
```

For **normal** declarations:
- **Unlayered** styles beat **every** named layer.
- Among named layers, the **later-declared** layer wins.

```
NORMAL:    unlayered  >  later layer  >  earlier layer
```

For **`!important`** declarations the whole stack flips:

```
IMPORTANT: earlier layer  >  later layer  >  unlayered
```

So an `!important` rule in the *earliest* layer outranks an `!important` rule that's unlayered — the reverse of the normal case.

### The one unifying rule
Both inversions are the **same** rule applied at two levels: `!important` reverses priority order. Origins flip, layers flip. It's not three special cases to memorize — it's one consistent flip wherever importance is involved.

### Why this matters: the design intent of `@layer`
Before cascade layers, the only way to win a conflict was to escalate specificity (`#header .btn.primary.primary`) or start an `!important` war. Layers solve this **structurally**: put a design system (Primer, Tailwind base, a reset) into low-priority layers, keep your app's own overrides unlayered, and your overrides win automatically — even with simple, low-specificity selectors. The `!important` + layer inversion deliberately protects the *foundational* layer so an app override can't `!important` its way past it and reignite the arms race layers were built to end.

## Examples

### Which color wins? (normal declarations)
```html
<style>
  @layer base, theme;
  @layer theme { p { color: green; } }
  @layer base  { #intro.note { color: red; } }   /* specificity 1-1-0 */
  p { color: blue; }                              /* unlayered */
</style>
<p id="intro" class="note">What color am I?</p>
```
**Answer: blue.** Resolved at the *layer* step — unlayered beats both layers — before specificity is ever consulted. The `1-1-0` selector loses to a bare `p` because it's trapped in a lower layer.

### Same markup, all `!important`
Make the unlayered rule `blue !important` and the `base` rule `red !important`. Now **red wins**, because for `!important` the earliest layer (`base`) ranks highest and the unlayered champion drops to the bottom.

### A real design-system scenario (GitHub / Primer style)
A team ships a design system in a `framework` layer and writes feature overrides unlayered. A weak `.btn { color: blue }` override beats the framework's `#header .btn.primary` — no specificity hacks needed. This is the intended way to manage a design-system-vs-overrides battle across hundreds of imported files.

## Diagrams

The cascade pipeline (stops at first decisive step):

```
┌─────────────────────────────────────────────┐
│ 1. Origin & importance                       │  ← !important inverts origin order
├─────────────────────────────────────────────┤
│ 2. Cascade layer (@layer / unlayered)        │  ← !important inverts layer order
├─────────────────────────────────────────────┤
│ 3. Specificity  (id, class, type)            │  ← only compares WITHIN the same layer
├─────────────────────────────────────────────┤
│ 4. Order of appearance (last wins)           │
└─────────────────────────────────────────────┘
```

Priority buckets, normal vs important:

| | unlayered | later layer | earlier layer |
|---|---|---|---|
| **normal**       | 🥇 highest | middle | lowest |
| **`!important`** | 🥉 lowest  | middle | 🥇 highest |

## Common Pitfalls
- **Reaching for specificity first.** A common mistake is computing the `(id, class, type)` tuple before checking importance and layer. Specificity is step 3 — it only breaks ties *within the same layer and importance*. A higher-specificity selector regularly loses to a weaker one in a higher-priority layer.
- **Assuming the strongest selector wins.** With `!important` or layers in play, the selector with the most ids/classes is frequently *not* the winner.
- **Thinking unlayered styles are "just normal."** Unlayered normal declarations are actually the *highest*-priority normal bucket — above every named layer.
- **Forgetting the `!important` inversion.** People remember `!important` "wins" but forget it reverses the *order among* important declarations (origins and layers both flip).
- **Confusing "first" and "last."** Order of appearance picks the *last* declared on a tie — and it's the final fallback, rarely the actual decider.
