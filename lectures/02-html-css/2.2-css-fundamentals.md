# 2.2 — CSS Fundamentals

> Module: 02 — HTML & CSS · First taught: 2026-06-17 · Last updated: 2026-06-18

## TL;DR
CSS decides which declaration wins through a fixed **4-step resolution algorithm**: origin & importance → cascade layer → specificity → order of appearance. Each step only runs if the previous one didn't already pick a winner. The two things that trip up even senior developers are the **inversions**: `!important` reverses both the origin order and the `@layer` order. The senior mindset is that **specificity is the third question you ask, not the first** — a weak selector can beat a strong one purely on importance or layer. Specificity itself is an `(A, B, C)` tuple compared left-to-right, and modern pseudo-classes (`:is()`, `:where()`) change the calculation in ways most devs haven't thought through. Stacking contexts mean z-index is local, not global. Custom properties have a three-level architecture: global tokens → component API → context overrides.

## Key Concepts

### The cascade is a 4-step pipeline
When two or more declarations set the same property on the same element, the browser resolves the winner in this exact order. It stops as soon as a step produces a single winner.

1. **Origin & importance** — who authored the rule, and whether it's `!important`
2. **Cascade layer** — which `@layer` the rule lives in (and unlayered vs layered)
3. **Specificity** — the `(id, class, type)` tuple of the selector
4. **Order of appearance** — among everything still tied, the **last** declared wins

The common folk-model — *"specificity, then last one wins"* — is only steps 3 and 4. The interesting decisions usually happen in steps 1 and 2.

### Origin order (step 1) and its `!important` inversion
There are three origins. For **normal** declarations the priority is:

```
user-agent  <  user  <  author          → author normally wins
```

For **`!important`** declarations the order **inverts**:

```
author-!important  <  user-!important  <  user-agent-!important   → UA/user wins
```

This is intentional: it guarantees a user's accessibility stylesheet (e.g. forcing a larger font) can override an author's `!important`, so a developer can never fully defeat a user who needs it.

### Cascade layers (step 2) and their `!important` inversion
`@layer` lets you declare named buckets in a chosen priority order:

```css
@layer reset, framework, overrides;   /* later layer = higher priority for normal rules */
```

For **normal** declarations:
- **Unlayered** styles beat **every** named layer.
- Among named layers, the **later-declared** layer wins.

```
NORMAL:    unlayered  >  later layer  >  earlier layer
```

For **`!important`** declarations the whole stack flips:

```
IMPORTANT: earlier layer  >  later layer  >  unlayered
```

So an `!important` rule in the *earliest* layer outranks an `!important` rule that's unlayered — the reverse of the normal case.

### The one unifying rule
Both inversions are the **same** rule applied at two levels: `!important` reverses priority order. Origins flip, layers flip. It's not three special cases to memorize — it's one consistent flip wherever importance is involved.

### Why this matters: the design intent of `@layer`
Before cascade layers, the only way to win a conflict was to escalate specificity (`#header .btn.primary.primary`) or start an `!important` war. Layers solve this **structurally**: put a design system (Primer, Tailwind base, a reset) into low-priority layers, keep your app's own overrides unlayered, and your overrides win automatically — even with simple, low-specificity selectors. The `!important` + layer inversion deliberately protects the *foundational* layer so an app override can't `!important` its way past it and reignite the arms race layers were built to end.

## Examples

### Which color wins? (normal declarations)
```html
<style>
  @layer base, theme;
  @layer theme { p { color: green; } }
  @layer base  { #intro.note { color: red; } }   /* specificity 1-1-0 */
  p { color: blue; }                              /* unlayered */
</style>
<p id="intro" class="note">What color am I?</p>
```
**Answer: blue.** Resolved at the *layer* step — unlayered beats both layers — before specificity is ever consulted. The `1-1-0` selector loses to a bare `p` because it's trapped in a lower layer.

### Same markup, all `!important`
Make the unlayered rule `blue !important` and the `base` rule `red !important`. Now **red wins**, because for `!important` the earliest layer (`base`) ranks highest and the unlayered champion drops to the bottom.

### A real design-system scenario (GitHub / Primer style)
A team ships a design system in a `framework` layer and writes feature overrides unlayered. A weak `.btn { color: blue }` override beats the framework's `#header .btn.primary` — no specificity hacks needed. This is the intended way to manage a design-system-vs-overrides battle across hundreds of imported files.

|---|---|---|---|
| **normal**       | 🥇 highest | middle | lowest |

## Specificity: the `(A, B, C)` tuple

Every selector gets three counters. Compare **left to right** — first column that differs decides the winner.

| Counter | What increments it |
|---|---|
| **A** — ID | `#id` |
| **B** — Class | `.class`, `[attr]`, `:pseudo-class` |
| **C** — Type | `div`, `p`, `::pseudo-element` |

`#main` beats `.card.card.card.card` — you can never stack enough class points to beat a single ID. The tuple comparison is not arithmetic: `(0,10,0)` loses to `(1,0,0)`.

### `:is()`, `:not()`, `:has()` — take the max argument

These pseudo-classes take the specificity of their **most specific argument**, not a sum:

```css
:is(#main, p) { }    /* (1, 0, 0) — #main is in the list */
:not(span)    { }    /* (0, 0, 1) — span is a type */
p:has(#anchor){ }    /* (1, 0, 1) */
```

Even if `p` is what matches, `:is(#main, p)` carries `(1,0,0)`. This is intentional — `:is(h1,h2,h3,h4)` shouldn't cost more than any one of those selectors.

### `:where()` — always zero specificity

```css
:where(#main, .card, p) { }   /* (0, 0, 0) always */
```

Use `:where()` in resets and base layers so any single class can override without a specificity fight.

## Stacking contexts: z-index is local, not global

The wrong mental model: *z-index is a global number — higher = in front of everything.*

The correct model: **z-index is local to a stacking context.** You can only compare z-index values between siblings in the **same** context. A child can never visually escape its parent context regardless of its z-index value.

Think Photoshop layer groups — a layer inside Group A can never appear above Group B if Group A is painted below Group B.

### What creates a stacking context

| Trigger | Notes |
|---|---|
| `position` (not `static`) + `z-index` not `auto` | The original |
| `opacity < 1` | Compositing requirement |
| `transform` (any non-`none`) | GPU layer promotion |
| `filter`, `backdrop-filter` | Compositing |
| `will-change: transform/opacity/filter` | Pre-promotes |
| `isolation: isolate` | Explicit, clean, no side effects |
| `position: fixed` or `sticky` | Always, no z-index needed |

**Common accidental trigger:** adding `transform: translateZ(0)` or a CSS animation to fix a repaint issue silently creates a stacking context and can trap descendant z-index values.

### `isolation: isolate` — the clean trigger

```css
.modal-root {
  isolation: isolate;   /* creates context, zero side effects */
  z-index: 200;
}
```

Prefer this over relying on `transform`/`opacity` side effects when you need a deliberate stacking context.

### Diagnosing z-index bugs

1. Chrome DevTools → Layers panel: each stacking context shows as a separate layer
2. Walk up the DOM from the buried element — find the first ancestor that triggers a context
3. Find the competing ancestor context root — compare their z-index values. That's the fight that matters.

## Custom properties: three-level architecture

### Level 1 — global tokens (`:root`)

```css
:root {
  --color-primary: #6c63ff;
  --spacing: 8px;
}
```

### Level 2 — component API (vars set on the component root with fallbacks to tokens)

Custom properties inherit down the DOM. A component exposes "slots" a consumer can fill:

```css
.btn {
  background: var(--btn-bg, var(--color-primary));   /* fallback to global token */
  padding: var(--btn-padding, 0.5rem 1rem);
}
```

### Level 3 — context overrides (consumer fills the slots from a parent)

```css
.danger-zone {
  --btn-bg: #ef4444;   /* all .btn inside danger-zone become red */
}
```

**Key rule:** on hover or state changes, mutate the variable — don't bypass it:

```css
/* Wrong — bypasses the API; consumer overrides of --card-shadow break hover */
.card:hover { box-shadow: 0 12px 32px rgba(0,0,0,0.18); }

/* Correct — property always reads from the var; API contract holds */
.card:hover { --card-shadow: 0 12px 32px rgba(0,0,0,0.18); }
```

### `@property` — typed, non-inheriting, animatable

```css
@property --gradient-angle {
  syntax: '<angle>';
  inherits: false;
  initial-value: 0deg;
}
```

Three things `@property` adds: **type validation** (browser rejects bad values), **`inherits: false`** (true encapsulation — value doesn't leak to children), and **animatability** (can use `transition`/`@keyframes` on the var — impossible without `@property`).

## Common Pitfalls
- **Reaching for specificity first.** A common mistake is computing the `(id, class, type)` tuple before checking importance and layer. Specificity is step 3 — it only breaks ties *within the same layer and importance*. A higher-specificity selector regularly loses to a weaker one in a higher-priority layer.
- **Assuming the strongest selector wins.** With `!important` or layers in play, the selector with the most ids/classes is frequently *not* the winner.
- **Thinking unlayered styles are "just normal."** Unlayered normal declarations are actually the *highest*-priority normal bucket — above every named layer.
- **Forgetting the `!important` inversion.** People remember `!important` "wins" but forget it reverses the *order among* important declarations (origins and layers both flip).
- **Confusing "first" and "last."** Order of appearance picks the *last* declared on a tie — and it's the final fallback, rarely the actual decider.
