# 4.4 — npm & Package Management

> Module: 04 — Modern JavaScript & TypeScript · First taught: 2026-06-26 · Last updated: 2026-06-26

## TL;DR
npm is the package manager for Node.js and JavaScript projects. It resolves third-party libraries from a registry, records exact versions in a lockfile, and runs project scripts. Understanding semver ranges, the lockfile contract, and when to use `npm ci` vs `npm install` separates engineers who can diagnose dependency issues from those who re-run `npm install` and hope.

## Key Concepts

### `package.json` Anatomy
The project manifest — records metadata, dependencies, devDependencies, and scripts.

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "dependencies": {
    "react": "^18.2.0",
    "dayjs": "^1.11.0"
  },
  "devDependencies": {
    "prettier": "^3.0.0",
    "typescript": "^5.0.0"
  },
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "lint": "eslint src",
    "format": "prettier --write ."
  }
}
```

**`dependencies`** — packages your app needs at runtime or that a Node.js server needs in production.
**`devDependencies`** — packages used only during development: type definitions, linters, formatters, test runners.

> In a **Vite/React SPA**, this distinction has no effect on the bundle — Vite bundles everything it imports regardless of which field it's in. The distinction matters for **Node.js servers** (only `dependencies` get installed in production) and for **npm libraries** (only `dependencies` are installed when others use your package). For SPAs it's a documentation convention.

### Semantic Versioning (semver)
Three-number version: `MAJOR.MINOR.PATCH`
- **PATCH** — bug fix, backward compatible
- **MINOR** — new feature, backward compatible
- **MAJOR** — breaking change

npm version range operators:
```
^18.2.0  →  >=18.2.0 <19.0.0   (minor + patch updates, never a new major)
~18.2.0  →  >=18.2.0 <18.3.0   (patch updates only)
18.2.0   →  exactly 18.2.0, nothing else
```

`^` is the default when you run `npm install`. It allows compatible updates per the semver contract. Breaking changes should only appear in major bumps — but some packages don't honor this, which is why auditing updates carefully matters.

### `package-lock.json` — The Reproducibility Contract
The lockfile records the exact resolved version of every package in the dependency tree (including sub-dependencies). Without it, running `npm install` at different times can produce different trees.

**In apps: always commit the lockfile.** It guarantees every developer and every CI run gets the exact same tree.

**In published npm libraries: don't commit it.** Consumers resolve their own compatible tree alongside their other dependencies.

The common "don't commit the lockfile" advice is a misconception. Merge conflicts on `package-lock.json` are the cost of working with npm — resolve them by fixing `package.json` and re-running `npm install` to regenerate the lockfile, then commit both.

### `npm install` vs `npm ci`
```bash
npm install   # reads package.json, resolves + installs, may update lockfile
npm ci        # reads lockfile ONLY — fails if lockfile is missing or out of sync
```

**Use `npm ci` in CI/CD pipelines.** It is faster (skips resolution), deterministic, and will catch the common mistake of updating `package.json` without committing the updated lockfile.

```yaml
# GitHub Actions example
- name: Install dependencies
  run: npm ci    # not npm install
```

### `npx` — Run Without Installing
Runs a package binary without adding it to `node_modules`:
```bash
npx create-vite@latest my-app
npx prettier --write .
```
This replaces the old pattern of global installs (`npm install -g`) for project scaffolding tools.

### `npm audit` — Vulnerability Scanning
```bash
npm audit              # list known vulnerabilities in the dependency tree
npm audit fix          # auto-fix safe upgrades (patch/minor only)
npm audit fix --force  # upgrade majors too — review carefully, may introduce breaking changes
```
Production teams run `npm audit` in CI so a vulnerable dependency fails the build before it ships.

### What to Commit
```
my-project/
├── node_modules/       ← NEVER commit — reproducible from lockfile via npm ci
├── index.js            ← commit
├── package.json        ← commit
└── package-lock.json   ← commit (in apps — not in libraries)
```

`node_modules/` goes in `.gitignore`. It is fully reproducible from `package-lock.json` via `npm ci` and contains thousands of files that don't belong in version control.

## Examples

### Initializing a project from scratch
```bash
mkdir my-app && cd my-app
npm init -y                        # creates package.json with defaults
npm install dayjs                  # adds to dependencies
npm install --save-dev prettier    # adds to devDependencies
```

### Running scripts
```json
"scripts": {
  "dev": "node index.js",
  "format": "prettier --write .",
  "check-format": "prettier --check ."
}
```
```bash
npm run dev
npm run format
```

### Diagnosing a lockfile issue
```bash
# Symptom: npm ci fails in CI but npm install works locally
# Root cause: someone updated package.json without committing the regenerated lockfile
# Fix:
npm install          # regenerates lockfile
git add package-lock.json
git commit -m "chore: regenerate lockfile after dependency update"
```

## Common Pitfalls

A common mistake is adding `package-lock.json` to `.gitignore`. This means every `npm install` can silently produce a different dependency tree — the "works on my machine" problem for dependencies.

A common mistake is using `npm install` in CI pipelines. `npm ci` is faster and deterministic; it will fail loudly if the lockfile is out of sync rather than silently updating it.

A common mistake is treating `^` as "always installs the absolute latest version." `^` respects the major boundary — `^18.2.0` will never install `19.0.0`. Minor and patch updates are allowed; major upgrades require a manual change to `package.json`.

A common mistake is running `npm audit fix --force` without reviewing what changed. This can upgrade major versions with breaking changes that the safe `npm audit fix` deliberately avoids.

## Quick Recall

1. What is the difference between `dependencies` and `devDependencies` in a published npm library vs a Vite SPA?
2. `package.json` has `"axios": "^1.4.0"`. A new version `1.6.0` is released. Will `npm install` upgrade to it? What about `2.0.0`?
3. Why should `package-lock.json` be committed in an app project, and what do you do if it causes a merge conflict?
4. When would you use `npm ci` instead of `npm install`?
5. What files would you add to `.gitignore` in an npm project, and why?

<details>
<summary>Answers</summary>

1. In a library, `dependencies` are installed when others `npm install` your package; `devDependencies` are not. In a Vite SPA, both fields are bundled regardless — Vite includes everything it imports at build time, so the distinction is documentation convention only.
2. Yes, `npm install` will upgrade to `1.6.0` (within the `^1.x.x` range). It will NOT install `2.0.0` — that crosses the major boundary.
3. The lockfile guarantees reproducible installs across developers and CI runs. On merge conflict: resolve `package.json`, run `npm install` to regenerate the lockfile, then commit both files.
4. In CI/CD pipelines — `npm ci` reads the lockfile only, is faster, and fails loudly if the lockfile is out of sync.
5. `node_modules/` — it's fully reproducible from the lockfile via `npm ci` and contains thousands of generated files that don't belong in version control.
