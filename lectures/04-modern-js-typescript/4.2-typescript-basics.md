## Key Concepts

### What `strict: true` actually turns on
A shorthand for 8 individual compiler flags. The 3 that matter most:

| Flag | What it catches |
|------|----------------|
| `strictNullChecks` | Prevents `null`/`undefined` from being silently assigned to any type — forces explicit handling |
| `noImplicitAny` | Prevents TypeScript from silently inferring `any` when it can't determine the type |
| `strictFunctionTypes` | Enforces contravariant checking of function parameter types |

**Common confusion:** React's `<StrictMode>` (causes double renders/API calls in dev) is completely unrelated to TypeScript's `"strict": true` in tsconfig.

### `interface` vs `type` — the rule
| Use `type` when... | Use `interface` when... |
|---|---|
| Union, intersection, or primitive alias | Pure object shape |
| Composing types together | Expected to be extended or merged |

```ts
type Status = "active" | "inactive" | "banned"; // must be type — union
type ID = string | number;                       // must be type — union

interface User {                                 // interface — object shape
  id: number;
  name: string;
  role: string;
}
```

`interface` supports **declaration merging** — useful for extending global types (e.g. `Window`, `Express.Request`) in library code.

### Key `tsconfig.json` fields

```jsonc
{
  "compilerOptions": {
    "target": "ES2020",        // JS version to compile down to
    "module": "NodeNext",      // Import/export format (NodeNext = ESM with .js extensions required)
    "outDir": "./dist",        // Where compiled .js files go
    "rootDir": "./src",        // Where .ts source files live
    "strict": true,            // The 8-flag package
    "esModuleInterop": true    // Enables default-import syntax for CommonJS modules
  }
}
```

**`module: "NodeNext"` gotcha:** imports must include `.js` extension even when importing `.ts` files.
```ts
import { getUser } from "./users.js"; // ← required under NodeNext
```

### Type narrowing
`find()` returns `T | undefined` under `strictNullChecks`. The fix is a narrowing guard — not `!` or `as`:

```ts
export function getUser(id: number): User | undefined {
  return users.find((u) => u.id === id);
}

// Caller — type narrows inside the if block
const user = getUser(99); // type: User | undefined
if (user) {
  formatGreeting(user);   // type: User ← TypeScript proves it's safe here
}
```

**Why not `!`?** It lies to the compiler — you're asserting it's non-null without proof. If wrong, you get the same runtime crash as untyped JS. The `if` guard actually *proves* safety at that code point.
