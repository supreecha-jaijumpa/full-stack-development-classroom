# 4.5 — Bundlers & Tooling (Vite)

> Module 04 — Modern JavaScript & TypeScript · Last updated: 2026-06-26

---

## Why browsers need bundling

Modern apps are split across hundreds of files. Shipping them unbundled in production means hundreds of HTTP requests before the page loads — terrible performance. Bundlers solve this by combining files into a small number of optimized chunks.

Bundlers also handle:
- **Transpilation** — converting TypeScript/JSX to plain JavaScript the browser can run
- **Asset handling** — images, CSS, fonts processed and fingerprinted
- **Tree-shaking** — dead code removed at build time (named imports only)
- **Minification** — whitespace + variable renaming removed for smaller file size

---

## Webpack vs Vite: the core difference

### Webpack dev server (old way)
```
You save a file
  → Webpack reads ALL your files
  → Bundles everything into bundle.js
  → Serves bundle.js to the browser
  → Browser reloads
```
On large apps this cold start can take 30+ seconds. Every save re-bundles the graph.

### Vite dev server (new way)
```
You save a file
  → Browser asks: "give me App.tsx"
  → Vite transforms just that file, sends it
  → Browser asks for its imports → Vite sends those
  → ...
```

**Vite never bundles in dev.** The browser handles the module graph using native ES modules (supported in all modern browsers since ~2018). Vite is a smart file server that transforms files on demand.

This gives Vite two speed advantages:
1. **Cold start** — nothing to bundle, server is ready instantly
2. **HMR** — on save, only the changed module and its direct dependents are invalidated; the browser swaps one module in memory without a full reload

## Why still bundle for production?

Native ESM in production means the browser would make hundreds of network requests on first load — terrible for real-world performance.

`vite build` uses **Rollup** under the hood to:
- Combine files into optimized chunks
- Tree-shake unused exports
- Minify and compress
- Generate **content-hashed filenames** (`index-B3kA9xQp.js`) for automatic cache busting

| | Dev | Production |
|---|---|---|
| Bundling | None — native ESM per file | Rollup bundles into chunks |
| Speed | Instant cold start, fast HMR | Optimized output size |
| File names | Original names | Hashed (e.g. `index-B3kA9xQp.js`) |
| Env vars | Loaded at startup | Baked into the bundle |

**Content hashing** — the hash in the filename is derived from the file's content. Same content = same hash = browser uses its cache. Changed content = new hash = browser downloads the new version. Automatic cache busting with zero config.

## Scaffolding a project

```bash
npm create vite@latest my-app -- --template react-ts
cd my-app
npm install
npm run dev
```

Default scripts:
- `npm run dev` — starts the dev server (native ESM, HMR, instant cold start)
- `npm run build` — produces an optimized production build in `dist/`
- `npm run preview` — serves the `dist/` folder locally to verify the production build

## `vite.config.ts`

The main config file. Common fields:

```ts
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import { fileURLToPath, URL } from 'node:url'

export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: {
      '@': fileURLToPath(new URL('./src', import.meta.url)),
    },
  },
})
```

**Why `fileURLToPath` + `import.meta.url` instead of `path` + `__dirname`?**

Vite 5+ runs config files as native ESM. `__dirname` is a CommonJS global and doesn't exist in ESM. `import.meta.url` is the ESM equivalent of `__filename`. Using `node:path` and `__dirname` in an ESM context will throw `ReferenceError: __dirname is not defined`.

**Also update `tsconfig.app.json`** (not `tsconfig.json`) to tell TypeScript about the alias:

```json
{
  "compilerOptions": {
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}
```

Without this, TypeScript won't resolve `@/` imports even though Vite does at runtime.

## Path aliases: `@/`

The `@/` alias maps to `src/`. Lets you write:

```ts
import Button from '@/components/Button'   // ✅
import Button from '../../../components/Button'  // ❌ fragile
```

Standard convention across Next.js, Vite, and most React projects. Immune to folder restructuring.

## Environment variables

Vite exposes env vars via `import.meta.env`. Only vars prefixed with `VITE_` are shipped to the browser — all others are stripped.

```
# .env
VITE_APP_TITLE=My App
DATABASE_URL=secret     ← never exposed to the browser
```

```ts
// in any component or module
const title = import.meta.env.VITE_APP_TITLE  // "My App"
```

**Important:** env files are read at dev server startup. If you change a `.env` file, restart the server.

Available env files (loaded in priority order):
- `.env` — always loaded
- `.env.local` — local overrides, gitignored
- `.env.production` / `.env.development` — mode-specific
- `.env.production.local` — mode-specific local overrides

## Production build output

`dist/` after `vite build`:
```
dist/
  index.html
  assets/
    index-[hash].js     ← bundled JS (Rollup output)
    index-[hash].css    ← extracted CSS
    logo-[hash].svg     ← hashed asset
```

All asset filenames include a content hash. The HTML file references them by their hashed names — no manual cache invalidation needed.
