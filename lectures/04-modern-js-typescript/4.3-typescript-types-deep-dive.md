## Key Concepts

### Generics
A generic is a type variable — a placeholder `T` the caller fills in at the call site.

```ts
function first<T>(arr: T[]): T | undefined {
  return arr[0]
}
// T inferred from the argument — no need to annotate explicitly
```

**Why it matters:** Write one function that works for any type, with full type safety for each use.

---

### `Result<T>` — generic discriminated union
Models success/failure explicitly instead of throwing or returning `null`.

```ts
type Result<T> =
  | { ok: true;  data: T }
  | { ok: false; error: string }
```

Narrowing with the discriminant:
```ts
if (result.ok) {
  // TS knows: result.data is T
} else {
  // TS knows: result.error is string
}
```

Accessing `result.data` without the check → TS error: property doesn't exist on both branches.

---

### Discriminated Unions — object shapes, not string unions

**Wrong:** `type CartState = "empty" | "active" | "checked-out"` — carries no data.

**Right:**
```ts
type CartState =
  | { status: "empty" }
  | { status: "active";       items: CartItem[]; total: number }
  | { status: "checked-out";  orderId: string }
```

The shared discriminant field (`status`) lets TS narrow to the correct branch automatically. Each branch carries all data needed for that state.

### Utility Types

```ts
interface User {
  id: number
  name: string
  email: string
  role: "admin" | "viewer"
}

type UserDraft     = Partial<User>              // all fields optional — update payloads
type PublicUser    = Pick<User, "id" | "name">  // subset of fields
type NewUser       = Omit<User, "id">           // drop a field (DB assigns id)
type UserMap       = Record<string, User>        // userId → User lookup
```

**Common combo:** `Partial<Pick<T, K>>` — some of these fields, none required (patch payload).

---

### `unknown` vs `any`

- `any` — disables type checking entirely. Avoid.
- `unknown` — type-safe alternative. Forces narrowing before use.

```ts
function process(value: unknown) {
  if (typeof value === 'string') {
    value.toUpperCase()  // safe — narrowed to string
  }
}
```

Use `unknown` for external data: API responses, `JSON.parse`, user input.

---

### Design Note: Computed vs Stored Values

Storing derived data in state (e.g., `total` alongside `items`) creates a consistency risk — the two can drift out of sync. Prefer computing on the fly:

```ts
// Safer: derive from source of truth
const total = state.items.reduce((sum, item) => sum + item.price * item.quantity, 0)
```

This principle applies broadly to state modeling across any language or framework.

## Exercise: Shopping Cart Domain

```ts
interface CartItem {
  id: number
  name: string
  price: number
  quantity: number
}

type CartState =
  | { status: "empty" }
  | { status: "active"; items: CartItem[]; total: number }
  | { status: "checked-out"; orderId: string }

type Result<T> = { ok: true; data: T } | { ok: false; error: string }

function getTotal(state: CartState): Result<number> {
  if (state.status === "active") {
    const total = state.items.reduce((sum, item) => sum + item.price * item.quantity, 0)
    return { ok: true, data: total }
  }
  return { ok: false, error: "Cart is not active" }
}

type CartSummary = Pick<CartItem, "id"> & { total: number }
```

**Correction made:** Initial attempt used `type CartState = "empty" | "active" | "checked-out"` (string union) — carries no data, prevents narrowing. Fix: object shapes with a shared `status` discriminant.
