# 4.1 — Modern JavaScript (ES2015+)

> Module: 04 — Modern JavaScript & TypeScript · First taught: 2026-06-24 · Last updated: 2026-06-24

## TL;DR
ES2015+ features are the baseline that React, TypeScript, and every modern JS codebase assume. The key mental shifts: `let`/`const` fail loudly before initialization instead of silently returning `undefined`; arrow functions borrow `this` from where they are *written*, not where they are *called*; and named exports let bundlers statically remove code that is never used.

## Key Concepts

### Block Scoping and the Temporal Dead Zone (TDZ)

`var` is function-scoped and hoisted — its declaration is moved to the top of the function before execution, so reading it before assignment gives `undefined` rather than an error. `let` and `const` are block-scoped: they exist only within the `{}` they were declared in.

Both `let` and `const` are also hoisted, but they land in the **Temporal Dead Zone**: the variable slot exists in memory but any access before the declaration line throws a `ReferenceError`.

```js
console.log(name); // ❌ ReferenceError: Cannot access 'name' before initialization
let name = "Alice";

console.log(other); // ✅ undefined  (var hoisting — no error)
var other = "Bob";
```

**Why TDZ exists:** silent `undefined` hides bugs; a loud crash surfaces them immediately. The same philosophy as TypeScript's strict mode — prefer visible errors over hidden state.

`const` locks the *binding* (the variable), not the *value* it points to:

```js
const user = { name: "Alice" };
user.name = "Bob";   // ✅ object contents can change
user = {};           // ❌ the binding cannot be reassigned
```

### `this` in Regular Functions vs Arrow Functions

In a regular function, `this` is determined by the **call site** — how the function is called at runtime, not where it was written.

```js
const user = {
  name: "Alice",
  greet: function() {
    console.log(this.name); // "Alice" — called as user.greet()
  }
};
user.greet(); // ✅ "Alice"
```

When the function is passed as a callback, the object context is lost:

```js
const user = {
  name: "Alice",
  greet: function() {
    setTimeout(function() {
      console.log(this.name); // ❌ undefined / window.name
    }, 1000);
  }
};
```

`setTimeout` calls the callback on its own — not as `user.callback()` — so `this` becomes `window` in a browser, or `undefined` in strict mode.

**Arrow functions fix this** because they have no own `this`. They inherit `this` from the scope where they were written:

```js
const user = {
  name: "Alice",
  greet: function() {
    setTimeout(() => {
      console.log(this.name); // ✅ "Alice" — inherited from greet's scope
    }, 1000);
  }
};
```

| | `this` determined by |
|---|---|
| Regular function | Call site (how it is invoked at runtime) |
| Arrow function | Lexical scope (where it is written) |

React class components historically used arrow function class fields (`handleClick = () => {...}`) for event handlers to avoid losing `this` when the method was passed as a prop. Hooks (`useState`, `useCallback`) removed this problem entirely.

### Tree-Shaking: Named vs Default Exports

**Tree-shaking** is the bundler's process of removing exports that are never imported. It works because `import` statements are **static** — the bundler reads the full import graph at build time, before running any code.

Named exports are statically analyzable:

```js
// utils.mjs
export const formatDate = () => { ... }
export const formatCurrency = () => { ... }
export const formatPhone = () => { ... }

// app.mjs
import { formatDate } from './utils.mjs';
// ✅ bundler sees only formatDate is imported — others are removed
```

Default exports export an object, which is opaque to static analysis:

```js
// utils.mjs
export default {
  formatDate: () => { ... },
  formatCurrency: () => { ... },
}

// app.mjs
import utils from './utils.mjs';
utils.formatDate();
// ❌ bundler cannot know which properties are used at runtime — ships everything
```

Real-world impact:

```js
import { debounce } from 'lodash-es';  // ✅ ships only debounce (~2 KB)
import _ from 'lodash';               // ❌ ships the full library (~70 KB)
```

At the architecture level this is enforced via ESLint rules (e.g., `import/no-default-export`) for shared utility libraries.

## Examples

### React class component — `this` lost vs fixed

```js
// ❌ method passed as prop loses this
class Button extends React.Component {
  handleClick() {
    console.log(this.state.count); // undefined — React calls it as a plain function
  }
  render() {
    return <button onClick={this.handleClick}>Click</button>;
  }
}

// ✅ arrow function class field — this is always the component instance
class Button extends React.Component {
  handleClick = () => {
    console.log(this.state.count); // correct — lexical this
  }
  render() {
    return <button onClick={this.handleClick}>Click</button>;
  }
}
```

### Two-file async/await module (exercise pattern)

```js
// api.mjs
export const fetchGitHubUser = async (username) => {
  const response = await fetch(`https://api.github.com/users/${username}`);
  if (!response.ok) throw new Error(`User not found: ${response.status}`);
  return await response.json();
};

// main.mjs
import { fetchGitHubUser } from './api.mjs';

async function init() {
  const { name, followers, public_repos } = await fetchGitHubUser('torvalds');
  console.log(`${name} — ${followers} followers, ${public_repos} repos`);
}

init().catch(err => console.error(err.message));
```

## Common Pitfalls

### Swallowing errors with an implicit `undefined` return

A common mistake is catching an error, logging it, and returning nothing:

```js
// ❌ catch swallows the error and returns undefined implicitly
async function fetchUser(id) {
  try {
    return await api.get(id);
  } catch (error) {
    console.log(error.message); // logged here...
  }
}

const { name } = await fetchUser(42); // ...but caller crashes: cannot destructure undefined
```

Fix: either re-throw from `catch`, or handle the error in the caller with its own `try/catch`.

### `fetch` does not throw on 4xx/5xx

`fetch` only rejects on network failure. A 404 is a successful network request — `response.ok` is `false` but no exception is thrown. Always check before parsing:

```js
const response = await fetch(url);
if (!response.ok) throw new Error(`HTTP ${response.status}`);
const data = await response.json();
```

This is the same rule as in 3.6 — reinforced here because it is a common source of silent bad data flowing through an application.

### `const` does not mean immutable

`const` prevents reassigning the variable — it does not freeze the object. Mutating a `const` array or object is valid JavaScript. This matters in React: spreading creates a new reference (triggers re-render); mutating in place returns the same reference (re-render skipped).

### Variable name mismatch in catch block

```js
// ❌ easy typo — err vs error
try { ... } catch (error) {
  console.log(err.message); // ReferenceError: err is not defined
}
```
