# 6.2 — Global State Management

> Module: 06 — Frontend Data, State & Styling · First taught: 2026-07-06 · Last updated: 2026-07-06

## TL;DR
Global state management is about sharing *client* state across components that sit far apart in the tree, without threading it through every layer as props. It is a **last resort**, reached only after local `useState` and lifting-state-up fail. The two tools are **React Context** (good when the value changes rarely) and a **store** like Zustand/Redux (good when the value changes frequently and has many independent readers, because a store lets each component subscribe to just one slice). The subtle trap: a Context value built as a fresh object literal on every render re-renders *all* consumers whenever the provider's parent re-renders — `useMemo` (plus stable callbacks) is what prevents that.

## Key Concepts

### The state-placement ladder
Before choosing *how* to share state, rule out the cheaper rungs. Always climb in this order:

1. **Local `useState`** — one component owns the value. Cheapest. Default.
2. **Lift + props** — move the value up to the nearest common ancestor of the components that need it, and pass it down as props.
3. **Global (Context or store)** — only when lifting would force you to pass the value through intermediate components that never use it.

Global is the *last* rung, not the second. The word that justifies climbing to it is **prop drilling**.

### Prop drilling — the trigger for going global
Prop drilling is when a value has to reach components that are **far apart** in the tree, so lifting means threading the prop through **many intermediate components that never read it** — they just forward it. That forwarding noise is the smell. A defensible sentence in a design review:

> "I reached for Context because lifting would mean prop-drilling through five layers that don't touch the value."

Note: "the value can be read/written anywhere" is *not* the trigger — that is true of any lifted state too. The specific trigger is the pass-through-layers-that-don't-care shape.

### Context vs. store — the decision rule
- **Context** when the shared value changes **rarely** (auth user, theme/locale, feature flags).
- **Store** (Zustand/Redux) when the value changes **frequently** *and* has **many independent readers**.

Two *different* reasons can send a value to a store — worth separating because they read as senior in review:
- **Speed** — the value updates very often (e.g. a live collaborative cursor at ~60×/sec). Context would re-render its whole consumer set on every tick and melt.
- **Selectivity** — the value has independent readers that each care about a *different slice* (e.g. a shopping cart: a badge reads `count`, a drawer reads `items`, checkout reads `total`). A store lets each component subscribe to just its slice, so adding one item updates the badge **without re-rendering the open drawer**. Context cannot express "I only care about part of this value."

### Why a store beats Context for big, slice-y state
When a **Context** value changes, **every** consumer re-renders — even consumers that only read a part that didn't change. Context has no partial-subscription mechanism; change *anything* in the value and *everyone* subscribed re-renders.

A **store** exposes selector subscriptions: `useStore(s => s.user.name)` re-renders the component **only** when that specific slice changes. Concrete payoff, using the YouTube header (avatar reads `user`, bell reads `notifications`, search box reads `searchQuery`, all in one store): a new notification arrives → **only the bell re-renders**; the avatar and search box stay put. Under Context, all three would have re-rendered because the shared object changed.

### The two causes of a re-render (and why `useMemo` on a Context value is essential)
A component re-renders for exactly two reasons:
1. Its **own state or props** changed.
2. Its **parent re-rendered** — by default, when a component re-renders, all of its children re-render too, whether or not their props changed.

Cause #2 is the one people forget, and it is what makes a Context provider dangerous:

```tsx
// BUG: new object literal every render
return <ThemeContext.Provider value={{ theme, toggleTheme }}>{children}</ThemeContext.Provider>;
```

`{ theme, toggleTheme }` builds a **brand-new object** (same contents, new reference) on every render of the provider. Context compares values by **reference**, not contents. So whenever the provider's *parent* re-renders for any unrelated reason (a route change, sibling state), the provider re-renders, rebuilds the object, the reference changes, and **every consumer re-renders even though the theme never changed**.

The fix pins the reference so it only changes when the data actually changes:

```tsx
const toggleTheme = useCallback(() => setTheme(t => (t === 'light' ? 'dark' : 'light')), []);
const value = useMemo(() => ({ theme, toggleTheme }), [theme, toggleTheme]);
```

`useMemo` does **not** protect against real theme changes (those *should* re-render everyone — the whole UI recolors). It protects against **parent-driven re-renders** rebuilding the object reference for no reason. And the `useMemo` is only effective if `toggleTheme` also has a stable identity — otherwise its dependency changes every render and the memo never holds. The two go together: stabilize the callbacks *and* memoize the object, or neither works.

### Typing a Context safely
Type the context as `T | null` with a `null` default, and expose a custom hook that throws when used outside the provider:

```tsx
const ThemeContext = createContext<ThemeContextValue | null>(null);

export function useTheme(): ThemeContextValue {
  const ctx = useContext(ThemeContext);
  if (ctx === null) throw new Error('useTheme must be used within a <ThemeProvider>');
  return ctx; // narrowed to ThemeContextValue — no `| null` leaks to callers
}
```

Why `null` and not a fake default like `{ theme: 'light', toggleTheme: () => {} }`? A fake default lets a component *accidentally rendered outside the provider* "work" silently against a dead no-op toggle — a bug that hides itself. `null` + a throwing hook turns that mistake into a loud, immediate error, and gives every caller a clean non-nullable type.

### Server state stays in TanStack Query
This whole topic is about **client** state. Server state (remote, shared, cacheable, goes stale) belongs in TanStack Query (see [6.1](6.1-data-fetching-tanstack-query.md)) — do not copy it into a Context or store. Keep the two separate: server cache in Query, genuine client state in Context/store.

## Examples
- **Theme toggle (Context):** light/dark changes rarely, and when it changes you *want* the whole tree to recolor — so a full re-render on change is correct, and Context is the right tool.
- **Auth user (Context):** `{ id, name, avatar }` changes only on login/logout — rare, so Context.
- **Live collaborative cursor (store, for speed):** Figma-style editor, updates ~60×/sec, many readers — Context would re-render everyone every tick.
- **Shopping cart (store, for selectivity):** Shopee cart where a badge, a drawer, and checkout each read a different slice — a store updates only the piece whose slice changed.
- **YouTube header (store, slice subscriptions):** avatar/bell/search each subscribe to their own slice, so a new notification re-renders only the bell.

## Common Pitfalls
- **Skipping the ladder.** Jumping straight to Context/store when lifting state up would have solved it. Global is the last resort, not the reflex.
- **Passing a fresh object literal as the Context `value`.** `value={{ a, b }}` re-renders every consumer whenever the provider's parent re-renders. Wrap it in `useMemo`.
- **Memoizing the value object but leaving callbacks unstable.** If a function in the value gets a new identity each render, the `useMemo` dependency changes every render and the memo never holds. Stabilize callbacks with `useCallback` first.
- **Thinking `useMemo` guards against the value changing.** It guards against *parent-driven* re-renders rebuilding the reference; real changes still (correctly) re-render consumers.
- **A fake Context default** (`{ theme: 'light', toggleTheme: () => {} }`) instead of `null`. It hides "used outside provider" bugs and leaks a nullable-feeling API. Use `null` + a throwing hook.
- **Putting server state in Context/store.** Server data belongs in a query cache that handles staleness; a hand-rolled Context copy loses caching, refetching, and invalidation.
- **Assuming Context is slow, or that a store is always better.** Context is perfectly fast for rarely-changing values. The choice is about change frequency × number of readers × render cost, not a blanket rule.
