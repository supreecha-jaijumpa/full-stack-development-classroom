# 6.6 — Custom Hooks

> Module: 06 — Frontend Data, State & Styling · First taught: 2026-07-17 · Last updated: 2026-07-17

## TL;DR
A custom hook is any function whose name starts with `use` and which calls other hooks — but the architect's definition is sharper: **a custom hook is a seam between behavior and presentation.** You extract one not to kill duplication but to draw a line where a *mechanism* (fetching, subscribing, syncing) hides behind a *stable interface*, so components stay dumb about the mechanism and the mechanism stays swappable without touching them. The hook's return value is a public API governed by the same contract discipline as component props (6.5): expose intent, not internals; return an object so the contract can grow additively. Hooks share logic by **composition** (calling small hooks inside bigger ones) — React's answer to what HOCs, mixins, and inheritance did worse. And the extraction rule from 6.5 applies unchanged: extract on *essential* sameness (changes together for the same reason), never on *coincidental* sameness (looks alike today), because a wrong shared hook is more expensive than the duplication it replaced.

## Key Concepts

### 1. A hook is a seam between behavior and presentation
A component that fetches data, tracks loading/error, *and* renders knows two unrelated things — *how to get data* and *how to display it* — so it has two reasons to change living in one file. Pull the mechanism into a hook and the component becomes a description of the UI:

```tsx
function ProfileCard({ id }: { id: string }) {
  const { user, isLoading, error } = useUser(id)   // WHAT it needs
  if (isLoading) return <Spinner />
  if (error) return <ErrorState />
  return <Card name={user.name} avatar={user.avatar} />   // HOW it looks
}
```

Because the seam is a stable interface (`{ user, isLoading, error }`), the implementation behind it — `fetch` → TanStack Query, REST → GraphQL — can be replaced and `ProfileCard` never changes. The real payoff is not "less code"; it is that **the component and the mechanism can now change independently**, so the next engineer who has to migrate the data source edits *one hook* instead of *every screen that used it*.

**Mid-level trigger vs architect trigger:** a mid-level dev extracts a hook when they notice *repetition*. An architect extracts one to *draw the seam* — the deciding question is "what mechanism do I want to hide behind a stable interface?", not "what's duplicated?"

### 2. The return value is a public API (same discipline as props)
Whatever a hook returns is a contract, exactly like a component's props.

- **Return an object, not a positional array** — unless you are deliberately mimicking `useState`'s two-item tuple (e.g. `useToggle` → `[on, toggle]`, where there are exactly two things and the order is obvious). A positional array is position-locked: add a fifth return value and every caller's destructuring must be rewritten. An object is **additive** — new fields don't touch existing callers, so the hook's contract can *evolve* without a breaking change.
- **Expose intent, not internals.** Return `{ user, isLoading, error, refetch }` — what the caller needs — not `{ cacheRef, abortController, rawResponse }`. Every field you return is a promise you must keep; leak an internal and someone depends on it, freezing your ability to change how the hook works.

### 3. Hooks compose — React's answer to sharing logic
Before hooks, sharing stateful logic meant HOCs (`withUser(Component)`), render props, or class inheritance / mixins — all fighting the same problem: *how do two components share behavior?* Hooks answer with **composition**: a hook can call other hooks, so big behavior is built from small behavior.

```tsx
function useAuth() {
  const token = useContext(AuthContext)
  const { data: user } = useQuery({
    queryKey: ['me'],
    queryFn: () => fetchMe(token),
    enabled: !!token,
  })
  return { user, isAuthenticated: !!user }
}
```

`useAuth` is just `useContext` + `useQuery` wired together and given a clean name. Each piece stays small, focused, and independently testable; the useful behavior emerges from the composition. This is the frontend expression of **composition over inheritance**.

The design rule that keeps it healthy: **one hook, one responsibility.** A hook that fetches data *and* manages a form *and* syncs a query param has three reasons to change in one place — touch it to fix the form and you risk breaking the other two, and a component that needs only one of the three behaviors can't reuse it without dragging along all three. Small focused hooks compose; a god-hook forces all-or-nothing.

### 4. Extract on essential sameness, not coincidental (the 6.5 trap again)
Two components whose logic *looks* alike is not a reason to extract a shared hook. Ask: do they look alike, or do they change for the same reason?

- **Coincidental** — `useUserForm` and `useCheckoutForm` both track `values`, `errors`, `isSubmitting`. Looks like one `useForm`. But they validate different things, submit to different places, and evolve on different schedules. Merge them and you get a hook with `if (isCheckout)` branches serving two masters — the **wrong abstraction**.
- **Essential** — every form blocks navigation on unsaved changes *the same way, changing together for the same reason.* That's one behavior; extract `useUnsavedChangesGuard` and every form gets fixes in one place. `useDebounce` is essential too — debouncing is a single behavior wherever it appears.

Apply the **rule of three**. And know why guessing wrong is worse than duplication: duplicated code is cheap because it's isolated — nothing else depends on the copy, so you just delete it. A wrong shared hook is expensive because callers now depend on its *shape* (its arguments and return values), so undoing it means un-merging it while people are standing on it.

## Examples
- **`useUser(id)` behind a `ProfileCard`** — a GitHub-style profile card renders from `{ user, isLoading, error }` and stays untouched when the data layer migrates from `fetch` to TanStack Query, or REST to GraphQL. The hook is the swap point.
- **`useAuth()` on a streaming app (Netflix/Spotify pattern)** — `useContext(AuthContext)` for the token + `useQuery(['me'])` for the profile, composed into one hook every screen calls; the navbar, the account page, and a route guard all read `{ user, isAuthenticated }` without knowing how either piece is fetched.
- **`useUnsavedChangesGuard()` across every form** — the "you have unsaved changes, leave anyway?" behavior is identical everywhere and changes for one reason, so it lives in one hook. The opposite of a fake `useForm` that tries to unify a user-settings form and a checkout form that merely share three state variable names.

## Common Pitfalls
- **Extracting a hook the moment code looks duplicated.** Repetition is a hint, not a mandate. Coincidental similarity (same shape today) is not essential similarity (changes together for the same reason); a hook built on the former becomes a magnet for props and `if` branches serving two masters. Apply the rule of three.
- **Returning a positional array by default.** It position-locks every caller, so the contract can't grow without a breaking change. Return an object; reserve the tuple for genuine two-item `useState`-style hooks where the order is obvious.
- **Leaking internals in the return value.** Handing back `rawResponse`/`cacheRef`/`abortController` invites callers to depend on them, freezing the implementation. Return only what expresses the caller's intent.
- **Building a god-hook.** One hook doing three jobs has three reasons to change, can't be partially reused, and spreads the blast radius of every edit. One hook, one responsibility — then compose.
- **Thinking the payoff is "less code."** The payoff is *independent change*: the component and the mechanism can each evolve without disturbing the other, so a data-layer migration touches one file instead of many.
