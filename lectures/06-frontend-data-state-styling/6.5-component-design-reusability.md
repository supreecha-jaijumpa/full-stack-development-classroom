# 6.5 — Component Design & Reusability

> Module: 06 — Frontend Data, State & Styling · First taught: 2026-07-17 · Last updated: 2026-07-24

## TL;DR
A component's props are a **public API** — a contract you publish and must keep, because the moment you ship a prop something depends on it. The architect's job is not "what props do I need today" but "what am I willing to promise forever," and the answer is: **expose the smallest surface that lets every screen use the component and none of them misuse it.** Express *intent* through props, hand out *content* through composition, decide deliberately *who owns the state*, and refuse to extract a shared component until the similarity is essential, not coincidental. This is the same architect move as the rest of the module — make valid choices declarable in one place and invalid ones hard to express — applied to **behavior** rather than data shape (6.3) or look (6.4).

## Key Concepts

### Props are a public API, not function arguments
Once a component is used in more than one place, its props become a contract other code depends on. Renaming `onChange`, narrowing what `variant` accepts, or making a required prop optional are **breaking changes to code you no longer own**. So every prop you add is a promise you must keep. The design question becomes: *what is the smallest set of promises that still lets callers do what they legitimately need?*

### A wide API is a liability, not a feature
The instinct to make a component "flexible" — a prop for every possible tweak — is the opposite of generous:

```tsx
// API A — "flexible" (leaks implementation)
<Button color="blue" hoverColor="darkblue" paddingX={16} paddingY={8}
        borderRadius={6} fontWeight={600} onClick={save}>Save</Button>

// API B — "constrained" (expresses intent)
<Button variant="primary" onClick={save}>Save</Button>
```

Two costs of the wide API:
1. **Drift.** Every caller can restyle locally, so the design fragments into inconsistency; when one value must change, a maintainer has to find and edit every call site instead of one config.
2. **It freezes your own hands.** The day you ship `paddingX`, a screen depends on it — now you *can't* migrate the button to a token-based spacing system without breaking that screen. The fewer things you promise, the more you stay free to change later.

**Rule: props express *intent* (`variant="primary"`), not *implementation* (`paddingX={16}`).** Intent props keep *how it looks* yours to evolve.

### Composition (`children`) is the safe escape hatch
A narrow API eventually meets a need you didn't anticipate. The usual right answer is **not** "add a prop" — it's "hand the caller composition."

```tsx
// Configuration — grows a new prop for every screen variation
<Card title="Repo" subtitle="public" badge="TS" footerButton="Star" />

// Composition — the caller assembles the pieces; the API never grows
<Card>
  <Card.Header>Repo <Badge>TS</Badge></Card.Header>
  <Card.Body>public</Card.Body>
  <Card.Footer><Button>Star</Button></Card.Footer>
</Card>
```

`children` flexibility is safe while `paddingX` flexibility is dangerous because of **what kind of thing each lets the caller vary**:
- `children` varies **content** — which is *supposed* to differ on every screen (cheap: it's code/content duplication).
- `paddingX` varies a **design decision** — which is supposed to stay identical everywhere (expensive: it's decision duplication).

`<Card>` stays consistent because it hands out **slots for content**, never **its decisions** — the look, spacing, and structure stay owned in one place. That is why composition scales without the API growing: *you give away the content, not the decisions.* (The 6.4 line, applied to structure: "duplication of code is cheap; duplication of decisions is expensive.")

### Controlled vs uncontrolled — who owns the state
When a component holds interactive state ("which tab is active," "is the menu open"), someone must own it. This choice is invisible in the markup but defines the contract.

```tsx
// Uncontrolled — the component owns its own state
<Tabs defaultActive="overview" />        // caller sets the start, then forgets

// Controlled — the caller owns the state
<Tabs active={active} onActiveChange={setActive} />  // caller drives the value
```

Good libraries (Radix, MUI, React's own `<input>`) support **both** on the same component, because there are two kinds of caller and neither should pay the other's cost — a pattern called **progressive disclosure**:
- The **90% caller** (simple screen) gets the cheap door: `defaultActive`, no state to wire.
- The **10% caller** (needs to coordinate the value with a URL, a sibling, a reset, a save) gets the powerful door: `active` + `onActiveChange`, driving the value **from outside** the component.

Ship only controlled and every simple caller pays boilerplate they don't need; ship only uncontrolled and the power caller hits a wall and forks your component. (Real-world: a video player's play/pause state — uncontrolled, the player just plays; controlled, the *page* owns it, which is what lets the product auto-pause on scroll or sync a "continue watching" state.)

### Don't extract too early — coincidental vs essential similarity
The senior counterweight to "make it reusable": **a wrong abstraction costs more than the duplication it replaced.** Before extracting a shared component from two things that *look* alike, ask the 6.4 test:

> "When one of these changes, do I want the other to change **with it** or **independently**?"

- **Essential similarity** — they'd change *together for the same reason* → extracting is correct.
- **Coincidental similarity** — they only *look alike today* and would evolve for *different* reasons → extracting now is a trap.

The failure mode of extracting too early: the shared component grows a **new prop (or `if` branch) every time the two callers drift apart**, until one component is nervously serving two masters — genuinely harder to maintain than the two honest copies you started with. The practical heuristic is the **rule of three**: duplicate first, extract on the third occurrence, when you can actually see what is shared versus what merely rhymed.

### A narrow contract can still be broken from the inside
A component can pass every check on paper — a small prop count, intent-named props, no leaked implementation details — and still violate its own contract through *what a prop is used to say*, not just what type it accepts.

Take a stat-tile-style component with a primary `value` and a secondary `note` prop meant to add short context. The implicit contract of a "context" prop is that it describes *the same subject* as the value next to it — a reader sees a label and a note together and assumes they're about one thing. Nothing in TypeScript enforces that: `note` accepts any string, so a caller under pressure to surface one more stat with nowhere else to put it can quietly stash unrelated information there ("Forks: 12K" with a note reading "Last push 3 hours ago"). The component still type-checks and the prop count stays narrow — but the contract is broken in a way types can't catch, because the violation is about *meaning*, not *shape*.

This is the same discipline as choosing `.strict()` at a validation boundary (see [6.3 — Forms & Validation](6.3-forms-and-validation.md)): a contract isn't only "what shape is allowed in this slot," it's also "what is this slot *for*," and a slot can be misused while every static check still passes. The fix is either a dedicated slot for the unrelated stat (a fifth tile, a different section) or leaving it out — never overloading a meaning-scoped prop as a dumping ground because it happened to be the nearest open surface.

## Examples
- **Button `variant` vs raw style props** — `variant="primary"` names the *role* (this is the primary action) and lets the design system own the pixels; `paddingX={16}` bakes a pixel decision into the public API and freezes future change.
- **A card in a content feed** (e.g. a GitHub repo card or a media card): configuration-style (`title`/`subtitle`/`badge`/`footerButton` props) forces a new prop for every layout the product dreams up; composition-style (`Card.Header`/`Card.Body`/`Card.Footer` + `children`) lets each screen bring its own content while the card owns the frame.
- **A video player's play/pause** — uncontrolled: the player owns it and just plays. Controlled: the page owns it, which unlocks page-level behavior (auto-pause when the user scrolls the player out of view, sync playback across a "continue watching" row) that the component alone could never coordinate.
- **A search-results list** where the "repo result" row and the "user result" row look similar today — extracting a shared `<ListItem>` is only safe if a design change to one *should* propagate to the other; if they'll drift (repos gain a star count, users gain a follow button), the shared component becomes a two-master tangle.

## Common Pitfalls
- **Confusing flexibility with quality.** A common mistake is adding a prop for every conceivable tweak; each prop is a permanent promise that both invites drift and blocks your own future refactors.
- **Leaking implementation through the API.** Exposing `paddingX`/`borderRadius`/`fontWeight` instead of an intent prop (`variant`) ties callers to *how* the component is built, so it can never be rebuilt without breaking them.
- **Reaching for a new prop when `children` is the answer.** If the caller just needs to put *different content* inside, that is composition, not configuration — adding a prop grows the API for something `children` already handles.
- **Handing out decisions instead of slots.** Composition is safe only when what the caller controls is *content*; if `children` (or a render prop) lets callers override the component's *design decisions*, you have reintroduced drift through a different door.
- **Picking controlled-only or uncontrolled-only by default.** Uncontrolled-only walls off callers who must coordinate the value externally; controlled-only taxes every simple caller with boilerplate. Mature components offer both.
- **Extracting on looks.** A common mistake is extracting a shared component because two pieces of UI *render* similarly today; similarity of appearance is not a reason to couple — only a shared reason-to-change is.
- **Abstracting before the rule of three.** Two occurrences rarely reveal the true shared shape; extracting then usually produces an abstraction that bends awkwardly as soon as a third, slightly different case appears.
- **Overloading a meaning-scoped prop.** A "context" or "note" prop implicitly promises it describes the same subject as the value beside it; stashing unrelated information there because it's the nearest open surface breaks that promise even though the type system sees nothing wrong.
