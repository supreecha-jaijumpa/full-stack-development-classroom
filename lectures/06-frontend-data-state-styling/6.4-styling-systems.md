# 6.4 — Styling Systems (Tailwind / CSS-in-JS)

> Module: 06 — Frontend Data, State & Styling · First taught: 2026-07-16 · Last updated: 2026-07-16

## TL;DR
Styling at scale is not about making one screen look right — it's about designing a *system* so the next engineer can't make things look wrong. Four architectural moves carry the topic: **design tokens as a contract** (one palette, the wrong value isn't typeable), **the utility-vs-component line** (extract *decisions*, not *accidental lookalikes*), **variants with cva** (valid combinations become a typed table), and **theming via semantic tokens → CSS custom properties** (components name *roles*, not colors, so themes swap underneath). The single idea under all four: **make the valid choices declarable in one place, and let the tooling or the cascade enforce them.**

## Key Concepts

### Design tokens as a contract
A utility class like `bg-brand` is a *name pointing at a value* in `tailwind.config`. That indirection is the whole point. Without tokens, every engineer picks raw values and the design drifts into "40 shades of blue," `13px` here and `14px` there, with no single place to fix it. With tokens, the config is the **single source of truth** for the product's look — the same architectural role a Zod schema plays for runtime shape (see [6.3](6.3-forms-and-validation.md)). An engineer can only reach for values that exist; rebranding means editing the config, not 800 files.

```ts
// tailwind.config.ts — the contract
export default {
  theme: {
    extend: {
      colors: {
        brand:  { DEFAULT: '#0969DA', hover: '#0860CA' },
        danger: '#CF222E',
      },
      spacing: { gutter: '1.5rem' },
    },
  },
}
```

The trade to be able to state out loud: **tokens cost the individual engineer the freedom to type any hex they want, and buy the product visual consistency.** A junior sees the constraint as a limitation; an architect sees *the constraint is the feature*.

### The utility-vs-component line
Tailwind gives two ways to reuse a look: repeat the utility classes inline, or extract a component (`<Button variant="primary">`). The decision rule:

> **Duplication of *code* is cheap. Duplication of *decisions* is expensive.**

Three `<div>`s that share `flex gap-2` aren't really duplicated — they each independently needed a row, and if one changes later you *want* it to change alone. A **button**, on the other hand, is a *decision*: "this is what a primary action looks like in our product," which must be identical everywhere and change in exactly one place. That deserves a name (a component). Accidental lookalikes do not.

| Extract a component when… | Keep utilities inline when… |
|---|---|
| It's a **named concept** (Button, Card, Badge) | It's a **one-off layout** (this page's grid) |
| The look **must stay identical** everywhere | Instances may **drift independently** |
| Changing it should change **all** instances | You'd be **coupling accidental lookalikes** |

The one-line test: **"if this changed, would I want all copies to change together, or independently?"**

### Variants with cva (class-variance-authority)
Once something *is* a real component, it usually has many looks: `intent × size × disabled`. Encoding that with nested ternaries in `className` is unreadable and unenforced. **cva** turns variants into a declared table:

```ts
import { cva } from 'class-variance-authority'

const button = cva('rounded-md font-medium transition-colors', {
  variants: {
    intent: {
      primary:   'bg-brand text-white hover:bg-brand-hover',
      secondary: 'bg-gray-100 text-gray-900 hover:bg-gray-200',
      danger:    'bg-danger text-white hover:bg-danger/90',
    },
    size: { sm: 'px-3 py-1 text-sm', md: 'px-4 py-2' },
  },
  defaultVariants: { intent: 'primary', size: 'md' },
})

<button className={button({ intent: 'danger', size: 'sm' })}>Delete</button>
```

The base classes live once; each variant is one readable row. Because cva infers types, the component's **API becomes a type** — `intent="dagner"` is a compile error, not a silently-unstyled button. The payoff is for the *person* who adds `intent="warning"` six months later: they add one isolated row (no side effects on siblings) and the compiler now knows the variant exists (typos die at build). Same instinct as [6.3](6.3-forms-and-validation.md)'s schema — *declare the valid states, let the tooling enforce them.*

### Theming via semantic tokens → CSS custom properties
Scattering `bg-white dark:bg-gray-900` across 500 components hardcodes *two* themes into every file — the theme decision smeared everywhere. The architectural version points tokens at **CSS custom properties** and lets the theme swap the properties:

```css
:root                      { --color-bg: #ffffff; --color-fg: #111827; }
:root[data-theme="dark"]   { --color-bg: #0b1120; --color-fg: #f9fafb; }
```
```ts
// tailwind.config — tokens read the variables
colors: { bg: 'var(--color-bg)', fg: 'var(--color-fg)' }
```
```tsx
<div className="bg-bg text-fg">…</div>   // names a role, never a color
```

Now the whole theme is one attribute on `<html>`. Flip `data-theme` and every `bg-bg` re-resolves with **zero component changes**. A third theme (high-contrast, a white-label brand) is one new block of custom properties — the components stay theme-blind because they name a **role**, not a color.

This is the same architecture appearing three times across the curriculum:
- **[2.2](../02-html-css/2.2-css-fundamentals.md)** — CSS custom properties as the swap point.
- **[6.2](6.2-global-state-management.md)** — `ThemeContext` is the React state that *decides* the active theme.
- **6.4 (here)** — semantic tokens → custom properties is *how components consume* that decision without hardcoding.

Full picture: context holds the choice → sets `data-theme` → custom properties resolve → semantic tokens (`bg-bg`) keep components theme-blind.

### CSS-in-JS trade-offs (the alternative)
Utility-first (Tailwind) isn't the only option — CSS-in-JS (styled-components, Emotion) colocates styles with components and enables fully dynamic, prop-driven styles. The cost is a **runtime**: styles are computed and injected as the component renders, which adds bundle weight and per-render work. Utility-first shifts that work to build time (the CSS is static, generated by scanning classes). Zero-runtime CSS-in-JS libraries (e.g. vanilla-extract) try to keep colocation while moving computation to build time. The architect's summary: **utility-first trades colocation for a static, runtime-free stylesheet; classic CSS-in-JS trades runtime cost for colocation and dynamic power.**

## Examples
- **GitHub** — buttons, badges, links, and focus rings all draw from one small palette of blues and one spacing rhythm. Nobody types `#0969DA` by hand; they type a token name, and the hex lives in exactly one place.
- **Spotify** — the "Play" button appears on an album, a playlist, a track row, and the now-playing bar. That's not "green rounded button" repeated four times; it's *one concept* (`PlayButton`) rendered in many contexts. Tweak the hover once, it changes everywhere.

## Common Pitfalls
- **Premature abstraction.** Extracting a `<Stack>`/`<Row>` that only wraps `flex flex-col gap-4` because it "looks repetitive." Those usages just happen to look alike; the moment one needs `gap-6` or a different direction, you pile on props (`gap`, `direction`, `align`, `wrap`) until you've rebuilt flexbox with a worse API — and any change to a default now risks every call site at once, even the ones that never agreed to move together.
- **Extracting too late.** Copy-pasting the same nine utility classes across thirty files for something that genuinely is one decision (a button). When design changes it, you're now editing thirty files and will miss one.
- **Theme decision smeared everywhere.** `dark:` prefixes on every element instead of semantic role tokens. It works for two themes and collapses the day a third theme (or a client white-label) is requested.
- **Hardcoding raw values past a token system.** Typing `#3b82f6` or `text-[13px]` when a token exists defeats the single-source-of-truth and reintroduces drift.
