# 6.3 — Forms & Validation

> Module: 06 — Frontend Data, State & Styling · First taught: 2026-07-07 · Last updated: 2026-07-07

## TL;DR
Forms are where three architecture decisions meet. **Who owns each input's value** — React state (controlled) or the DOM node (uncontrolled) — decides whether every keystroke re-renders the form; React Hook Form is fast because it keeps inputs uncontrolled and re-renders only subscribers. **Where validation runs** is a trust-boundary decision: client-side validation is a UX courtesy for honest users, while server-side validation is the only real gate, because it is the only validation running on a machine you control. **Where the data shape is declared** should be exactly one place — a Zod schema — with TypeScript types derived via `z.infer`, because TS types are erased at compile time and derivation can only flow from runtime value to static type.

## Key Concepts

### Controlled vs uncontrolled: who owns the value?
**Controlled** — the value lives in React state; the DOM input is a puppet that displays whatever the `value` prop says:

```tsx
const [email, setEmail] = useState("");
<input value={email} onChange={(e) => setEmail(e.target.value)} />
```

Every keystroke must travel event → `setState` → **re-render** → new `value` prop before the character appears on screen. React sits between the keystroke and the pixel.

**Uncontrolled** — the value lives in the DOM node itself (browsers natively hold input text; no framework needed):

```tsx
<input ref={inputRef} />
```

Typing triggers **zero** React re-renders — no state changed anywhere. React reads the value only when it cares: `inputRef.current.value` on submit.

Cost model for a fully-controlled 12-field form with all state at the top: one keystroke re-renders the form component (own state changed) and all 12 fields (parent re-rendered). If that render takes ~80ms on a slow device while the user types ~7 keys/second, keystrokes queue up — the user types `passw`, the box still shows `pas`, and the missing letters catch up in a burst when they pause.

### React Hook Form's architecture
`register("email")` attaches a **ref** — the input stays uncontrolled and the DOM holds the text. RHF tracks values in a mutable internal object (a ref, not `useState`), so typing changes data without triggering any render. Components re-render only when they **subscribe** to something: `formState.errors`, `formState.isValid`, `watch("email")`.

This is the same subscription architecture as a client store with slice selectors (see [6.2 — Global State Management](6.2-global-state-management.md)): writes don't re-render; only subscribers re-render, and only when their slice changes. **RHF is a form-scoped store.**

`<Controller>` is the escape hatch, not the core mechanism — it wraps third-party components that *must* be controlled (a MUI `Select`, a date picker) while isolating their re-renders.

### Validation as a trust boundary
A public endpoint can be called directly, skipping the frontend entirely:

```bash
curl -X POST https://yourapp.com/api/signup \
  -H "Content-Type: application/json" \
  -d '{"email": "x", "password": "a"}'
```

When that request arrives, **zero lines of frontend code run**. Client-side validation executes on the sender's machine, under the sender's control — the client is enemy territory; your React app is a suggestion, not a gate.

- **Client-side validation protects the honest user from frustration.** A typo (`john@gmial.com`) turns the field red instantly instead of costing an 800ms server round-trip. It is a UX feature, and it is optional.
- **Server-side validation protects the database from every client on the internet** — curl, buggy mobile apps, frontends running a stale schema. It is the only validation on a machine you control. Its absence is a **security incident**, not a UX gap: without it, `email: "a"` lands as a row in the users table.

One line to keep: **client validation is a courtesy; server validation is the law.**

### One schema as the single source of truth
Hand-writing a TS interface *and* a Zod schema for the same shape is drift waiting to happen:

```ts
// types.ts — hand-written
interface SignupForm { email: string; password: string }

// schema.ts — also hand-written
const signupSchema = z.object({
  email: z.string().email(),
  password: z.string().min(8),
});
```

TypeScript sees these as two unrelated declarations and never compares them. When a teammate adds a `username` field to the interface and the JSX but not the schema: the build passes (TS checks JSX against the interface only), and at runtime `z.object` **strips unknown keys by default** — validation *succeeds* while silently deleting the new field. No red field, no 500, no log line. Weeks later, someone asks why every `username` in the database is null.

A crash gets someone paged in five minutes; **silent data loss gets discovered in a quarterly report.** Two hand-maintained declarations that "agree today" is an architecture smell.

The fix — write the shape once, derive the rest:

```ts
export const signupSchema = z.object({
  email: z.string().email(),
  password: z.string().min(8),
  username: z.string().min(3),
});
export type SignupForm = z.infer<typeof signupSchema>;
```

The same imported schema runs in the client resolver (`zodResolver(signupSchema)`) and in the server handler (`signupSchema.safeParse(req.body)`). Running it twice is not duplication — the two runs answer different questions (UX vs integrity) from one declaration.

### Type erasure and the direction rule
TypeScript types do not survive compilation — an `interface` compiles to **zero bytes of JavaScript**. At runtime there are no types left in the running program, which is also the deep reason TS cannot validate a network payload. A Zod schema survives because it is not a type: it is a plain JavaScript object, a value in memory. `z.infer` is TypeScript reading that value's structure *at compile time* and computing a type from it.

Hence the rule: **derivation flows value → type, never type → value.** You can read a type off a runtime object; you cannot manufacture a runtime object from something that got erased.

### Server errors in the same inline UI
Some failures only the server can know ("email already taken"). Return them as field errors (400 + flattened field errors from `safeParse`, or a domain error), and map them back into RHF on the client:

```ts
setError("email", { message: "This email is already registered" });
```

The server-sourced error renders in the *same inline spot* as client Zod errors — one error UI, two validation sources.

Accessibility wiring for inline errors: `aria-invalid` on the input, and the error text linked via `aria-describedby` (see 2.5 — the error message becomes part of the input's accessible description).

### `.strict()`
`z.object({...}).strict()` rejects unknown keys instead of silently stripping them — turning silent schema drift into a loud 400 that gets noticed the day it ships.

## Examples
- **Slow-laptop sign-up form:** fully controlled, 12 fields — typed letters trail the fingers and catch up in a burst, because each character can only paint after React re-renders the whole form. With RHF's uncontrolled inputs, the browser paints each letter natively before React does anything; React wakes only for subscribed pieces (the error message, the submit button).
- **The curl attacker:** a perfectly working client-side Zod schema blocks the form UI, but `curl -d '{"email":"x","password":"a"}'` posts straight to the endpoint — only the server-side `safeParse` stands between that payload and a database row.
- **The username drift story:** interface + JSX updated, schema forgotten → build green, validation green, and every submitted username silently vanishes until the null column is noticed weeks later.

## Common Pitfalls
- A common mistake is believing client-side validation provides security. It runs on the sender's machine and can be bypassed entirely (curl, DevTools, disabled JS) — it protects only the honest user's experience.
- A common mistake is reaching for `<Controller>` as React Hook Form's default. The default is `register` (uncontrolled); `Controller` exists only for third-party components that must be controlled.
- A common mistake is expecting interface↔schema drift to produce an error. It produces *nothing*: TS never compares the declarations, and `z.object` silently strips unknown keys — the bug ships green and surfaces as missing data.
- A common mistake is hand-writing a TS type "to match" a Zod schema. Derive it with `z.infer` instead — two hand-maintained declarations always eventually disagree.
- A common mistake is describing validation's payoff in terms of code ("prevents an invalid payload") instead of people and systems ("the user sees the red field instantly"; "no malformed row ever reaches the users table").
- A common mistake is treating a disabled submit button as a gate. It's a courtesy in one place; the invariant is enforced at the server chokepoint.
