# 6.7 — Frontend Performance (memo, lazy, code-split)

> Module: 06 — Frontend Data, State & Styling · First taught: 2026-07-23 · Last updated: 2026-07-23

## TL;DR

React's default behaviour is already fast — a re-render is a function call plus a diff, not a repaint. Every optimisation you add (`React.memo`, `useMemo`, `useCallback`) buys speed with **complexity and a new correctness surface**, so the discipline is *measure first, optimise the proven hot path*. Memoisation only works if props stay **referentially stable**, which means memoising a child forces stabilisation on everything upstream that feeds it — often the better fix is structural (move state down, pass heavy children as `children`). Code splitting (`React.lazy` + `<Suspense>`) solves a *different axis* entirely: initial bundle size and time-to-interactive, not render speed.

## Key Concepts

### 1. The default is fast — optimisation is a cost, not a free win

A re-render means React calls your component function and diffs the resulting element tree. That is usually cheap, and it is **not** the same as the browser repainting.

Every memoisation primitive has a price:

- **Memory** — the cached value and its dependency list are kept alive.
- **Comparison cost** — the prop/dependency check runs on every render, whether or not it saves anything.
- **A new bug class** — a dependency array is a correctness surface you volunteered for. Get it wrong and you ship a stale closure or a stale value: the UI renders yesterday's data with no error anywhere.

So the rule is not "optimise." It is: **profile → find the component that genuinely re-renders hundreds of times or costs real milliseconds → fix that one.** Everything else stays simple, because simple is also a feature.

Precision worth keeping straight: **`React.memo` has no dependency array.** It takes a component and compares props. `useMemo` and `useCallback` are the ones with dependency arrays. That distinction changes what you are actually arguing about in a code review — memo's cost is *comparison overhead plus coupling*; `useMemo`/`useCallback`'s cost is *correctness risk*.

### 2. `memo` + `useCallback`/`useMemo` are one system — referential stability

`React.memo` skips a re-render only when the incoming props are **referentially equal** to the previous ones (a shallow, `Object.is`-style comparison).

That means the moment a parent passes an inline value:

```tsx
<ExpensiveList
  onSelect={() => …}      // new function reference every render
  style={{ padding: 8 }}  // new object reference every render
  items={data.filter(…)}  // new array reference every render
/>
```

…the comparison fails every single time. The memo does nothing except add work. **A defeated memo is pure overhead.**

The architectural consequence: **you cannot memoise a component in isolation.** Memoising the child is a contract the parent must honour — it obliges `useCallback` on the handlers and `useMemo` on the objects/arrays feeding it, and if that parent is itself fed by another, the obligation propagates upward. Before paying that coupling, ask whether the real fix lives somewhere else.

### 3. The best re-render fix is structural, not `memo`

Two moves usually beat memoisation, because they remove the cause instead of masking the symptom:

**Colocate state (push it down).** State held higher than it needs to be re-renders everything beneath it. Move it into the smallest component that actually reads it, and the expensive subtree simply stops being under the change.

**Lift the slow child up and pass it as `children`.** A child element created in the *grandparent's* render and handed down as a prop does not get recreated when the middle component's own state changes — so it does not re-render.

```tsx
// Before: typing in the parent re-renders <HeavyChart/> on every keystroke
function Page() {
  const [q, setQ] = useState('')
  return (
    <>
      <input value={q} onChange={e => setQ(e.target.value)} />
      <HeavyChart />
    </>
  )
}

// After: the state lives in <Toolbar/>; <HeavyChart/> is created here, once
function Page() {
  return (
    <Toolbar>
      <HeavyChart />
    </Toolbar>
  )
}
```

Composition achieves for free what memo achieves with bookkeeping. `memo` treats the symptom; **moving where state lives treats the disease.**

### 4. Code splitting is a different axis — bundle size, not render speed

`React.lazy` + `<Suspense>` defers a chunk of code out of the initial download. This targets **time-to-interactive**, a separate problem from re-render cost, with separate diagnostics.

```tsx
const Analytics = lazy(() => import('./routes/Analytics'))

<Suspense fallback={<PageSkeleton />}>
  <Analytics />
</Suspense>
```

**Where to split.** At boundaries where (a) the user will not feel the async gap and (b) the deferred code is genuinely heavy:

- **Routes** — the default win. The user already expects a transition.
- **Modals / drawers / dialogs** — not needed until opened.
- **Below-the-fold or tab-hidden panels.**
- **Heavy dependencies** — chart libraries, rich-text/WYSIWYG editors, map SDKs, date pickers with large locale data.

**The two cliffs.** Too granular → a waterfall of tiny network requests, each with its own latency, which can be *slower* than one bundle. Too coarse → the initial bundle stays huge and splitting bought nothing.

A lazy boundary is a **promise that the UI can render something meaningful before that code arrives.** So it needs a real fallback and must tolerate the gap — which is why route level is the natural seam and mid-component level rarely is.

**Adjacent tools for the same axis:** route-based prefetching (start the import on hover/intent, before the click), and for long lists, **pagination or virtualization** — rendering 20 rows instead of 10,000 beats memoising 10,000 rows.

### 5. Which axis am I on? — the diagnostic

| Symptom | Axis | Tool |
|---------|------|------|
| Blank screen / spinner on **first** load, snappy once it's up | Bundle size · time-to-interactive | `React.lazy` + `<Suspense>`, route splitting, prefetch |
| Loads fast, but typing lags / list stutters / interactions feel heavy | Render speed | Profiler → colocate state → composition → memo as a last resort |
| Slow **after** an interaction, growing with list length | Render volume | Pagination, virtualization |

A slow first paint that turns snappy afterwards is the **signal that you should split** — it is not something splitting causes. After splitting, first paint gets *faster*, because the heavy code is deferred until the user actually needs it.

## Examples

**Netflix-style browse page.** The row grid, the hero banner and the profile switcher are all in the initial bundle — the user sees them immediately. The full-screen video player, its DRM/streaming SDK and the subtitle engine are `lazy`-loaded, because nobody needs them until a title is clicked, and the click already carries a natural loading moment. Splitting there cuts megabytes off the first download without the user ever perceiving a wait.

**YouTube header + notifications.** A notification arriving updates state near the top of the tree. If that state lives in the app shell, every child re-renders, including the video grid. Colocating it in the notifications component means the grid never hears about it — no `memo` required anywhere.

**Spotify search-as-you-type.** Every keystroke updates state. If the "now playing" bar and the album grid sit under that state, they re-render on each character. The structural fix is to keep the query state inside the search component and pass the grid down as `children`, so it is created once by the parent above. Reaching for `memo` on the grid instead would also require `useCallback`/`useMemo` on every prop feeding it — more code, more dependency arrays, same result.

**A defeated memo in the wild.** A `memo`-wrapped table row that still re-renders on every parent update, because the parent passes `onRowClick={() => select(row.id)}` inline. The memo has been paying its comparison cost the entire time and saving nothing.

## Diagrams

```
Two different axes — do not confuse them
─────────────────────────────────────────────────────────────
                  │ before app runs │ after app runs
 ─────────────────┼─────────────────┼──────────────────────
  what's slow     │ downloading &   │ re-rendering on
                  │ parsing the JS  │ every state change
 ─────────────────┼─────────────────┼──────────────────────
  metric          │ bundle size,    │ render time,
                  │ TTI, first paint│ frames per second
 ─────────────────┼─────────────────┼──────────────────────
  tool            │ React.lazy      │ colocate state →
                  │ + Suspense,     │ composition →
                  │ route splitting │ memo (last resort)
```

```
Order of attack for a slow re-render
────────────────────────────────────
 1. Profile        → is it actually slow, and where?
 2. Colocate       → can the state live lower?
 3. Compose        → can the heavy child be passed as `children`?
 4. Paginate       → am I rendering 10,000 things?
 5. memo/useMemo   → only now, and only on the measured hot path
```

## Common Pitfalls

- **Memoising by reflex, without profiling.** A common mistake is wrapping everything in `React.memo` "to be safe." The next person inherits dozens of dependency arrays they did not write, and when one goes stale they debug a UI showing yesterday's data — with no profiling evidence anywhere explaining why the memo existed. A measurable bug risk was traded for an unmeasured speedup.
- **Confusing `React.memo` with `useMemo`.** `React.memo` wraps a component and compares props; it has no dependency array. `useMemo`/`useCallback` cache a value/function and do.
- **Defeating your own memo.** Passing inline arrow functions, object literals or freshly-`filter`ed arrays to a memoised child makes every comparison fail. The memo now costs and saves nothing.
- **Assuming a re-render is a repaint.** React re-rendering a component does not mean the browser repainted pixels. Treating every re-render as a performance bug leads to optimising things that were never slow.
- **Splitting too granularly.** Lazy-loading many small components creates a request waterfall that can be slower than shipping one bundle. Split at meaningful boundaries — routes, modals, heavy libraries.
- **A lazy boundary with a poor fallback.** If the fallback causes a layout jump or shows nothing, the "faster" load feels worse. The boundary is a promise that something meaningful renders in the gap.
- **Memoising a huge list instead of not rendering it.** Rendering 10,000 rows and memoising them is far worse than paginating or virtualising down to the ~20 visible ones.
- **`useMemo` on trivially cheap values.** Caching `a + b` costs more than recomputing it, and adds a dependency array to get wrong.
