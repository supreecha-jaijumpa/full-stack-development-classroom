# 6.1 — Data Fetching (TanStack Query)

> Module: 06 — Frontend Data, State & Styling · First taught: 2026-07-06 · Last updated: 2026-07-06

## TL;DR
Server data and client data are different *kinds* of state and need different tooling. Server state is remote, shared, and cacheable — the moment your copy lands it can already be **stale**, because someone else can change the source. TanStack Query is not a `fetch` wrapper; it's a **cache with a synchronization policy**. `useQuery` gives you the four async states (loading / error / empty / success), automatic caching keyed by a query key, and **stale-while-revalidate** by default: render the copy you have instantly, revalidate in the background, swap silently if it changed.

## Key Concepts

### Server state vs. client state — staleness is the deciding property
The one distinction that justifies the whole library:

- **Client state** is data you *own*. A drawer being open, the active tab, a form's dirty flag. It's synchronous, true the instant you set it, and **only you can change it**. So it can never go stale. `useState` / a client store (Zustand) is correct here.
- **Server state** is data you're *borrowing*. A product list, a user profile, a repo's star count. You didn't create it and don't own it. It is:
  - **remote** — fetching is async, can fail, can be slow;
  - **shared** — someone else can change the source after you read it, so your copy goes **stale** the moment it lands;
  - **cacheable** — many components want the same data; refetching per-component is waste.

The test for "which tool?" is **staleness**: *can this data change without my app knowing?* If yes → server state → TanStack Query. If no (only I change it) → client state → `useState`/store.

> Worked example: on a repository page, the **list of files** is server state (the server owns it; a teammate's commit changes it behind your back → it goes stale). Whether the **file-tree sidebar is collapsed** is client state (only the user toggles it → it can never go stale). Same screen, two kinds of state, two tools.

### `useQuery`: the four states as distinct branches
`useQuery({ queryKey, queryFn })` returns status you branch on. Render **four visibly distinct UIs**, never fold them together:

1. **loading** — no data yet, first fetch in flight
2. **error** — the fetch failed
3. **empty** — the fetch *succeeded* but returned `[]` (a distinct happy-path state — easy to accidentally hide inside "loading")
4. **success** — data present, render it

```tsx
interface Repo { id: number; name: string; html_url: string }

// The fetcher THROWS on a non-ok response — this is the crux.
// Without it, an API's error JSON slips through as "data" and the
// error and empty branches blur together.
async function fetchRepos(username: string): Promise<Repo[]> {
  const res = await fetch(`https://api.github.com/users/${username}/repos`)
  if (!res.ok) throw new Error(`Request failed: ${res.status}`)
  return res.json()
}

function RepoList({ username }: { username: string }) {
  const { data, isLoading, isError, error } = useQuery({
    queryKey: ['repos', username], // key includes the input → cached per user
    queryFn: () => fetchRepos(username),
  })

  if (isLoading) return <Spinner />                        // loading
  if (isError)   return <p>{(error as Error).message}</p>  // error
  if (data.length === 0) return <p>No repositories.</p>    // empty (its own branch)
  return <ul>{data.map(r => <li key={r.id}>{r.name}</li>)}</ul> // success
}
```

The **query key** (`['repos', username]`) is the cache identity: each distinct key is cached independently, and changing the key fetches (or serves cached) data for the new input.

### `staleTime` vs. triggers — stale ≠ "refetch now"
Two independent axes, and conflating them is the most common misunderstanding:

- **`status`** answers *"do I have data?"* — `'pending'` = no data yet, `'success'` = have data.
- **`fetchStatus`** answers *"am I on the network right now?"* — `'fetching'` / `'idle'`.

`staleTime` is a **freshness window**: how long the cached data is trusted without a second thought. Inside the window the data is **fresh** and will be served from cache with *no* refetch considered. Once the window passes, the data is **stale** — but "stale" triggers nothing by itself. It only means *"next time a good moment comes, revalidate."*

A refetch happens only when data is **stale AND a trigger fires**. Triggers include: a component mounts and requests the query, the window/tab regains focus, the network reconnects, or the query is explicitly invalidated.

> Two gates: `staleTime` decides *whether* data counts as old; triggers decide *when* to actually fetch. That's why fresh data is never refetched (gate 1 blocks it) and stale data isn't refetched on every render (gate 2 waits for an event).

### Stale-while-revalidate (SWR) — the default behavior
Because of the two gates, the default UX is: **serve the cached copy instantly (UI is never blank), then revalidate in the background on a trigger and swap silently if it changed.** This is what makes a page's number render immediately and then quietly update a beat later.

The anti-pattern it replaces: a **blocking** refetch that shows a spinner on every visit for data the app already has a snapshot of. Concretely — a cart that already knows its contents shouldn't make the customer stare at a loader for 800ms; it should show the products *instantly* from the snapshot and update prices in the background if anything changed. SWR turns "spinner every visit" into "instant, then quietly correct."

### Mutations and invalidation (writes)
Reads are `useQuery`; writes are `useMutation`. After a successful write, the cached read is now stale — you tell the cache to refetch by **invalidating** the relevant query key:

```tsx
const qc = useQueryClient()
const addRepo = useMutation({
  mutationFn: createRepo,
  onSuccess: () => qc.invalidateQueries({ queryKey: ['repos', username] }),
})
```

Invalidation is the explicit "a trigger" from the staleTime model: it marks matching queries stale and refetches the active ones, so the UI reflects the write without manual cache surgery.

   ┌── fresh?  (within staleTime) ──▶ yes ──▶ return cache, no fetch

                                          │
                                          ▼
                                   revalidate in background ──▶ swap if changed
```

## Common Pitfalls
- **Treating server data like client data.** Dropping fetched data into `useState` + `useEffect` re-implements caching, staleness, and refetching by hand — badly, and duplicated in every component. That hand-rolled `fetch + loading/error/empty + cleanup` block is exactly what `useQuery` deletes.
- **Folding the empty state into loading.** A successful fetch returning `[]` is its own branch; hiding it makes an empty result look like it's still loading forever.
- **A fetcher that doesn't throw on `!res.ok`.** `fetch` does *not* reject on 4xx/5xx. If the fetcher returns the error body as data, the error branch never fires and the empty/error states blur. Always `throw` on a non-ok response.
- **Confusing `isPending` with `isLoading` (v5).** `isPending` means *status is 'pending'* → "no data yet," which is **not** the same as "currently fetching." A **disabled** query (`enabled: false`) sits at `status: 'pending'` + `fetchStatus: 'idle'`, so `isPending` stays `true` even though nothing is loading — gating a spinner on `isPending` shows a loader forever. Use `isLoading` (`isPending && isFetching`) for a true "first fetch in flight," or handle the idle case explicitly.
- **Blocking refetch instead of SWR.** Showing a spinner on every visit for data you already cached throws away the whole point. Render from the snapshot; revalidate in the background.
- **Silent truncation.** Capping a list (e.g. `per_page=100`, first page only) without noting it hides a real limit; make bounded coverage explicit in a comment or the UI.
