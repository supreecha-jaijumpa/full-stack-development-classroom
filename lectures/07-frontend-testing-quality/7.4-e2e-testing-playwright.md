# 7.4 — E2E Testing (Playwright)

> Module: 07 — Frontend Testing & Quality · First taught: 2026-09-17 · Last updated: 2026-09-17

## TL;DR
An end-to-end (E2E) test runs the real, built app in a real browser the way a user would, so it is the only layer that catches failures in the *seams* — build output, routing, env config, cookies/CORS, and the handoff between pages. That makes it the most expensive and most flake-prone layer, so treat it as a small deliberate budget: cover only the 1–3 critical journeys. Playwright removes guessing about timing: actions auto-wait for the element to be actionable, and web-first assertions (`await expect(locator).toBeVisible()`) retry until a condition holds. Reliability comes from isolation (fresh browser context, unique data per test), a deliberate choice between a real backend and `page.route` fakes, traces for debugging CI-only failures, and a CI job that uploads the report.

## Key Concepts

### What E2E is for — the seams
Unit and component tests check pieces in isolation (jsdom, faked network). They cannot catch:
- a broken production build (wrong env variable, wrong `base` path),
- a route wired to the wrong page,
- CORS, cookie, or redirect problems that only appear in a real browser,
- two pages that each work, but the handoff between them breaks.

**Rule:** E2E is a budget, not a coverage target. Cover the 1–3 flows where "if this breaks silently for an hour, it costs money or trust." Everything else is pushed down to component and unit tests (the pyramid rule from 7.1: test at the lowest level that can still catch the bug).

Why not "an E2E test per page": each test is slow (real browser, real services), and flakiness compounds — if each of 60 tests fails spuriously even 1% of the time, a fully green run stops being the normal outcome, and the team learns to ignore red builds.

### Setup — test what ships
`npm init playwright@latest` scaffolds the config and an `e2e/` folder. Point `webServer` at the **production build**, not the dev server:

```ts
// playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './e2e',
  fullyParallel: true,
  forbidOnly: !!process.env.CI,          // a stray test.only fails CI instead of silently skipping the suite
  retries: process.env.CI ? 2 : 0,
  reporter: process.env.CI ? [['github'], ['html', { open: 'never' }]] : 'html',
  use: {
    baseURL: 'http://localhost:4173',     // vite preview port
    trace: 'on-first-retry',
  },
  projects: [{ name: 'chromium', use: { ...devices['Desktop Chrome'] } }],
  webServer: {
    command: 'npm run build && npm run preview',
    url: 'http://localhost:4173',
    reuseExistingServer: !process.env.CI,
  },
});
```

Keep Vitest away from Playwright files — Vitest's default `include` also matches `e2e/*.spec.ts`:

```ts
// vitest.config.ts
import { configDefaults } from 'vitest/config';
// ...
test: { exclude: [...configDefaults.exclude, 'e2e/**'] }
```

### Locators — the same role-first idea as RTL
`page.getByRole('button', { name: 'Search' })`, `page.getByLabel('Email')`, `page.getByText(...)`. The query priority learned in React Testing Library transfers directly, and a failing role query still doubles as an accessibility signal. Locators are **lazy** — they describe how to find an element and are resolved each time they are used.

### Auto-waiting and web-first assertions — no sleeps
- **Actions auto-wait.** Before `click()`, Playwright waits until the element is attached, visible, stable (not animating), enabled, and receiving pointer events (not covered).
- **Web-first assertions retry.** `await expect(locator).toBeVisible()` re-checks until it passes or the timeout (5 s by default) runs out. It is a **condition wait** — the Playwright counterpart of RTL's `findBy*`.
- **A fixed sleep (`page.waitForTimeout(500)`) is a guess**: too short on a slow machine (flaky), too long on a fast one (slow suite).

**Snapshot vs. condition:**

```ts
// ❌ snapshot — checks once, right now; plain expect does not retry
expect(await page.getByRole('heading', { name: 'facebook/react' }).isVisible()).toBe(true);

// ✅ condition — retries until visible or timeout
await expect(page.getByRole('heading', { name: 'facebook/react' })).toBeVisible();
```

The `await` in the first line only waits for the *check* to finish, not for the heading. On a fast laptop the heading is usually already rendered, so it passes; on CI (fewer shared CPU cores, parallel workers, variable API latency) the page is slower, the heading isn't there at the moment of the check, and the test fails intermittently.

### Auth — log in once with `storageState`
A setup project logs in through the UI once and saves cookies + localStorage; test projects start from that file.

```ts
// e2e/auth.setup.ts
import { test as setup, expect } from '@playwright/test';

const authFile = 'playwright/.auth/admin.json';   // gitignore it — it's a live session

setup('log in as admin', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill(process.env.E2E_EMAIL!);
  await page.getByLabel('Password').fill(process.env.E2E_PASSWORD!);
  await page.getByRole('button', { name: 'Sign in' }).click();
  await expect(page.getByRole('button', { name: 'Account' })).toBeVisible(); // login finished before saving
  await page.context().storageState({ path: authFile });
});
```

```ts
// playwright.config.ts — projects
projects: [
  { name: 'setup', testMatch: /.*\.setup\.ts/ },
  {
    name: 'chromium',
    use: { ...devices['Desktop Chrome'], storageState: 'playwright/.auth/admin.json' },
    dependencies: ['setup'],
  },
],
```

Each test still gets a **fresh browser context** (isolated cookies/storage), just pre-logged-in.

### Isolation — the browser is isolated, the server is not
Parallel workers share the backend. Two tests that both "create role `Editor` → delete `Editor`" collide randomly. Give each test its own data:

```ts
test('admin creates and deletes a role', async ({ page }, testInfo) => {
  const roleName = `e2e-role-${testInfo.workerIndex}-${Date.now()}`;
  // create → expect the row visible → delete → expect the row gone
});
```

Tests must also never depend on running in a particular order.

### Network — real backend or `page.route`?

```ts
await page.route('https://api.github.com/repos/*/*', (route) =>
  route.fulfill({ json: reactRepoFixture }),
);
```

| | Real backend | `page.route` fake |
|---|---|---|
| Tests the real contract | ✅ | ❌ — API shape changes go unnoticed |
| Deterministic and fast | ❌ | ✅ |
| Main risk | Rate limits and outages (unauthenticated GitHub: 60 requests/hour per IP; CI runners share IPs → random 403s) | Fixture drifts away from reality |

**Default:**
- **Backend you own** → use it for real (seeded test database or staging). Testing that seam is the point of E2E.
- **Third-party API you don't control** → fake it with `page.route`, **plus** one scheduled smoke test against the real API to catch contract changes. Faking everywhere with no real check means the tests stay green while production breaks.

**Next.js caveat:** `page.route` only intercepts requests made *by the browser*. A `fetch` in a Server Component or route handler runs on the server and is invisible to Playwright — fake those on the server side (e.g. MSW in Node, or a test backend URL via env).

### Flakiness — sources and fixes

| Source | Fix |
|---|---|
| Fixed sleeps, snapshot checks (`isVisible()`) | Web-first assertions |
| Parallel tests sharing server data | Unique data per test |
| Order-dependent tests | Each test sets up its own state |
| Real third-party network | `page.route` + a separate smoke test |
| CI timezone / locale differs | `use: { timezoneId: 'Asia/Bangkok', locale: 'en-US' }` |
| Animations | Actions wait for stability; otherwise `reducedMotion: 'reduce'` |

**Retries** keep one flake from blocking CI, but a pass-on-retry is reported as **flaky** — treat that as a bug ticket, not a pass. Sometimes the race is in the app, and real users hit it too.

### Debugging — headed, UI mode, trace viewer
- `npx playwright test` — headless (default).
- `--headed` — watch the browser. `--ui` — step through tests interactively.
- `trace: 'on-first-retry'` records `trace.zip` when a test is retried; open it with `npx playwright show-trace trace.zip`. It shows an action timeline, **DOM snapshots before/after each action**, network requests, and console output — the tool for CI-only failures you can't reproduce locally.

### CI (GitHub Actions)

```yaml
# .github/workflows/e2e.yml
name: e2e
on: [pull_request]
jobs:
  e2e:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test
      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}            # upload the report even when tests fail
        with: { name: playwright-report, path: playwright-report/, retention-days: 7 }
```

The CI reporter must include `html` (see the config above) — the `github` reporter alone writes no `playwright-report/` folder, so the upload step would have nothing to upload.

## Examples

**Which flows deserve E2E:**
- GitHub: sign in → open a pull request → merge. If this breaks, the product is effectively down even if every component test is green.
- Netflix: sign in → pick a profile → press play.
- "Change your avatar" does not need E2E — a component test covers it.

**Repo Pulse happy path (search → dashboard):**

```ts
// e2e/search-to-dashboard.spec.ts
import { test, expect } from '@playwright/test';

test('user searches a repo and lands on its dashboard', async ({ page }) => {
  await page.goto('/');

  await page.getByRole('textbox', { name: 'Repository' }).fill('facebook/react');
  await page.getByRole('button', { name: 'Search' }).click();   // auto-waits until clickable

  await expect(page).toHaveURL(/\/repos\/facebook\/react$/);
  await expect(page.getByRole('heading', { level: 1, name: 'facebook/react' })).toBeVisible();
  await expect(page.getByRole('region', { name: 'Stars' })).toContainText(/\d/);  // needs <section aria-labelledby=...>
});
```

This version calls the real GitHub API — acceptable for a local smoke run, but for the everyday suite the GitHub calls should be faked with `page.route` (third-party dependency, rate-limited).

## Diagrams

```
Where each layer catches bugs

 Unit        ── pure logic (formatters, reducers)             ~1 ms
 Component   ── one component's behavior, network faked       ~100 ms
 E2E         ── built app + real browser + seams between      seconds
                pages, routing, build, cookies, backend
                → only the 1–3 critical journeys
```

```
Snapshot vs condition wait

 isVisible():        t0 ──check──▶ false ──▶ expect(false).toBe(true) ✗
 toBeVisible():      t0 ─check✗─ t1 ─check✗─ t2 ─check✓──▶ pass
                                                 (or timeout at 5 s ✗)
```

## Common Pitfalls
- Using `page.waitForTimeout(...)` or `expect(await locator.isVisible()).toBe(true)` — both are guesses about time; use web-first assertions.
- Writing E2E tests for every page — slow, flaky, and duplicates component tests.
- Running E2E against the dev server — it doesn't test what ships.
- Letting Vitest pick up `e2e/*.spec.ts` because the default include pattern matches it.
- Assuming a fresh browser context also means fresh server data — parallel tests collide on shared records.
- Faking every third-party call with no real check at all — contract changes pass silently.
- Expecting `page.route` to intercept server-side `fetch` in Next.js Server Components.
- Treating "passed on retry" as green instead of as a flakiness bug.
- Using only the `github` reporter in CI, then uploading an HTML report folder that was never created.
- Committing `playwright/.auth/*.json` — it contains a live session.
