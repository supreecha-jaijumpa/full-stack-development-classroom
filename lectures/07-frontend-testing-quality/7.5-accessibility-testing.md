# 7.5 — Accessibility Testing

> Module: 07 — Frontend Testing & Quality · First taught: 2026-09-17 · Last updated: 2026-09-17

## TL;DR
Assistive technology reads the **accessibility tree** (role, name, state), not pixels, so treat that tree as a public API contract. Test it in layers: lint → role-first queries and axe in component tests → axe in E2E on real pages (where colour contrast can be checked) → manual keyboard and screen-reader passes. Automated tools only check **generic rules on one DOM snapshot**, so "axe passes" means "no *detectable* issues", not "accessible". Gate in CI deliberately: scope narrowly, never disable a rule globally without a reason, and use a baseline ratchet for existing debt.

## Key Concepts

### Why accessibility is an architecture concern
- **Users:** people who use only a keyboard, people on screen readers, people with low vision, and anyone with a temporary impairment (for example, a broken trackpad).
- **Law:** the EU Accessibility Act has been enforced since June 2025, and ADA lawsuits are common in the US.
- **Blast radius:** an inaccessible shared component (for example, a design-system `<Select>`) spreads the bug to every screen that uses it. Fixing it once at the source fixes it everywhere.

### The accessibility tree is a public API
The browser derives an accessibility tree from the DOM. Every node exposes:

| Property | Example |
|---|---|
| **Role** | `button`, `checkbox`, `dialog`, `group` |
| **Name** | "Delete repository" |
| **State** | `checked`, `expanded`, `busy`, `disabled` |

If the role, name, or state is wrong, the contract is broken for assistive-technology users, even when the UI looks perfect. The usual target standard is **WCAG 2.2 AA**, organised under **POUR**: Perceivable, Operable, Understandable, Robust.

### The layered strategy

| Layer | Tool | Catches |
|---|---|---|
| Static | `eslint-plugin-jsx-a11y` | `<img>` without `alt`, click handlers on non-interactive elements |
| Component | Role-first queries (RTL) + axe run in Vitest | Missing names, wrong roles, invalid ARIA |
| E2E | `@axe-core/playwright` | All of the above on real pages, plus **colour contrast** (jsdom has no layout, so contrast can't be computed there) |
| Manual | Keyboard-only pass, screen reader (VoiceOver / NVDA), 200% zoom | Meaning, reading and focus order, whether the flow makes sense |

Automated tools catch only part of real-world issues. Deque, the company behind axe, estimates roughly half by volume, and many WCAG criteria can only be partly checked by a machine.

### What axe can and cannot know
axe applies **generic rules to one snapshot of the DOM**. That explains its blind spots:
- **It can** flag an input with no accessible name, invalid ARIA, or low contrast.
- **It can be satisfied too easily.** A `placeholder`, `title`, or `aria-label` counts as a name, so an input whose *visible* label isn't linked can still pass. `getByLabelText('Visible label')` is stricter.
- **It cannot** know your app's meaning. Ten checkboxes all named "Edit" are valid HTML. A role query like `getByRole('checkbox', { name: 'Edit' })` throws "multiple elements found", which forces a fix: wrap each set in `role="group"` with `aria-labelledby`.
- **It cannot** know about state that changes over time. It has no idea a region is still loading, so a missing `aria-busy` or loading announcement needs an explicit test or a manual pass. Screen readers handle `aria-busy` alone inconsistently, so it is often paired with a visually hidden live region ("Loading roles…").

### Keyboard and focus
A modal dialog makes four promises:
1. **Focus moves in** when it opens.
2. **Focus is trapped** inside while it is open.
3. **Escape closes** it.
4. **Focus returns** to the trigger when it closes. This is the one most often forgotten: without it, keyboard users are dropped back at the top of the page.

Also: use real `<button>`s rather than clickable `<div>`s, style `:focus-visible` rather than removing outlines, and give repeated icon buttons names that tell them apart ("Delete Editor role", not "Delete").

### Scoping, disabling, and baselines
- **`include` / `exclude`** limit the audit to the area you own. Excluding a narrow third-party widget is better than disabling a rule.
- **`disableRules`** turns a rule off everywhere, including code written later. CI stays **green** and new violations ship silently. The check goes blind; it does not fail loudly. Every disable needs a written reason and a ticket.
- **Baseline ratchet:** for a legacy app with many existing violations, record today's violations (rule ID + target), fail only on new ones, and shrink the baseline over time. A gate that is always red gets switched off.

### The Lighthouse accessibility score
It runs a weighted **subset of axe rules** on **one page, in one state**. It doesn't see open modals, error states, or pages behind login unless you script them. A score of 100 means "no detectable issues in that one snapshot". Track it as a trend, not as proof.

### Where to gate in CI

| When | Check | Blocks the merge? |
|---|---|---|
| Every PR | `jsx-a11y` lint | Yes |
| Every PR | Component tests (role queries + axe) | Yes |
| Every PR / main | E2E axe on critical pages **in their interesting states** (modal open, form errors) | Yes, on new violations |
| Per release / new shared component | Manual keyboard + screen-reader pass | Part of the Definition of Done |

**Fix at the source:** check contrast once on the design tokens, and test focus management once in the shared `<Dialog>`. Every screen then inherits the fix.

## Examples

### axe in an E2E test
```ts
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('dashboard has no detectable a11y violations', async ({ page }) => {
  await page.goto('/dashboard');
  // Wait for real content, or you're auditing the loading skeleton
  await expect(page.getByRole('heading', { name: 'Repo Pulse' })).toBeVisible();

  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa'])
    .analyze();

  expect(results.violations).toEqual([]);
});
```

### Scoped audit with a justified exclusion
```ts
new AxeBuilder({ page })
  .include('main')
  .exclude('#intercom-widget')   // third-party code: not ours to fix here
  .disableRules(['region'])      // ticket A11Y-42: layout refactor pending
```

### Keyboard-only dialog test
```ts
test('delete dialog manages focus', async ({ page }) => {
  await page.goto('/admin/roles');
  const trigger = page.getByRole('button', { name: 'Delete Editor role' });
  await trigger.focus();
  await page.keyboard.press('Enter');

  const dialog = page.getByRole('dialog', { name: 'Delete role?' });
  await expect(dialog.getByRole('button', { name: 'Cancel' })).toBeFocused(); // moved in

  for (let i = 0; i < 5; i++) await page.keyboard.press('Tab');
  await expect(dialog.locator(':focus')).toHaveCount(1);                      // trapped

  await page.keyboard.press('Escape');
  await expect(dialog).toBeHidden();                                          // closes
  await expect(trigger).toBeFocused();                                        // returned
});
```

### A role & permission admin screen: which layer catches which bug?

| Bug | Caught by | Why |
|---|---|---|
| Form label not linked to its input | axe (if the input has no other name) and `getByLabelText` (always) | Missing accessible name is a generic rule, but a placeholder can satisfy axe |
| Every permission group has checkboxes named "View" / "Edit" / "Delete" | Role-first query | Duplicate names are valid HTML, so axe has no rule for them; `getByRole` throws on multiple matches |
| Loading skeleton with no busy state or announcement | Explicit test or manual screen-reader pass | "Still loading" is state over time; a snapshot can't reveal it |

Fix for the duplicate names, and a test that reads the way a screen-reader user navigates:
```ts
const repos = screen.getByRole('group', { name: 'Repositories' });
await user.click(within(repos).getByRole('checkbox', { name: 'Edit' }));
```

### Common fixes

| Issue | Fix |
|---|---|
| `<div onClick>` | `<button>`: you get keyboard support, focus, and the role for free |
| Icon-only button | `aria-label="Delete Editor role"` |
| Decorative image | `alt=""` (empty, not missing) |
| `outline: none` | Style `:focus-visible` instead |
| Poor contrast | Change the design **token**, not each component |

### Design-review phrasings
- *"A 100 doesn't mean accessible. Lighthouse and axe only check generic rules on the snapshots they see, so they miss other states, focus flow, and meaning. Because of that, bugs reach production. The people who pay are users who can't complete the task, and our team, who find out from complaints instead of tests. We still need keyboard and screen-reader passes."*
- *"Disabling contrast globally is a bad trade. The problem is it turns the check off for everything, including code we write next week, so new contrast bugs ship while CI stays green. Because of that, the debt grows without anyone seeing it. The people who pay are low-vision users who can't read our UI, the company, which carries the legal risk, and our team, who later face a much bigger cleanup. Instead, let's baseline the known violations so the release ships, keep the rule on for everything else, and fix the brand token with a darker text variant."*

## Common Pitfalls
- Treating "axe passes" or "Lighthouse 100" as "accessible". They only mean "no detectable issues in these snapshots".
- Running axe before content loads, which audits the skeleton instead of the real UI.
- Auditing only the default state of a page and never the open modal or the error state.
- Relying on axe for form labels while inputs carry placeholders, which satisfy the rule even when the visible label isn't linked.
- Believing a globally disabled rule will "show up as red later". A disabled rule doesn't run, so CI stays green while new violations ship.
- Accepting a global disable "temporarily" with no ticket. Temporary disables tend to become permanent.
- When a legacy app has many violations, answering "disable the rule" or "skip the suite" instead of **baseline + fix at the source**.
- Forgetting to return focus to the trigger when a dialog closes.
- Giving repeated icon buttons identical names ("Delete", "Delete", "Delete").
