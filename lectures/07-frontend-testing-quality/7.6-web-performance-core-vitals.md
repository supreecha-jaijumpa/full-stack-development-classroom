# 7.6 — Web Performance & Core Web Vitals

> Module: 07 — Frontend Testing & Quality · First taught: 2026-09-17 · Last updated: 2026-09-17

## TL;DR
The three **Core Web Vitals** each answer one user question: **LCP** (is it loading?), **INP** (does it respond?), and **CLS** (is it stable?). Google judges them at the **75th percentile of real page loads over 28 days**, so only **field data** (real users) is the truth. **Lab data** (Lighthouse) is for debugging and for blocking regressions before merge. Fix a metric by breaking it into its parts and targeting the slow part, then lock the gain in with **performance budgets** in CI that are raised only through a ticketed exception and tightened as things improve.

## Key Concepts

### Why performance is an architecture concern
Most performance problems come from decisions in shared layers, not from one slow component:

| Decision | Performance effect |
|---|---|
| CSR vs SSR vs RSC | When the first useful pixel appears (LCP) |
| State library choice, how widely a context re-renders | How fast the page reacts to input (INP) |
| Design-system `<Image>` / `<Card>` without reserved space | Layout shifts everywhere it's used (CLS) |
| "Just add the analytics SDK / chat widget" | Main-thread blocking the team doesn't control |
| API shape (one call vs a request waterfall) | Server response time, then LCP |

As with accessibility, a problem in a shared component has a large **blast radius**.

### The three Core Web Vitals

| Metric | User's question | Measures | Good | Poor |
|---|---|---|---|---|
| **LCP** — Largest Contentful Paint | "Is it loading?" | When the largest image or text block in the viewport renders | ≤ 2.5 s | > 4 s |
| **INP** — Interaction to Next Paint | "Does it respond?" | Delay from a click, tap or key press to the next frame; the reported value is roughly the worst interaction of the visit | ≤ 200 ms | > 500 ms |
| **CLS** — Cumulative Layout Shift | "Is it stable?" | Unexpected movement of visible content (the worst burst of shifts) | ≤ 0.1 | > 0.25 |

- **p75 rule:** Google evaluates the 75th percentile per URL group over a rolling 28-day window (CrUX). If the slowest quarter of visits is slow (typically mid-range phones on weak networks), the page fails.
- **INP replaced FID (March 2024).** FID measured only the input delay of the *first* interaction. INP covers every interaction, including processing and paint, so heavy re-renders now count.

### Breaking each metric into parts
- **LCP** = TTFB (server) → resource load delay (was the hero discovered late?) → resource load time (size, format, CDN) → render delay (blocking JS, fonts, hydration).
- **INP** = input delay (main thread already busy) → processing time (event handlers, React re-render) → presentation delay (layout and paint of a large DOM).
- **CLS** comes from media, ads or embeds without reserved size, late web fonts, and content inserted above what the user is reading.

**Trace the number to the metric:** script size and TBT measure main-thread JavaScript work, so they predict **INP**, not CLS. Check what a failing number actually measures before naming the metric it affects.

### Lab data vs field data

| | **Lab** (Lighthouse, DevTools Performance panel) | **Field / RUM** (CrUX, `web-vitals`, Search Console) |
|---|---|---|
| Who | One simulated device and network | Real users |
| When | On demand, in CI | After deploy, collected over time |
| Good for | Debugging; blocking regressions before merge | The truth; what Google ranks on |
| Blind spots | One page, one state, no real interactions, fast machine, small test data | Slow feedback (28-day window), little detail on *why* |
| INP | **Not measurable** (nobody interacts); **TBT** is the lab proxy | ✅ |

**Rule:** lab data *prevents* regressions, and field data *judges* the product. You need both.

### Fixes mapped to metrics

| Metric | Main fixes |
|---|---|
| **LCP** | Server-render or preload the hero; never lazy-load the LCP image; `fetchpriority="high"`; AVIF/WebP with `srcset`; CDN; remove request waterfalls |
| **INP** | Ship less JS; split long tasks; `useTransition` / `useDeferredValue`; virtualise long lists; narrow context and store subscriptions; load third-party scripts with `async`/`defer` or on interaction |
| **CLS** | Set `width`/`height` or `aspect-ratio` on media; reserve space for embeds and skeletons; font fallback metrics (`size-adjust`) plus `font-display`; never insert content above the reading position |

### Bundle size
JavaScript costs download time **plus parse and execute time on the main thread**. On mid-range phones, parse and execute usually dominate.
- **Route-level code splitting** keeps code for other routes out of the initial load.
- **Tree-shaking** needs ESM imports (`lodash-es/debounce`, not the whole `lodash`). Large barrel files can defeat it.
- **Analyse before cutting**, for example with `rollup-plugin-visualizer` in Vite.

### Caching and loading order
- Hashed assets: `Cache-Control: public, max-age=31536000, immutable` (a new build produces a new file name).
- HTML: `Cache-Control: no-cache` (always revalidate so users get the new asset names).
- Render-blocking resources in `<head>` delay every paint: use `defer` for your scripts and load third-party scripts last.

### Performance budgets
A budget is a line in CI that a PR can't cross without a conversation.
- Run Lighthouse several times per check (lab numbers are noisy, and a flaky gate gets ignored).
- **Raising a budget requires an exception** with a ticket, owner, and expiry date, scoped to the change. Never delete the assertion: a deleted or loosened budget means CI stays **green and blind** to the next regression.
- **Ratchet down:** when a metric improves, tighten the budget.
- **Two loops:** lab budgets block the PR before merge; field RUM plus alerts catch what the lab can't see after deploy.

## Examples

### Collecting field data with `web-vitals`
```ts
// src/reportWebVitals.ts
import { onLCP, onINP, onCLS, type Metric } from 'web-vitals';

function send(metric: Metric) {
  // sendBeacon survives page unload — fetch may be cancelled
  navigator.sendBeacon('/api/vitals', JSON.stringify({
    name: metric.name,          // 'LCP' | 'INP' | 'CLS'
    value: metric.value,
    rating: metric.rating,      // 'good' | 'needs-improvement' | 'poor'
    page: location.pathname,
  }));
}

onLCP(send);
onINP(send);
onCLS(send);
```
The `web-vitals/attribution` build also reports *which* element or interaction was slow.

### LCP image vs below-the-fold images
```tsx
<img src="/hero.avif" width={1200} height={600} fetchPriority="high" alt="…" />
<img src="/chart.avif" width={600} height={300} loading="lazy" alt="…" />
```

### Keeping typing responsive during a heavy filter
```tsx
const [query, setQuery] = useState('');
const deferredQuery = useDeferredValue(query);
const rows = useMemo(() => filterRepos(repos, deferredQuery), [repos, deferredQuery]);
```

const router = createBrowserRouter([

```

    }
  }

```

### Scenario: "Which one is lying?"
A GitHub-style repo dashboard scores Performance 97 in Lighthouse on a developer laptop (LCP 1.1 s, TBT 40 ms), while Search Console rates it "Poor" (LCP p75 4.3 s, INP p75 420 ms). Neither is wrong:
- the laptop has a fast CPU, a warm cache, and a small test account;
- real power users have many repos, so there is more data to load and a larger DOM to re-render;
- CrUX is a 28-day p75, so older regressions are still counted;
- Lighthouse only measured the first load and never clicked anything, so it has no INP value at all.

> "Neither is lying. Lighthouse measures one first load on a fast simulated device with a tiny account; Search Console measures the p75 of real users over 28 days, including every click. We debug with Lighthouse, but we judge ourselves by field data."

### Scenario: "Just raise the budget before launch"
A PR adds a third-party chat widget and an analytics SDK. Lighthouse CI fails: script size 410 KB (budget 250 KB), TBT 480 ms (budget 200 ms). A recommended response:

> "If we raise the budget, CI stays green even when the next PR adds another 40 KB, so we're blind. That means INP gets worse: clicks feel slow, first for users on mid-range phones. Instead, we load the chat widget only when the user clicks 'Chat' and load analytics with `defer`. If we're still over, we allow a temporary exception for this PR only, with a ticket, owner, and date, so we still ship on time. Otherwise users pay first with a slow dashboard, then the business pays when Search Console marks the page 'Poor', and then the team pays by fixing it under pressure."

## Diagrams

```
LCP = TTFB  →  resource load delay  →  resource load time  →  render delay
INP = input delay  →  processing time  →  presentation delay
CLS = unsized media · late fonts · content injected above the reading position

  PR ──► Lighthouse CI budgets (lab) ──► merge ──► deploy ──► web-vitals RUM (field) ──► alerts
         prevents regressions                                  judges the product
```

## Common Pitfalls
- Treating a high Lighthouse score as proof that users have a fast experience. It covers one first load on a simulated device.
- Expecting Lighthouse to report INP. It can't, because nobody interacts; TBT is only a proxy.
- Naming the wrong metric for a failing number. Script size and TBT are main-thread work, which affects INP, not CLS.
- Lazy-loading the LCP image, which delays the very metric you want to improve.
- Raising or deleting a budget "for now". CI stays green and hides every later regression; use a scoped, ticketed exception instead.
- Loading third-party widgets eagerly on page load when they're only needed after a user action.
- Testing performance with a small test account and a warm cache, which hides the slow p75 users.
